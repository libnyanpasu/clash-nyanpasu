# MCP 入口 任务卡（M0，A–G）

[设计](design.md) r9 的执行清单。D-1 至 D-18 全部已裁定，各卡按依赖顺序即可动工。

约定：

- 一张卡是一个 PR，一个 PR 做一件事并且能独立构建（`workflow.md` 的提交规则）。
- 现有五种参与者的授权、共享与可见性不变。权限基线（`nyanpasu-rpc/src/permission_baseline.rs`，含 `:351-363` 写死的行数）的比较按“原有的行在原有三个目标上不变”判定；每张卡在“基线”一栏列出它新增的行，除此之外的差异为空。`redaction` 与 `privacy` 的现有测试不改期望。
- 线上方法名、函数名不改。
- “验证”列的每一项都要能机械地判断通过与否，每个情形只有一个期望结果。
- 改了 guide 所述规则的卡，在同一 PR 里改 guide。重新生成时三个绑定文件一起：`frontend/rpc/src/tauri-bindings.ts`、`frontend/rpc/src/rpc-bindings.ts`、`frontend/query/src/query-bindings.ts`。
- 开始前按 `workflow.md` 评估是否使用 worktree。
- 后端测试只测公开行为：纯函数用普通值，actor 经类型化客户端加假适配器，HTTP 经真实监听；用假时钟与显式的同步点（屏障），不用全局夹具与 sleep（`testing.md`）。
- 每张后端卡结束前跑：`cargo test -p nyanpasu-rpc-macro --features syn/full rpc_resource_table_is_fresh`、受影响 crate 的测试、`pnpm run lint:backend-boundaries`、`pnpm run lint:architecture-ledger`。`nyanpasu-rpc` 的特性组合只跑当时已经存在的：C-1 之前没有 `mcp`；C-1 起加 `--features mcp`。

依赖与特性出现的顺序：

```text
M0 ─┬─> A-1 ──> A-2 ──> B-1 ───────────────────────────────┐
    └─> C-1（特性 mcp：schemars；RpcTarget/RpcTransport::Mcp；ResponseVisibility::Agent）
          ├──> C-2（暴露面与投影）──────────┐                │
          └──> D-1（另需 A-1）──> D-2 ──> D-3（另需 C-2）──> F-1（另需 A-2、B-1）──> E-1 ──> E-2 ──> G-1
                                                              E-1 把 dep:rmcp 加进特性 mcp
```

- D-1 用到 `RpcTarget::Mcp`、`RpcTransport::Mcp` 与 `ResponseVisibility::Agent`，所以在 C-1 之后。
- D-3 是暴露面在真实管线上的回归：它要 C-2 的命令与 D-1、D-2 的分派都在，所以单独成卡。
- F-1 用到 B-1 导出的 `MCP_MAX_ROLE_HEADER`。
- **E-1 在 D-2 与 F-1 之后：** 入口没有独立开关，一合入就可用；届时数据共享层要已经在位，所有者也要已经有页面可以作答。A-2 到 E-1 之间 `MCP_PATH` 由占位路由占住。
