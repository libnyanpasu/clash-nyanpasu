## 热度依据

仓库没有使用埋点，以下热度来自任务推断，置信度中：

- 高：总量与上下行、进程与主机排行、出口排行（按流量计费的订阅）。
- 中：当前速率；选中一项后下钻。
- 中低：路径诊断，通常从规则页或连接页跳转进入。
- 低：地理分布；单机用户的来源与入站。

## P2 项目

### 1. 总览路径预览（TODO：等查询优化后再加）

总览排行下方放一张路径预览：每列 3 个节点，模板跟随路径页；点节点在总览内筛选，“展开”进入路径页；替换网格最后一格的两个入口按钮。

这个预览曾在本分支实现，后因成本移除：总览每次轮询都要多算一份拓扑，拓扑又会先为每一行建出全部节点和边，每列 3 个的限制只作用于输出。合成库上的实测见 [查询性能 review](../review/2026-10-16-traffic-report-query-performance.md)：带预览的概览单次成本是只算排行时的 2.2–2.7 倍（S 库 7 天：109 → 241 ms；M 库 7 天：311 → 717 ms）。

更早的一组测量（每列 7 个节点的路径，`report` 的合成行，release，每档取 5 轮交替运行中的最小值）：

| 行数 | 仅排行（进程筛选） | 排行 + 路径 |
| ---- | ------------------ | ----------- |
| 10k  | 1.45 ms            | 2.46 ms     |
| 100k | 16.97 ms           | 26.93 ms    |
| 500k | 85.96 ms           | 134.15 ms   |

**加回的前提**，满足其一即可：

- review 的 #3（拓扑改为两遍、用数字节点 id）或 #1（维度值驻留为整数编号）已落地；
- 拓扑从概览的 2 s 轮询中拆出来，单独以 10 s 查询，或者只在预览进入视口时才请求。

**验收：** 带预览的概览单次耗时不超过只算排行时的 1.3 倍（用 review 中的基准测量）。

### 2. 规则排行卡

后端 `Dimension::Rule` 已经支持排行，前端只需在 `RANKINGS` 里加一项。

- 收益：直接回答“哪条规则命中的流量最多”，有助于调整规则。从规则页跳来时已带上 rule 筛选，配合“排行忽略自身筛选”，能看到同一 profile 下其他规则的对比。
- 待定：放在热度排序的第几位；单机用户的总览会因此多一张卡。

### 3. 时间趋势图

`TrafficReport` 没有时间序列，需要后端按桶返回序列，并新增查询与 RPC，应单独立项。竞品（Clash Party、MetaCubeXD）的历史统计页都有趋势图，见 `docs/report/2026-09-16-traffic-topology-research.md`。

## 已放弃

### 筛选变更改用 `replace` 写入历史

原计划让筛选变更不再推入浏览器历史，使“返回”直接离开页面。路径页和地图页已能显示排行，不再需要回总览看结果；而且改用 `replace` 后返回总览时，路径页上选的筛选同样会丢失。收益不足以改变现有的历史行为，因此不做。

## 相关的既有问题（非本次引入）

- `frontend/nyanpasu/src/generated/data-slots.gen.ts` 在 main 上已过期（缺少多个已有 slot）；在 Windows 上重新生成会改写全部换行。本次没有更新。
