# Rust code guide

This is the Rust style for handwritten code in the parent Cargo workspace
(`backend/Cargo.toml`). It adopts the
[Google Rust Style Guide](https://google.github.io/styleguide/rustguide.html)
where it applies, and records each deliberate deviation below.

Architecture, package boundaries, RPC, and test strategy are defined by
[Architecture and ownership](architecture.md), [Backend packages](backend-packages.md),
[Unified RPC](rpc.md), and [Testing and review](testing.md). This guide covers how the
Rust is written and does not relax those rules.

Out of scope: `backend/nyanpasu-runtime` and `backend/enable-loopback` own independent
workspaces and configurations; `backend/tauri-plugin-deep-link` is a vendored fork that
keeps its upstream style; generated bindings and `build.rs` output follow their
generators.

## 1. Rule status

- "Must" and "do not" are requirements. "Prefer" and "should" are defaults that a
  review may waive for a stated reason.
- New code must follow this guide. Existing code that does not is migration debt
  (section 12), not a pattern to copy.
- Changes stay minimal ([AGENTS.md](../../AGENTS.md) §3). Do not bring surrounding
  code up to this guide as part of an unrelated change; do that in a focused
  migration change.
- A deviation from Google listed in section 2 is part of the standard. Do not add
  other local exceptions; propose a change to this guide instead.

## 2. Deviations from Google

| Google guidance                                                               | Project decision                                                                                                                                                                    |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prefer small crates; flat `rust_library` layout [chrome]                      | Conventional Cargo layout. Crates follow ownership and dependency boundaries ([Backend packages](backend-packages.md)), not size.                                                   |
| Import at `Module` granularity                                                | Keep rustfmt's `imports_granularity = 'Crate'`. A workspace-wide import rewrite does not justify its churn.                                                                         |
| Don't implement APIs in non-leaf modules                                      | A capability's `mod.rs` may also hold its typed client (for example `SystemProxyClient` in `client/system_proxy/mod.rs`), because that client is the capability's public interface. |
| No `async`/`.await`; no `std` threads; `fuchsia_sync`; gtest [chrome/Fuchsia] | Tokio and ractor are the runtime. `std::thread` is allowed for a stated reason. Tests use `#[test]` and `#[tokio::test]`.                                                           |
| Prefer generics over `dyn Trait`                                              | Injected ports use `dyn Trait`; generics stay for reusable computation (section 5.3).                                                                                               |
| Never reach inside a poisoned mutex; no `catch_unwind`                        | Poison recovery is prohibited without exception (section 7.4). `catch_unwind` is prohibited except through the conditional use in section 7.3.                                      |
| No code before `main`                                                         | Kept, except that RPC commands register through `inventory` (`unified_rpc.rs`, generated by `nyanpasu_macro::rpc`). That registry must not construct services or start work.        |

Everything else in Google's guide applies, including its own exceptions: shared
ownership when alternatives are unreasonably complex, non-`Copy` errors that carry
owned data, `Vec` returns for naturally built collections, and exhaustive types whose
consumers are updated together.

## 3. Formatting, lints, and checks

### 3.1 Toolchain and rustfmt

The root `rust-toolchain.toml` selects nightly. The workspace uses Rust 2024 and
`backend/rustfmt.toml`:

| Setting             | Convention                                                                 |
| ------------------- | -------------------------------------------------------------------------- |
| Line width          | 100 columns                                                                |
| Indentation         | Four spaces, no hard tabs                                                  |
| Newlines            | `Auto`, as configured by Rustfmt                                           |
| Imports and modules | Reordered; imports grouped at crate granularity                            |
| Derives             | Merged by the formatter                                                    |
| Rewrites            | No requested try or field-init shorthand rewrites                          |
| Other syntax        | Remove nested parentheses; preserve configured heuristics and explicit ABI |

Let Rustfmt format imports, expressions, attributes, and `where` clauses. Use
`#[rustfmt::skip]` only for meaningful manual alignment, such as a matrix, or for
generated code, and say why.

A nightly toolchain does not permit unstable features. Do not add `#![feature(...)]`
or unstable lints to the parent workspace.

### 3.2 Clippy and suppressions

`pnpm lint:clippy` checks all targets and features. There is no `clippy.toml` and no
`[lints]` table, and CI does not deny warnings, so review is the gate: a change must
not add warnings, including in `cfg(windows)` or `cfg(target_os = "macos")` code that
only another OS's CI job compiles.

Suppress a lint at the narrowest scope with a reason. Prefer
`#[expect(lint, reason = "...")]`, which warns once the suppression is stale;
otherwise use `#[allow(lint, reason = "...")]`. A crate may tighten lints in its root,
as `boa_utils` forbids `clippy::unwrap_used` outside tests. Do not enable `pedantic`,
blanket `-D warnings`, or a broad allow list as a substitute for review.

### 3.3 Commands

```sh
pnpm lint:rustfmt
pnpm lint:clippy
pnpm test:backend
# Apply formatting:
pnpm fmt:backend
```

Rust files are excluded from Prettier. Staged backend files run Clippy and Rustfmt
through `.lintstagedrc.js`; tests are separate. After package-boundary changes, run
`deno task lint:backend-boundaries`; after architecture static-policy changes, run
`deno task lint:architecture-ledger`. Tauri checks also require the
[gitignored build prerequisites](workflow.md#gitignored-build-prerequisites-a-fresh-worktree-lacks).
Process-lifecycle tests need the `fake-core` binary built; a dev-dependency alone does
not build it (`backend/tauri/Cargo.toml`).

## 4. Modules and imports

- Give a leaf module one responsibility, and name it after its primary item or, inside
  a capability directory, after its role: `actor.rs`, `ports.rs`, `adapters.rs`,
  `error.rs`, `tests.rs` (see `client/system_proxy/` and `client/hotkey/`).
- Non-leaf modules contain declarations, re-exports, a small amount of wiring, and the
  typed client exception in section 2. Split a `mod.rs` that grows beyond that.
- Use the narrowest visibility that serves real consumers: private, then `pub(super)`
  or `pub(crate)`. Actor messages and raw `ActorRef`s do not leave their capability.
- Do not use glob imports. Google's exceptions are the only ones: `use super::*` in an
  inline module, `use Enum::*` in code that mostly handles that enum, and
  `pub use submodule::*` in a non-leaf re-export module. File modules that import their
  parent with `use super::*` are migration debt (section 12).
- Import a trait where it is used. When only its methods are needed, import it as
  `Trait as _` (`use snafu::ResultExt as _;`).
- Import types and use them unqualified. Keep a module path or alias when it adds
  context or avoids a collision: `io::Error`, `fmt::Result`, `Profiles as DomainProfiles`.
- Call free functions from another module through that module:
  `tokio::task::spawn_blocking(..)`, `serde_json::to_string(..)`.
- Put `use` declarations at the top of the file or function body, grouped std, external
  crates (including workspace crates), then `crate`/`super`/`self`.
- When moving code to its owner, update the callers. Do not leave a re-export at the
  old path.

## 5. Function APIs, types, and traits

### 5.1 Library and application code

Google's API rules for library code apply to code that is general-purpose and meant
for other consumers, such as `nyanpasu-local-channel`, `nyanpasu-tsdb`, and
`nyanpasu-geodata`. Application behavior stays application code after it moves into
`nyanpasu-core` or `nyanpasu-config`. Do not add generics, builders, or compatibility
APIs for callers that do not exist.

### 5.2 Inputs, outputs, and data types

- Accept flexible borrows: `&str`, `&[T]`, `&T`, `Option<&T>`, `&Path`, not
  `&String`, `&Vec<T>`, `&Box<T>`, `&Option<T>`, `&PathBuf`.
- Take ownership when the value is stored, moved into a task, or sent to an actor. Do
  not add lifetimes to an actor message to avoid an owned payload.
- Reusable libraries may accept and return iterators where real callers benefit.
  Application code may take slices and return `Vec<T>`.
- Avoid `impl Into<T>` parameters in application code unless several real call sites
  pass different types.
- Replace a `bool` parameter whose meaning is unclear at the call site with an enum.
  Opposing conventions such as `automatic: bool` (`client/app_update/`) and
  `explicit: bool` (`application_workflow/tcc.rs`) for the same idea should share one
  enum. A clear binary setting, such as `set_debug_http_enabled(enabled: bool)` or a
  serialized `enabled` field, stays a `bool`.
- Use a newtype when values with the same representation mean different things:
  `ProfileId` and `FolderId`, `EffectRevision`, `Version`. Use a type alias only as a
  shorthand.
- Prefer named fields over multi-field tuples. Single-field newtypes and short local
  tuples are fine.
- Use typed enums and actor messages for protocols and finite states, not strings or
  integers.
- Use private fields when construction must establish an invariant, and keep every
  decoding path through the validating constructor, as `ManagedProfilePath` does.

### 5.3 Traits

- Define a trait for a port, for generic code with more than one real implementation,
  or for an extension trait (`…Ext`). Do not define one only to group methods.
- Ports are owned by their consumer and kept narrow. Actor dependencies are
  `Arc<dyn Port>`; add `Send + Sync + 'static` only where the value crosses a task or
  actor boundary. Synchronous borrowed ports, such as `ProfileContentSource` and
  `ScriptRunner` in `nyanpasu-config/src/runtime/executor/ports.rs`, need neither.
- Use `#[async_trait::async_trait]` for async methods of a trait used as `dyn`. Make a
  port mockable with `#[cfg_attr(test, mockall::automock)]` where practical
  ([Testing and review](testing.md)); a handwritten fake is fine when it reads better.
- Name a port after the capability it provides. An existing `…Port` suffix
  (`OsProxyPort`, `RuntimeBuildPort`) is acceptable; do not rename for style alone.
- Implement standard traits instead of ad hoc methods: `FromStr`, `Display`, `From`
  for lossless conversions, `TryFrom` for fallible ones. Pair an important `From`
  with a named constructor.
- Derive when the derived semantics are correct. Do not derive `Clone`, `Copy`,
  `Default`, or equality for resource owners or where the operation would mislead, and
  do not give a service a dummy `Default` to avoid injecting a dependency.
- Options structs with public fields implement `Default`. Implement `len()` and
  `is_empty()` together.

### 5.4 Shared ownership

Prefer unique ownership and borrowing. `Arc` is expected for cheap handles such as
`NyanpasuClient` and typed clients, for injected ports, and for immutable snapshots
(`arc-swap` in `nyanpasu-core`, shared `ConfigValue` subtrees). `Rc`/`RefCell` stay
within a single-threaded context, as in the Boa adapter. Cloning an `Arc` is not a
deep copy; do not deep-clone only to silence the borrow checker, especially in
`nyanpasu-tsdb`, `nyanpasu-traffic`, and `nyanpasu-geodata`.

### 5.5 Attributes

- Use `#[non_exhaustive]` only for types that mirror an externally evolving protocol
  or carry an explicit stability promise. Workspace-internal enums, actor messages,
  and DTOs stay exhaustive so that a new variant fails to compile where it is not yet
  handled.
- When matching a foreign non-exhaustive enum, list the known variants and give the
  wildcard arm conservative, deliberate behavior (`CoreState` in
  `core/actor_v2/endpoint.rs`).
- Use `#[must_use]` on pure functions, builders, guards, and results that the caller
  must act on (`WindowTable::set_watchdog`). `Result` and futures already have it.
- Mark a public function `const` only when it can reasonably stay `const`.

## 6. Configuration and wire types

- Persisted types must decode files that earlier versions wrote. A new persisted field
  needs `#[serde(default)]`, `#[serde(default = "...")]`, a container default, or a
  deliberate migration. Startup parses the whole `NyanpasuAppConfig`, so a missing
  default stops existing installs from starting.
- Serialized names are on-disk and on-wire contracts. Do not change one by renaming
  the Rust item; fix it with `#[serde(rename...)]`.
- Types that cross RPC derive `serde` and `specta::Type` and live in the neutral crate
  that owns the concept. Regenerate bindings; never hand-edit them.
- Keep patch semantics distinct: an omitted field leaves a value unchanged, an explicit
  `null` clears it, and an enum definition is replaced as a whole
  (`nyanpasu-config/src/profile/patch.rs`, `profile/tests/remote_options_patch.rs`).
  Profile and application patches use `struct_patch::Patch`.
- Configuration order is behavior. Keep `IndexMap`-backed values ordered, and do not
  round-trip them through an unordered representation.

## 7. Errors, panics, and assertions

### 7.1 Choosing the mechanism

- `Option` when absence is expected and needs no cause.
- `Result` for failures a correct program can still meet: IO, network, IPC, parsing,
  validation, state conflicts, external processes.
- Panic only for a bug or a violated invariant, never for user input, files, the
  network, the core process, or the OS.

### 7.2 Error types

- Use a typed error enum when callers need to match, retry, localize, or settle a
  failure. Carry structured fields, not preformatted strings, and do not add
  string-bucket variants such as `Custom(String)`.
- Follow the error framework the module already uses. In a new module without one,
  use `snafu` (the most common choice: about 94 `Snafu` derives against 28
  `thiserror::Error`). Do not convert a module to another framework in an unrelated
  change.
- `anyhow::Result` is acceptable at the composition root, at startup, in binaries,
  and in tests. Preserve sources and add context where an error crosses a layer.
- Keep structured domain and `RpcError` information across RPC boundaries.
- A side-effect failure after a state commit is reported as degraded, not as an
  error implying the commit did not happen.
- Prefer `match`, `if let`, `let ... else`, and `?` to a check followed by
  `unwrap()`. In production code, use `expect()` with a message that states why the
  invariant holds instead of a bare `unwrap()`. Tests, examples, and benches may
  unwrap.
- Add context to assertions when the condition does not explain the failure.

```rust
let Value::Mapping(payload) = value else {
    return Err(StampError::NotAMapping);
};

let stamp = serde_yaml_ng::from_value(stamp).map_err(StampError::Malformed)?;
```

### 7.3 Panic recovery

A panic is fatal under `nyanpasu-panics`. Do not call `std::panic::catch_unwind` in
production code, and do not turn a panicking task's `JoinError` into an ordinary
error.

The only recovery path is `nyanpasu_panics::catch_recoverable`, and only under all
of these conditions:

- It wraps one synchronous call into code that is known to panic on bad input and
  whose failure must not end the process, such as a third-party launcher.
- It does not wrap async code. The recoverable flag is thread-local and does not
  follow a task across `.await`.
- The call site has a `// SAFETY:` comment, as an `unsafe` block would, that says why
  the panic is expected, why no shared state is left half-updated, and how the caller
  handles the recovered failure.
- A test covers the recovered path: a panicking call yields the error and the caller
  falls back as documented.

Tests may use `catch_unwind` to assert that something panics.

### 7.4 Poisoned locks

Never recover a poisoned lock: no `PoisonError::into_inner`, `get_mut` or
`clear_poison` on a poisoned `std::sync` lock in production code. Handle the
`LockResult` with `expect()` that states why no holder panics. Where a lock must not
fail on poisoning, use a `parking_lot` lock, which has no poisoning, instead of
recovering a `std::sync` one.

## 8. Ownership, async, and concurrency

[Architecture and ownership](architecture.md) defines ownership; the code-level
consequences are:

- Use Tokio directly in clients, actors, and services; never `tauri::async_runtime`.
  Keep pure services synchronous.
- Do not block async workers. Move blocking or CPU-heavy work to
  `tokio::task::spawn_blocking`. Respect documented execution contexts:
  `EnhanceScriptRunner` must not be called from an async worker.
- Actor-owned mutable state stays private and is serialized by the mailbox. Do not
  expose it as `Arc<Mutex<_>>` or `Arc<RwLock<_>>`. A shared lock outside an actor needs
  a stated ownership reason and a small scope.
- Use the lock type the crate already uses (`std::sync` or `parking_lot`); use
  `tokio::sync` only when a guard must be held across `.await`. Never hold a
  `std`/`parking_lot` guard across `.await`.
- In-process request/reply waits for the real result (`call(.., None)`); deadlines
  belong to network and IPC adapters. Map "the actor stopped before answering" to an
  explicit result instead of unwrapping it.
- Dropping a caller does not cancel owner-started work.
- Shutdown uses the root `CancellationToken` and each owner's cleanup. Spawn long-lived
  tasks through the injected `TaskTracker` (`drain_on_shutdown`), not a detached
  `tokio::spawn`, unless the task holds no resource.
- UI-thread work goes through the injected `MainThreadExecutor` port.
- Avoid synchronous cross-actor call cycles.
- Name a `std::thread` that outlives its function.

## 9. Macros, unsafe code, and platform code

- Prefer functions, types, and traits, then a local `macro_rules!`, then generated
  code, then a proc macro. Use the existing generators instead of hand-writing their
  output: `#[nyanpasu_macro::rpc(...)]`, `OwnedFields` and the other derives in
  `nyanpasu-macro`, and external derives such as Serde, Specta, and `struct-patch`.
- Write `unsafe` only when safe Rust cannot provide the functionality, inside a small
  safe function in a platform or low-level module. Business logic, actors, and pure
  services contain none.
- Every `unsafe` block or `unsafe impl` has a `// SAFETY:` comment stating the
  precondition and why it holds. Public unsafe functions and traits document
  `# Safety`. A performance justification links a benchmark.
- Do not add `unsafe impl Send` or `Sync` to get past an executor boundary.
- Do not call `std::env::set_var` or `remove_var` in production code.
- Gate platform code with `#[cfg(...)]` on the item, and keep the `cfg(not(...))`
  counterpart next to it with the same signature.
- Keep test-only APIs out of production interfaces: put them behind `#[cfg(test)]` or
  in test-support modules, not behind a `dead_code` suppression.
- Do not access another crate's `#[doc(hidden)]` items or overload operators as
  syntax sugar.

## 10. Naming and documentation

### 10.1 Naming

- `snake_case` for modules, functions, and fields; `PascalCase` for types, traits, and
  variants; `SCREAMING_SNAKE_CASE` for constants.
- Use role names from the architecture guide: `…Actor`, `…Client`, `Args` for actor
  startup input, port names after their capability, adapters after their technology
  (`FsProfileContentSource`), pure services after their computation (`RuntimeBuilder`). Avoid
  `Manager`, `Helper`, and `Utils`.
- `as_` for cheap borrowed views, `to_` for owned or expensive conversions, `into_`
  for consuming `self`.
- Constructors follow Google: `new()`, `new_with_foo()` when there are several, and
  `try_new()` when the constructor returns `Result`. `from_foo()` for value-to-value
  conversions with a `From` impl. Use `spawn` for a client constructor that starts its
  actor, and `parse` for validating untrusted input.
- Use `foo()`, `foo_mut()`, `set_foo()`, `take_foo()`, `replace_foo()` for accessors,
  without a redundant `get_`. Facade operations that name an application request,
  such as `NyanpasuClient::get_profiles`, are not accessors and keep their names.
- Use `'_` where possible and descriptive lifetimes when several borrows interact.
  Keep generic names short and meaningful (`T`, `S`).
- Avoid abbreviations other than established domain terms (RPC, IPC, HTTP, DNS, TUN,
  UI, OS). Do not use the legacy `verge` name in new identifiers.

### 10.2 Documentation and comments

- Document every item exported for another crate. Explain its contract (ownership,
  lifecycle, blocking or async requirements, units, ordering) instead of restating
  its name.
- A capability module starts with `//!` docs that say what it owns and why it is an
  actor, pure service, or adapter.
- Document non-obvious failures under `# Errors`, input-dependent panics under
  `# Panics`, and unsafe obligations under `# Safety`.
- Use `///` for items, `//!` for modules and crates, and `//` for implementation
  notes that explain invariants, ordering, and constraints the code cannot express.
- Do not commit commented-out code.
- Compatibility bridges keep the architecture guide's `TODO(actor-migration)` or
  `FIXME(actor-migration)` marker with its reason and removal condition.

## 11. Implementation readability, logging, and tests

- Annotate a binding when inference hides the type of `.parse()`, `.into()`, or a
  collected value; prefer that annotation to a turbofish.
- Use short iterator chains for simple transformations and a `for` loop for side
  effects, early returns, or error handling. Avoid `for_each`.
- Use `format!` and `write!` for substitution and multi-part concatenation.
- Log with `tracing` and structured fields. Do not add new `log` macros. Never log
  secrets, subscription URLs with tokens, or full configuration; use
  `nyanpasu-config/src/redact.rs` (`redact_config`, `redact_text`) for previews.
- Derive application paths from the injected `nyanpasu-paths` resolver, not from
  `dirs` or the environment inside a service.
- Test pure services with plain values and actors through their typed clients with
  fake adapters. Do not use global fixtures, real user configuration, or sleeps for
  synchronization; use replies, acknowledgements, or
  `#[tokio::test(start_paused = true)]`.
- Test behavior and failure semantics, and match meaningful error variants instead
  of only `is_err()`. Reproduce a bug with a test before fixing it.

## 12. Migration debt

These areas do not meet this guide yet. Migrate each in a focused change with
behavior verification; do not mix it into feature work.

1. **Fallible `new` constructors.** About 13 `pub fn new(..) -> Result<..>` exist, for
   example `ManagedProfilePath::new` and `EnhanceScriptRunner::new`. Rename them to
   `try_new` and update callers.
2. **Production `use super::*`.** File modules such as
   `nyanpasu-config/src/profile/{definition,dependency,folder,item,patch,profiles,source}.rs`
   and `nyanpasu-tsdb/src/status/read.rs` import their parent with a glob. Replace
   these with explicit imports.
3. **`catch_recoverable`.** The call in `tauri/src/utils/help.rs` needs the call-site
   comment and test required by section 7.3.
4. **Poison recovery.** `nyanpasu-tsdb` recovers poisoned `std::sync` locks with
   `unwrap_or_else(PoisonError::into_inner)` (`budget.rs`, `version.rs`,
   `storage/memory.rs`, `storage/redb.rs`, `storage/redb/disk.rs`). Consider replacing these locks with `parking_lot` and removing
   the recovery.
5. **Ambiguous booleans.** Replace the opposing `automatic`/`explicit` retry
   parameters with one shared enum.
6. **Failure contracts.** Replace production bare `unwrap()` and check-then-unwrap
   with pattern matching, `Result`, or an `expect()` that states the invariant.
7. **Module dependencies.** Qualify non-local free functions and move substantial
   implementations out of non-leaf modules (`tauri/src/client/mod.rs`,
   `use crate::core::*` in `tauri/src/ipc.rs`).
8. **Logging and errors.** Replace remaining `log` macros with `tracing`, and replace
   string-bucket error variants with domain variants.
9. **Documentation.** Document exported cross-crate APIs crate by crate. Only a crate
   that is clean may opt into `missing_docs`.

A migration change is complete when its area meets the rule, the relevant behavior
tests pass, and no compatibility wrapper was added to avoid updating callers.

## 13. Review checklist

- Formatting, Clippy (on every OS), and the relevant behavior checks pass.
- The change is minimal and new code follows this guide rather than nearby legacy code.
- No global mutable service state, and no new Tauri dependency in clients, actors,
  pure services, or neutral crates.
- Ownership, error, and concurrency semantics match the API contract.
- New persisted fields decode old files, and RPC types have regenerated bindings.
- Every `unsafe`, `catch_recoverable`, and lint suppression has its comment and narrow
  scope, and no poisoned lock is recovered.
- Comments and documentation describe the new behavior.
