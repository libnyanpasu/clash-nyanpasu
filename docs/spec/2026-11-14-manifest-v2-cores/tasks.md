# 内核分发接入 resource manifest v2：任务卡

[设计](design.md) 的实施划分。卡片按仓库分组；每张卡是一个可独立评审、合并后主干可构建的 PR。

## 依赖

```text
M1 ─┬─► A2 ─► A3 ─► A4 ─► A5 ─► A6 ─► B1 ─► B2
M3 ─┤         ▲     ▲           ▲            ▲
M2 ─┘         │     │           │            │
A1 ───────────┴─────┘           │            │
M1, M3 ─► R2 ─► R3 ─────────────┘            │
M1 ─► M4 ────────────────────────────────────┘
R1（独立）
```

- M = manifest 仓，R = runtime 仓，A = 本仓应用，B = 打包。
- A1、R1、M2 不依赖其他卡，可以先做。

## 合并与发布

"可合并"指主干能构建、测试通过、现有行为不退化。"可发布"另有门禁：

| 门禁 | 原因 |
| --- | --- |
| A3 到 A6 必须在同一个发布版本里 | A3 之后受管内核在数据目录；A6 之前服务还不能使用它们。A3 合并后、A6 合并前，主干上服务模式只能运行随包内核，不得发布 |
| A6 的发布版本带 R3 之后的服务，并声明服务最低版本 | 应用与服务必须一起升级（设计 §7.5） |
| B2 至少晚于 B1 一个发布版本 | 迁移（设计 §9.3） |
| B2 晚于 A6 的发布 | 缩减后非随包内核只存在于数据目录，服务必须已经能收录 |

## manifest 仓

### M1 产物的 `binary` 字段

- `TemplateArtifact` 与 `ResourceArtifactTemplate` 加可选的 `binary`；模板严格解码，编译产物宽松解码。
- `validate_manifest` 检查路径形状（设计 §5.1）；下载计划返回渲染后的路径。
- 重新生成 schema 与 TS 类型；`check:generated` 无差异。
- 一致性语料补用例，Rust 与 Node 的用例集合保持相等。
- 用真实资产核对三个内核各平台归档内的路径，写入生成器配置。
- 判据：发布的 `resources.json` 里每个归档产物都有 `binary`；裸可执行与 `.gz` 产物没有。

### M2 基础变体约定的测试

- 生成器测试断言设计 §5.2 的约定。
- 判据：把默认配置里任一 channel 的基础变体改成带附加 tag，测试失败。

### M3 只验签的依赖面

- `manifest-signature` 的验签路径不拉入签名实现。
- 判据：只启用验签时，`cargo tree` 里没有密钥解密相关的依赖。

### M4 可在仓外使用的下载器

- 依赖 M1。发布包或带 wasm 的单文件构建；行为与工作区内的下载器相同（先验签、显式策略、校验后落盘）。
- 按 `binary` 产出解包后的可执行文件，或返回渲染后的归档内路径。
- 判据：在一个不含 manifest 仓的目录里，用它下载并校验一个 stable 产物与一个 alpha 产物；其中一个是 Windows 的 zip 归档，得到其中的可执行文件。

## runtime 仓

### R1 删除未使用的镜像类型

- 删除 `nyanpasu-core-metadata` 的 `dist` 模块与 `ClashCoreResourceVariant`；更新 README。
- 判据：工作区与父仓都能编译；父仓不需要任何改动。

### R2 内核库

- 库的目录布局、创建与从文件系统根开始的逐级验证（设计 §7.2），Unix 与 Windows 各一个实现；服务安装步骤加固服务专有的祖先目录；系统祖先与服务专有目录分开判断；含默认系统布局通过的正向用例与经父目录替换服务数据目录的对抗测试。
- `InstallDirectory` 的逐级打开与在句柄上的检查（设计 §7.4），含祖先目录与替换竞争的对抗测试。
- 收录的三种证据的核对逻辑，作为库内部的函数，带测试；引入 manifest crate 的依赖与内置公钥。
- 本卡不接入 IPC，不改变服务的查找行为，不声明能力。
- 判据：设计 §15 "内核库的验证"与"收录"两行里不涉及 IPC 的用例。

### R3 按哈希启动与收录操作

- IPC 的 `CoreBinaryRef` 与 `CoreIngestReq`；启动、协调、配置检查三种请求都带 `CoreBinaryRef` 并走同一段检查；收录与它们经同一个命令队列。
- 卸载服务时删除内核库。
- 删除 `find_binary_path`；不带 `CoreBinaryRef` 的启动请求返回"需要升级应用"。
- `allow-unanchored-cores` 开关，安装服务时写入；执行时也检查。
- 收录的审计日志。
- 服务状态声明 `core-store`。
- 判据：设计 §15 "按哈希启动""收录""版本错位"三行里服务一侧的用例。这是破坏性的 IPC 变更，随该仓的主版本发布。

## 应用

### A1 `core-bin` 布局、记录与查找

- `InstalledCoreRecord`、`CoreProvenance` 放 `nyanpasu-contracts`。
- `PathResolver` 加受管内核的路径推导；读记录的端口 `InstalledCoreReader` 放 contracts，由 `nyanpasu-os` 实现并注入；"受管优先"的组合在 core。删除 `data_or_sidecar_path`。paths 不依赖 contracts。
- 版本读取器接收解析好的路径；桌面与 server 两处组合根更新。
- 数据目录根下旧文件的 WARN；启动时清理暂存与孤儿目录。
- 判据：设计 §15 的"查找顺序"一行；`core-bin` 为空时现有行为不变。`lint:backend-boundaries` 通过。

### A2 `CoreCatalog` 与清单获取

- 引入 manifest crate 的 git 依赖，只进 `nyanpasu-updater`；`lint:backend-boundaries` 通过。
- 槽位映射、`CoreCatalog` 的三条约定、`CoreVariantChoice` 的类型与解析规则。
- 清单的获取、验签、合并缓存与防重放。
- 本卡不改变 updater 的行为：新代码还没有调用方，v1 路径照旧。
- 判据：设计 §15 的"槽位映射""`CoreCatalog`""变体解析""清单缓存"四行。

### A3 安装事务

- `BinaryInstaller` 的请求改为暂存路径、槽位与记录；`nyanpasu-os` 在一次调用里实现设计 §6.3 的第 5、6、8 步，含复用哈希目录时补齐产物；产物按 digest 命名且不覆盖。
- 删除提权复制与相关错误变体；两个组合根不再传安装目录。
- updater 仍按 v1 清单下载，但安装到 `core-bin`，记录的来源暂为 `Migrated`（v1 没有可记录的 manifest 身份）。
- 判据：设计 §15 的"安装事务"一行；安装目录只读时更新成功。
- 发布门禁：本卡之后服务模式只能运行随包内核，见上表。

### A4 updater 改用 manifest 计划，并迁移其消费者

- 版本、checksum、下载都按 `manifest-core` 的计划执行；按槽位给出校验策略；镜像筛选；四类大小限制。
- 按 `binary` 解包；§6.4 的版本规则表，用六个槽位的真实二进制核对。
- 保留有锚安装的原始产物；记录的来源为 `Manifest`。
- 同一张卡里：facade 与 RPC 的 `fetch_latest_core_versions` 换成 `inspect_core_catalog`；新增 `list_core_slots`；前端的版本合并改用它们；重新生成绑定。然后删除 v1 结构与上游专用解析。
- 判据：设计 §15 的"更新流程""大小限制""版本核对""v1 等价""RPC"五行；仓内不再有读 `manifest/version.json` 的运行时代码（构建脚本除外，见 B2）。

### A5 变体选择与内核管理页

- `set_core_variant` 变更命令，提交前用清单核对；应用配置的新键。
- 内核管理页按槽位显示来源、变体、checksum 裁决；缺失槽位显示下载；WebUI 上显示不支持下载。
- 所选内核缺失时的状态与两个操作（设计 §9.3）。
- 判据：选了可选变体后，更新取到该变体的产物；另一个 channel 的选择被拒绝。

### A6 服务模式接入内核库

- 更新 runtime 子模块到 R3 之后的版本；更新服务最低版本与打包的服务。
- 启动、协调与配置检查请求带 `CoreBinaryRef`；`CoreNotIngested` 时按设计 §7.4 的表选择证据并收录；安装事务的第 4 步。
- 服务不声明 `core-store` 时不发内核请求，提示升级服务。
- 无锚与迁移来源槽位的标记。
- 判据：设计 §15 "版本错位"一行里应用一侧的用例；按用户安装下服务模式能运行受管的 stable 内核；开关关闭时 alpha 槽位得到明确的拒绝原因。

## 打包

### B1 迁移版

- 启动时把安装目录里的非默认内核装成来源为 `Migrated` 的受管内核（设计 §9.3 第 1 步的专用步骤，不做版本比较）。
- 判据：设计 §15 的"迁移"一行。

### B2 只带默认内核

- `externalBin` 缩减；portable 脚本同步。
- 准备脚本改用 M4 的下载器并验签：打包只取 Mihomo stable，开发模式取其余五个。此后构建不再读 v1 清单。
- 判据：安装包里只有一个内核；全新安装后非默认槽位显示"下载"并能完成下载；设计 §15 的"准备脚本"一行。

## 不在本批

- sing-box 的世代筛选与 history 按版本段保留（设计 §10）。
- geodata 与 wintun 改走 manifest。
- 把内核下载开放给 HTTP。
- 把内核加载的 DLL 收进服务的信任边界（设计 §13 的 U6）。
- 停止生成 v1 清单；等仍在读它的已发布版本不再维护。
