# 启动失败分级：可降级与不可降级

**日期：** 2026-10-29

**状态：** 已实施，见[实施计划](../../plan/2026-10-29-startup-failure-handling.md)。本文档给出分级和处理方式；实施中的偏离与已知限制记录在计划的实施记录中。

**基线：** app `main@ad0ac5786`；runtime `v2.0.2`（`e73b9f5`）；tauri `2.12.5`。

**来源：** codex（gpt-6.1-sol，xhigh）只读审计 setup 路径，我逐项复核关键结论并补充。第 9 节列出哪些结论已对照源码核实。

**权威顺序：** 当前 AGENTS.md 与 development guides > 本 spec。

## 1. 背景与目标

#6033 中，一条残留的 `core-*.pid` 让 `CoreManager` 构造失败，错误经 setup 闭包传给 Tauri，Tauri 以 `Failed to setup app` panic。记录留在磁盘上，所以每次启动都崩溃，直到用户手动删掉它。runtime v2.0.2 修好了这一个触发点，但同类问题仍然存在：任何会持久存在的磁盘状态，只要让 setup 返回错误，都会造成同样的崩溃循环。

目标：**启动时不再出现 setup panic。**

- **可降级错误：** 记一条 `warn` 日志，跳过或重建出问题的部分，应用照常启动。
- **不可降级错误：** 不 panic，改为弹出带明确恢复步骤的对话框，然后干净退出。

## 3. 分级原则

**可降级**：同时满足以下三条。

1. 出问题的状态是**派生、缓存或历史数据**，或者对应的功能是**可选的**。丢掉它不损失用户编写或配置的内容。
2. 跳过或重建不会带来**安全风险**。特别是，不能因此对无法证明归属的进程发信号。
3. 应用在缺少它的情况下仍能完成主要功能，或者功能缺失会在对应界面上表现为错误状态，而不是静默错误。

降级的标准动作：

- **保留现场：** 把出问题的文件或目录改名为 `<原名>.corrupt-<UTC 时间戳>`，不直接删除。降级后再升级回去，或者事后排查时，证据都还在。
- **记录日志：** `tracing::warn!`，内容包含路径、错误链，以及采取的动作（已隔离、已重建、已禁用某功能）。
- **升级为不可降级：** 改名或重建本身失败时，按不可降级处理。

### 3.1 IO 错误：先重试，权限错误不回退

启动期的文件操作（打开、读取、改名、删除）遇到 IO 错误时，先按错误种类决定是否重试，再决定降级还是报错：

| 错误种类                                                                                                                                  | 处理                                                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 暂时性：`Interrupted`、`WouldBlock`、`TimedOut`、`ResourceBusy`；Windows 的 `ERROR_SHARING_VIOLATION`（32）、`ERROR_LOCK_VIOLATION`（33） | 有限次指数退避重试（最多重试 3 次，间隔 50、100、200 ms，单个文件最多多等约 350 ms），复用 `nyanpasu-utils` 已依赖的 `backon`。重试耗尽后按"占用"报不可降级错误，提示退出占用该文件的进程（杀毒软件、另一个实例） |
| 权限：`PermissionDenied`                                                                                                                  | **不重试、不降级、不隔离**，直接报不可降级错误，给出路径并提示检查权限。即使该文件属于可降级项（D3–D6）也一样                                                                                                     |
| 数据问题：解析失败、格式不符、节点类型不对（文件变成目录等）                                                                              | 可降级项按第 3 节标准动作隔离重建；不可降级项报错                                                                                                                                                                 |
| 其他                                                                                                                                      | 不重试，按所在项的分级处理                                                                                                                                                                                        |

权限错误暂不回退的原因：权限问题通常说明环境被改动过（以其他用户身份运行过、目录被加了 ACL），自动隔离重建会掩盖问题，而且改名本身多半也会失败。

**已知限制：** Windows 上对处于"删除挂起"状态的文件操作也返回 `ERROR_ACCESS_DENIED`，std 把它映射为 `PermissionDenied`，按上表会直接报错而不重试。实践中出现频率低，先接受；若现场反馈多，再单独识别。

**不属于本规则的权限错误：** D1 中查询**其他进程**身份时遇到的拒绝访问（例如 PID 被另一个用户的进程复用），不是我们自己文件的权限问题，而是"无法证明这个进程属于我们"。runtime 把它当作无法证明归属（`pid_file.rs:869` 读不到 `/proc/<pid>/exe` 时视为未知，`pid_file.rs:650` 把 `PermissionDenied` 列为暂时性），从不发信号。已确认（2026-10-29）保持"不发信号"，按 D1 的"存活进程无法证明归属"处理。更正：v2.0.2 中这种情况并不是跳过，而是让 `CoreManager` 构造失败，D1 把它改为进入阻塞 quarantine。

### 3.2 错误模型：setup 改用 snafu 领域错误

setup 及其调用链目前返回 `anyhow::Error`（`setup.rs:56`，以及 `client/mod.rs`、`client/jobs.rs`、`client/runtime.rs`、`core/actor_v2/local_host.rs` 等 13 个文件），只剩一串文本，无法按种类给出恢复步骤。改为 snafu 领域错误，遵循 [Rust 代码指南](../../development/rust.md) 的错误约定：

- **每个模块自有错误类型。** setup 有自己的 `setup::Error`，变体按失败的步骤命名（如 `OpenStorage`、`StartJobs`、`BuildCoreManager`、`BuildClient`、`RunMigrations`），携带路径等上下文，`source` 是下游模块自己的错误类型。不建全 crate 的大 enum，不用字符串上下文。
- **调用链上的 `anyhow` 一并替换。** 只替换 setup 实际经过的构造函数和启动函数；与启动无关的 `anyhow` 不在本次范围内。
- **分类在边界上做一次。** setup 闭包拿到 `setup::Error` 后，由一个函数把它映射成"降级已在下游完成的不会到这里，到这里的都是不可降级"的 `StartupFailure { kind, path, detail }`，`kind` 对应第 5 节的 N1–N7，再据此选对话框文案和按钮。IO 错误的种类判断（第 3.1 节）在这里和下游重试处共用一个函数。
- **测试断言错误变体**，不断言文本。

**不可降级**：涉及用户数据或应用正常运行的前提，自动处理可能造成数据丢失或行为错误。

- 用户配置和订阅：`application.yaml`、clash 配置、`profiles.yaml`。
- 迁移状态，以及由更新版本写入的文件（降级场景）。
- 应用目录本身不可用，或界面无法显示。
- 程序内部不变量被破坏（组装缺陷），用户无法自行修复。

## 6. 对话框选型

### 6.1 rfd 只适合一次性对话框

rfd 的三个桌面后端，任何按钮按下后对话框都会关闭并返回结果，没有公开接口能让某个按钮执行动作而不关窗（rfd 0.17.2 源码核实）：

| 平台    | 实现                                                                                     |
| ------- | ---------------------------------------------------------------------------------------- |
| Windows | `TaskDialogIndirect`，`pfCallback: None`（`backend/win_cid/message_dialog.rs:153`）      |
| macOS   | `NSAlert::runModal`（`backend/macos/message_dialog.rs:101`），NSAlert 的按钮总会结束模态 |
| GTK     | `gtk_dialog_run` 后 `gtk_widget_destroy`（`backend/gtk3/message_dialog.rs:122,175`）     |

所以现有的 `migration_failed_dialog`（`utils/dialog.rs:38-58`）是在循环里**重新弹出**对话框：点"打开日志"后窗口消失、目录打开、对话框再出现一次。多按钮、点了不该关窗的场景不再用 rfd 做。

### 6.2 多操作对话框的候选

| 方案                                                | 结论                                                                                                                                                                                                                                                              |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 改 rfd                                              | 需要给三个后端各加回调接口（macOS 的 NSAlert 本身做不到，要换成自建面板），等于自己写一套原生对话框，不如直接写                                                                                                                                                   |
| 自写 Windows `TaskDialogIndirect` + 回调            | 可行：`TDN_BUTTON_CLICKED` 回调返回 `S_FALSE` 即可阻止关闭（[Microsoft Learn, TDN_BUTTON_CLICKED](https://learn.microsoft.com/en-us/windows/win32/controls/tdn-button-clicked)）。还支持可展开的详情区和超链接。但只覆盖 Windows，macOS、Linux 仍要另做           |
| xdialog 4.1.3                                       | 不合适。文档中消息框的按钮同样返回结果并关闭（`show_message(...).wait()`），没有不关窗的按钮；而且它的自绘后端要占用主线程或接入应用自己的 winit 事件循环，和 tao 冲突（[docs.rs/xdialog 4.1.3](https://docs.rs/crate/xdialog/latest)，单一来源，仅文档未看源码） |
| Slint 报告器（`nyanpasu-crash-reporter`，独立进程） | 已有、三平台一致，已支持 `--language` 与可滚动可复制的详情；按钮行为完全自控。代价是加一个"启动失败"模式和对应的参数协议，并且要另起进程                                                                                                                          |

### 6.3 决定

已确认（2026-10-29）：

- **多操作的对话框用 Slint 报告器。** 新增 `startup-failed` 子命令：主进程把 `StartupFailure`（类别、路径、错误链、版本、日志与备份路径）序列化后传给子进程，同步等它退出，再退出主进程。按钮"打开所在目录 / 打开备份目录 / 打开日志"执行后**不关窗**，只有"退出"关闭。详情区可复制。覆盖 N2、N3、N4、N7，迁移失败对话框也迁到这里。
- **一次性对话框继续用 rfd。** 只有一个"确定/退出"按钮、正文把路径写出来即可的场景：N1（应用目录不可用，报告器所需的环境也可能不全）、N5（WebView2 不完整，提示重装）。
- **报告器拉不起来时退回 rfd 一次性对话框**，正文带路径和日志位置。现有 panic hook 已是这个模式（`lib.rs:97-135`）。
- 不为 Windows 单独写 TaskDialog：三平台用同一套报告器更简单，原生 TaskDialog 带来的只是外观差别。

### 6.4 后续调查：原生 UI

本次不做，留作后续调查。目标是不另起进程、外观与系统一致的多操作对话框：

- **Windows：** `TaskDialogIndirect` 加回调（`TDN_BUTTON_CLICKED` 返回 `S_FALSE`），附带可展开详情和超链接。
- **macOS：** NSAlert 做不到，需要确认 NSPanel 自建面板的工作量，以及能否在 tao 事件循环已运行时以模态方式弹出。
- **Linux：** 确认 GTK `GtkDialog` 的 `response` 信号能否不关窗，以及无 GTK 环境（纯 Wayland 或 X11 最小环境）怎么办。
- **xdialog：** 本次只看了文档，需要看源码确认 Win32 后端能否在 tao 进程内使用，以及有没有不关窗的按钮。

调查结论出来前，Slint 报告器是唯一的多操作对话框实现。

## 8. 待决策

1. **不可降级时如何退出。** 已确认（2026-10-29）：不用 `std::process::exit` 直接结束，先取消 `shutdown` token、等 `TaskTracker` 收尾，让已启动的 owner 正常 Drop（落盘、释放锁），再以非零退出码结束。

   **退出手段（已核实 tauri 2.12.5 源码）：**

   - Rust 没有"从任意栈帧退出并执行 Drop"的标准手段。`std::process::exit` 与不稳定的 `ExitCode::exit_process` 都不执行任何线程栈上的析构；只有从 `main` 返回才会。用 `resume_unwind` 带标记值跳回 `main` 不可取：它跨过 tao 的事件循环，Linux 后端没有 `catch_unwind` 包装，遇到 `extern "C"` 回调会直接 abort（子代理调查，Linux 部分未核实）。
   - setup 闭包在事件循环的 `RuntimeRunEvent::Ready` 回调里执行（`app.rs:1442-1446`），此时 `AppHandle::exit(code)` 走正常的 `request_exit`（`app.rs:581-587`），会触发 `ExitRequested`。
   - 现有退出路径已经完成"先收尾再退出"：`ExitRequested` → `utils::exit::on_exit_requested` 阻止退出并 `start_shutdown`，等 `NyanpasuClient::wait_shutdown` 完成后再次 `exit`（`utils/exit.rs:129-169`）。`ExitBoundary` 在 builder 上注册（`lib.rs:323`），早于 setup。

   **做法：** setup 遇到不可降级错误时，不返回 `Err`：先弹对话框（阻塞等报告器进程退出），再调用 `app.handle().exit(code)`，然后返回 `Ok(())`。之后走与正常退出相同的收尾路径。

   **实施时要核实的两点：**

   - **部分构造的 owner。** 失败发生在 `NyanpasuClient` 注册之前时，`request_shutdown` 返回 `None`（`utils/exit.rs:231-234`），不会等任何 owner。setup 中已创建的局部 owner 会在提前返回时按 RAII 析构；但已经 spawn 到 `TaskTracker` 的任务需要 setup 自己取消 token 并等待，不能依赖 client。
   - **是否改用 `App::run_return`。** `lib.rs:407` 用的是 `app.run`，事件循环结束后 tao 调用 `process::exit`，`App` 及其托管状态不会 Drop。owner 已经在上面的收尾路径中停止，所以不改也满足"允许 Drop"。改成 `run_return` 加 `main` 返回 `ExitCode`，可以让托管状态也析构，但会改变所有退出路径，单独评估。

2. **profiles 的 `current` 指向不存在的 ID。** 已确认（2026-10-29）：清空选择并 warn，归为 D10。
3. **固定版 WebView2 不完整时，能否退回系统 WebView2。** 已确认（2026-10-29）：便携版不退回（N5）；安装版退回，见第 5 节表后说明。
4. **日志不可用。** 已确认（2026-10-29）：目前不可降级（N8），在退出流程的对话框里显示错误。等日志可以不保留后再考虑降级。
5. **本次是否处理 N6。** Linux 无显示环境只能输出到 stderr，可以不处理。
