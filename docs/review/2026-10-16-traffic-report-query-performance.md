# 流量报表查询性能与优化目标

**日期：** 2026-10-16

**基线：** 分支 `feat/traffic-heat-layout`。排行已忽略自身维度的筛选。测量时，总览请求还带有每列 3 个节点的路径预览；该预览已因本文的结论从分支移除，留作 TODO（见 #6）。

**依据：** 只读代码审阅，加上用合成数据库对 `nyanpasu-traffic` 的 release 计时。codex 独立分析了同一批代码，结论已逐条核对。测量程序没有入仓。

**结论摘要：**

- 合成库上的主要成本是 `report()` 的内存聚合，约为读库的 4–6 倍。只有「组合少、历史长」时读库才占大头。
- 聚合慢在顺着 `Arc<Dimensions>` 和 `String` 的指针读内存，不在哈希上。把维度值换成整数编号后，5 个排行的分组从 106 ms 降到 1.2 ms。
- 概览带上路径预览后，单次请求的成本是只算排行时的 2.2–2.7 倍。原因是拓扑先为每一行建出全部节点和边，每列 3 个的限制只作用于输出。预览因此已移除，等拓扑优化后再加回。
- `report()` 在 traffic actor 的消息处理里同步执行。报表、连接帧处理和 flush 排成一队，用户等到的是队列里所有请求的耗时之和。
- 真实库被运行中的应用锁定，没有测量。下文的规模推断置信度低。

## 2. 时间分布

一次报表请求依次经过三步：读库（`redb.rs:316` `usage()` → `sum_by_tuple`）、拼行（`actor.rs:307` `with_rows`）、聚合（`query.rs` `report()` 和 `topology.rs`）。

| 单价 | 取值                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 读库 | 每个 `(bucket, tuple)` 条目约 0.06–0.2 µs。redb 迭代约 45 ns，SipHash 累加约占另一半；60 万个组合时，映射回 `Arc<Dimensions>` 再多约 40% |
| 聚合 | 5 个排行约 1.1–1.3 µs/行，加 4 层拓扑后约 2.7 µs/行                                                                                      |
| 分界 | B/U（条目数 ÷ 组合数）低于约 15–30 时，聚合占主导。合成库的 B/U 为 1.8–4.2                                                               |

| 库 / 范围 | 行数 | 读库   | 仅排行  | 概览（排行 + 预览拓扑） |
| --------- | ---- | ------ | ------- | ----------------------- |
| S / 24h   | 18k  | 3.9 ms | 18.7 ms | 41 ms                   |
| S / 7d    | 87k  | 24 ms  | 109 ms  | 241 ms                  |
| M / 24h   | 58k  | 17 ms  | 75 ms   | 152 ms                  |
| M / 7d    | 234k | 134 ms | 311 ms  | 717 ms                  |
| L / 30d   | 597k | 495 ms | 732 ms  | 1698 ms                 |

放大因素：

- `group_key()`（`model.rs:185`）每次调用都分配一个 `String`；Rule 用 `format!`，Chain 用 `join`。每个排行和拓扑都各自重扫全部行。
- 按出口分组（只有 18 个值）处理 87k 行仍要 8 ms，约 90 ns/行。时间花在指针跳转上；换成 FxHash 只快 0–10%。
- 前端轮询：24 小时以内的范围每 2 s 一次（`search.ts` `pollInterval`），但库里的数据每 30 s 才 flush 一次。连接页在筛选状态下每 2 s 对全部历史做一次 closed 报表，只为一个计数（`connections/_modules/status-tabs.tsx:119`）。每张订阅卡片每 10 s 各查一次（`profile-card-subscription.tsx:210`）。
- 序列化通常可以忽略；路径页「全部」档一次返回 4–6 MB，序列化要 4–8 ms。

## 4. 实施顺序

价值排序和实施顺序不同：先做低风险、能立刻止血的项目，再做收益最大的改造。

1. #2、#7。验证：actor 测试用计数 fake store，断言两次 flush 之间 `usage()` 只调用一次。
2. #5。验证：概览请求进行中，连接帧处理和 summary 的延迟不变。
3. #3，以及 #4 中不与 #1 冲突的部分。验证：`query.rs`、`topology.rs` 的现有测试守住语义，再用基准回归。#3 落地后可以加回 #6 的预览，用基准对比概览和仅排行的耗时。
4. #1，顺带做 #8。验证：同一批测试加上第 2 节的基准，目标见第 3 节。
5. #9 等补测真实库、确认 B/U 很高时再考虑。

## 5. 未验证

- 真实库的条目数、组合数和 B/U。「聚合占大头」依赖 B/U < 约 15–30 的假设；如果真实库组合少、历史长，#2 和 #9 的排位会上升。
- #1 用于筛选与拓扑、以及 #3 的倍数没有做原型。
- 用户的保留期设置没有找到，按默认 7 天推算。
- 窗口隐藏或最小化时轮询是否停止，没有验证。
