# 时序存储调研与存储层设计

调研日期：2026-10-17。三个 subagent 分别调研了三组系统：Prometheus、VictoriaMetrics 和 Gorilla 论文；InfluxDB、TimescaleDB 和 QuestDB；ClickHouse、IoTDB、TDengine，以及 DuckDB、Parquet、Arrow、LSM 等嵌入式和参考格式。主线程核对了版本日期、redb 4.4.0 源码和本仓库的写入语义。依据是官方文档、设计文档、论文和固定 tag 的源码，没有运行这些数据库做性能测试。文中标注的置信度：高 = 源码或两个以上独立来源；中 = 单一官方来源；低 = 推断或厂商宣传数字。

第 8 节是在调研基础上提出的存储层设计（`nyanpasu-tsdb`）。设计参考了 codex 对本仓库代码的独立分析：codex 会话只读、未改文件，它引用的代码位置已由主线程逐条核对。按用户要求，设计先不计实现复杂度，追求性能最优、功能够用、留有扩展余地。

本报告是撰写当时的快照，后续设计以 [nyanpasu-tsdb 设计抽象](../design/nyanpasu-tsdb.md) 为准。文中的代码位置以撰写时的本地分支为准：它叠在 #5807 之上，含尚未合入的查询优化（例如 `UsageTable`），所以与 main 相比部分行号有偏移。

**结论摘要：**

- 被调研的系统都不为「一个时间点 × 一个序列」各建一条索引项。数据先攒成有序、按列存放的批次，索引只指向批次：ClickHouse 每 8192 行一个 granule，DuckDB 每 122,880 行一个 row group，TimescaleDB 每 1,000 行一个压缩 batch，TsFile 每页最多 10,000 个点，TSM 每块最多 1,000 个点。我们原型「每个小时一条打包记录」是同一个做法，读库快 17 倍的原因也相同：每条记录约 45 ns 的 B 树遍历开销没有了。
- 要「所有组合 × 一段时间」这种查询的系统，都按时间优先存放：IOx/InfluxDB 3、TimescaleDB 的 columnstore、QuestDB、ClickHouse 按时间分区都是如此。按序列优先存放（Prometheus、VictoriaMetrics、TSM）适合「少数序列 × 长时间」，在高基数下索引和内存先出问题。我们每次查询都要扫过几乎全部组合，应保持按时间（桶）优先。
- 对计数器来说最接近的模型是 ClickHouse 的 **SummingMergeTree**：写入时追加增量，合并时把主键相同的行相加，查询时仍做 `sum() GROUP BY`，因为合并不保证做完。迟到数据最接近 IoTDB 的**顺序与乱序分离**：比最后一次落盘时间更早的数据进入单独的乱序文件，读取时合并，之后再由压实折叠回顺序文件。
- 我们的迟到写入**只做加法**：连接关闭时，把它经过的各个桶的用量按最终维度一次加进库（`accounting.rs:344-370`），小时和分钟用量表只收已关闭连接的用量。所以不需要部分调研建议的「负增量 / 墓碑」，增量层可以只用无符号加法。
- 可选设计按复杂度从低到高：每个桶一条打包记录整条重写 → 每个桶按 id 范围分段 → 已封存的整条记录加一层增量记录、维护时折叠 → 加日桶层级 → 内存里按窗口维护的累计和。前两种已有原型数据。要不要上增量层，取决于真实库里长连接关闭时会碰到多少个旧小时，这一点还没测。
- 设计结论（第 8 节）：参照 TiDB 与 TiKV 的分工，把存储拆成四层。最底层是可替换的事务型有序 KV 引擎，先用 redb；上面一个独立 crate `nyanpasu-tsdb` 负责字典、时序表和事件表；最上层是流量业务。时序表按桶分段、列式存放，迟到写入走增量块；事件表（已关闭连接明细）按时间切块、只存组合 id，封存后压缩。所有写入仍在调用方的同一个事务里提交。
- 压缩值得做，但收益最大的不在用量表，而在已关闭连接明细。真实库（第 1.1 节）的数据：
  - 8 天积累 12.2 万个已关闭连接，明细占了库中实际数据的 98%，用量表和组合表合计不到 1 MB。
  - 明细平均每条 527 B 的 JSON 加 44 B 的键；改成只存组合 id、列式加 zstd 后实测每条 25 B，约为原来的 1/23。
  - 按每天 10–20 万连接推算，现在的格式每月约 1.7–3.4 GB，新格式约 75–150 MB。
- 真实库与合成库差别很大：只有 1,297 个组合，每个小时桶的中位数只有 58 条。读库性能在这份真实库上不是问题。另外 redb 文件从不收缩（代码里没有调用 `compact()`）：156 MB 的文件整理后只剩 89 MB。
- 时序层要做得通用。内核日志、任务日志同样是只追加、按时间查询的事件负载，事件表的列类型、块统计和保留策略都按通用需求设计（第 8.5、8.8 节）。

## 2. 按序列优先的引擎

### 2.1 Gorilla（Facebook，VLDB 2015）

- **架构**：内存里的写透缓存，只存最近 26 小时。每个序列由若干已封存的 2 小时块和一个只追加的开放块组成；块封存后不再修改（[论文](https://www.vldb.org/pvldb/vol8/p1816-teller.pdf) §2.2、§4.2）。
- **编码**：
  - 时间戳用差值的差值（delta-of-delta）：D = 0 时只写 1 bit；`10`、`110`、`1110` 加 7、9、12 bit；超出范围时 `1111` 加 32 bit。约 96% 的时间戳只占 1 bit。
  - 浮点值与前一个值做 XOR 编码。
  - 每个点 1.37 字节，原始是 16 字节，约 12 倍（§4.1）。置信度：在 ODS 数据上为高，不能直接套到别的负载。
- **迟到数据**：格式只追加，论文没有描述改写旧块。它总结的经验是「Prioritize recent data over historical data」（§6.3）。
- **对我们**：XOR 编码针对缓慢变化的浮点值。我们的值是整数增量，用不上；但「最近的块可变、旧块封存」值得借鉴。

### 2.2 Prometheus TSDB（检查 tag v3.15.0，2026-09-25 发布）

- **写入路径**：
  - 内存里的 Head 块由 WAL 保护，WAL 按 128 MB 分段。每个序列往一个活跃 chunk 里追加，目标是 120 个样本一个 chunk（`DefaultSamplesPerChunk`）。
  - 写满的 chunk 映射到 `chunks_head/`。
  - Head 跨度达到 3 小时，就把最早的 2 小时压成持久块。
  - 持久块是一个不可变目录：`meta.json`、`chunks/`、`index`、`tombstones`。
  - 分级压实为 2h → 6h → 18h …，单块上限取保留期的 10% 和 31 天中较小的那个。
  - 来源：[存储文档](https://prometheus.io/docs/prometheus/latest/storage/)、[Ganesh Vernekar 的 TSDB 系列](https://ganeshvernekar.com/blog/prometheus-tsdb-the-head-block/)、源码 `tsdb/db.go`、`tsdb/compact.go`。
- **chunk 格式**：样本数 + 首个时间戳 + 首个值，后接 delta-of-delta 时间戳和 XOR 值。Prometheus 用毫秒，分档改为 14、17、20、64 bit（`tsdb/chunkenc/xor.go`）。官方说每个样本平均 1–2 字节（置信度中）。
- **索引**（[`tsdb/docs/format/index.md`](https://github.com/prometheus/prometheus/blob/v3.15.0/tsdb/docs/format/index.md)）：
  - **符号表**：排序去重的字符串。
  - **序列段**：按标签集排序、16 字节对齐，序列 id = 偏移 / 16；每个序列列出它的 chunk 元数据（mint、maxt、chunk 引用，差值编码）。
  - **倒排表**：每个（标签名，标签值）对应一个有序的 4 字节序列 id 列表。
  - **查询**：先按时间选块，再按标签求倒排表交集、减去否定匹配，然后只加载与时间范围重叠的 chunk。时间裁剪做两次：块级 min/max 和 chunk 级 mint/maxt。
- **迟到数据**：默认拒收（`ErrOutOfOrderSample`）。v2.39 起可以配置 `out_of_order_time_window`：
  - 乱序样本进入每个序列一个小缓冲（v3.15 里 `DefaultOutOfOrderCapMax = 32`）和单独的日志（WBL）。
  - 压实会产生时间重叠的块，读取时边读边合并，之后再做垂直压实。
  - Grafana 报告乱序比例高时 CPU 最多多 50%（单一来源，[Mimir 博客](https://grafana.com/blog/2022/09/07/new-in-grafana-mimir-introducing-out-of-order-sample-ingestion)）。
- **删除和保留**：删除写墓碑 `(series ref, mint, maxt)`，读取时过滤，压实时物理删除。保留只删整块，不逐个删样本。
- **预聚合**：没有原生降采样，靠 recording rules。
- **失败模式**：每个活跃序列都占 Head 内存；序列频繁更替会让每个块的索引膨胀。

### 2.3 VictoriaMetrics（检查 tag v1.154.0，2026-10-12 发布）

- **写入路径**：没有 WAL。
  - 行先进入分片的 `rawRows`，每 2 s 转成内存 part（`lib/storage/raw_row.go`），每 5 s 落盘（`partition.go`）。
  - part 按月分区存放，落盘并 fsync 后再原子登记到 `parts.json`，所以不会读到写了一半的 part。
  - 后台合并时选择写放大最小的一组 part，一次最多合并 15 个。合并时同时做去重、降采样，清理已删除的序列。
  - 代价是崩溃会丢最后几秒的数据。
- **格式**：part 内的块按 TSID 排序，每块是一个序列、最多 8192 个样本，时间戳和值分文件存放（按列）。
  - 浮点值先转成共享指数的十进制 int64 尾数，再选 Const、DeltaConst、NearestDelta 或 NearestDelta2 编码，再试 zstd，至少省 10% 才保留（`lib/encoding/encoding.go`、`lib/decimal/decimal.go`）。
  - 常被引用的「每个样本约 0.4 字节」出自作者的 Medium 文章，调研时该文返回 403，**未核实**（置信度低）。
- **索引（indexdb）**：
  - 是一个独立的有序字节串 LSM（mergeset），带前缀压缩，由命名空间前缀区分映射：名称 → TSID、标签 → MetricID、日期 → MetricID、（日期, 标签）→ MetricID 等（`index_db.go`）。
  - 时间范围短于分区时走按日索引。
  - v1.133.0（2026-01-05）起，每个分区各有一份 indexdb，随分区一起删除。
- **迟到数据**：保留期内无条件接受，写进新 part，由合并排进去。不支持更新：时间戳相同的点都会存下，由去重处理。回填时要关闭或重置结果缓存。
- **保留**：每月第一天删除整个过期分区，磁盘最多占用保留期加一个月。
- **预聚合**：去重和降采样（企业版）都只保留区间内最后一个值，**不做求和**。
- **失败模式**：序列频繁更替时 indexdb 可能达到数据量的 2 倍；活跃序列放不进缓存时写入变慢；合并需要预留磁盘空间。

### 2.4 InfluxDB 1.x/2.x：TSM（检查 tag v2.7.12）

- **写入路径**：
  - 写入先进 WAL（Snappy 压缩、fsync，10 MB 一段），同时进内存 Cache。
  - Cache 超过 25 MB 就快照成一级 TSM 文件；超过 1 GB 直接拒绝写入，这是设计上的背压（`tsdb/config.go`）。
  - 文件逐级压实到「full」，并重写成每个序列连续存放。
- **格式**：`Header | Blocks | Index | Footer`。索引按序列键排序，每个块一条 `minTime, maxTime, offset, size`。每块最多 1000 个点，只含一个序列的一个字段（`DefaultMaxPointsPerBlock`）。
  - 时间戳用差值加 Simple8b/RLE；浮点值用 Gorilla XOR；整数用 ZigZag 加 Simple8b/RLE。
  - 厂商称约每个值 3 字节（置信度中）。
- **索引（TSI）**：SeriesFile 给每个序列分配自增 id；每个分片的索引分区由日志文件加不可变的 mmap 索引文件组成，倒排表用位图做合并、交集和差集。
- **迟到数据**：任何写入都是 upsert，同一时间戳以后写的为准。写入已变冷的分片会产生新的小文件，并重新触发压实。删除写墓碑文件。保留按整个分片删除。
- **预聚合**：v1 的 Continuous Query 只处理最近一个区间，迟到数据要手工回填，没有失效跟踪。
- **对我们**：按序列优先的布局在「全部组合 × 短时间」下最吃亏，每个组合都有自己的索引项和块。TSM 的高基数问题正是因此出现的。

## 3. 按时间优先、按列存放的引擎

### 3.1 InfluxDB 3 / IOx（检查 commit `06200ef9`，2026-09-18）

- **架构**：内存缓冲用 Arrow，带一段短 WAL，按时间块写成 Parquet 文件。Core 版每 1 s 把缓冲写进 WAL，攒满 600 个 WAL 文件（约 10 分钟）做一次快照；每个 10 分钟时间块执行一次排序加去重，再写成 gen1 Parquet（`influxdb3_write/src/write_buffer/queryable_buffer.rs`）。目录服务记录每个文件的位置和 min/max 时间。
- **格式**：Parquet 列，标签值做字典编码，再对整数编码做 RLE，最后 zstd。排序时把基数最低的列放在前面，让 RLE 的连续段更长。默认按天分区。
- **索引**：不建序列索引，所以宣传「无限标签基数」。时间裁剪靠分区键、文件 min/max 和 row group 统计。
- **迟到数据**：落入时间范围与已有文件重叠的新文件。查询时只对重叠的文件做排序合并加去重（`DeduplicateExec`），压实器之后消除重叠。
- **失败模式**：
  - 小文件过多。Core 版限制一次查询最多 432 个 Parquet 文件，默认设置下约 3 天的量（`serve.rs`）。
  - 企业版默认引擎已改为 PachaTree（`.pt` 文件，按列族、序列键、时间排序），目标是高基数、频繁回填和低延迟查询，布局实际上又回到了按序列优先（只有文档，置信度中）。

### 3.2 TimescaleDB（检查 tag 2.30.2）

- **架构**：hypertable 是按时间自动切分 chunk 的 PostgreSQL 表，默认每 7 天一个 chunk（`src/dimension.h:115`）。热数据是普通行存；冷 chunk 由后台策略转成 columnstore（2.18 起改名，原名「compression」）。
- **columnstore 格式**：
  - 先按 `segmentby` 分组，组内按 `orderby` 排序，每 1000 行切成一个 batch。
  - 每个 batch 存成一行堆行，其中每列是一个压缩数组（`tsl/src/compression/README.md`）。
  - 各列可用的编码：时间戳和整数用差值的差值、ZigZag、Simple8b-RLE；浮点用 Gorilla；还有字典编码，以及较新版本加入的 FastLanes 风格 SIMD 位打包。
  - 厂商称节省 90–98% 空间（置信度中）。
- **索引**：`segmentby` 列不压缩，单独存在 batch 旁边并建 B 树。每个 batch 带 min/max、布隆过滤器以及首末值等稀疏索引，不解压就能跳过。
- **迟到数据**：从 2.11 起，压缩 chunk 可以 DML。
  - 插入的数据进入该 chunk 的未压缩暂存区。
  - 更新和删除会把受影响的 batch 解压到暂存区，修改后再异步重新压缩。
  - `compact_chunk` 只合并时间重叠的 batch。
- **连续聚合**：
  - 修改 hypertable 时，把受影响的时间范围记入失效日志；刷新时只重算失效的桶（`tsl/src/continuous_aggs/invalidation.c`）。
  - 有一条失效阈值：阈值之上的写入不记失效，因为那一段还没物化。
  - 实时聚合（物化部分加阈值之后的原始数据）从 2.13 起默认关闭。
- **失败模式**：`segmentby` 基数过高会让 batch 太小；对冷数据做 DML 有解压和重新压缩的写放大。

### 3.3 QuestDB（检查 tag 10.0.1）

- **架构**：每个表每个连接一个 WAL 写入器，异步应用到表存储。表按时间分区（HOUR、DAY、WEEK、MONTH、YEAR），每个分区目录里每列一个文件，只追加并 mmap。原生格式不压缩，官方建议用 ZFS + LZ4；旧分区可以转成 Parquet。
- **SYMBOL 类型**：按列的字典，行里只存整数引用。字典常驻内存，千万级以上的取值会占用大量内存。
- **时间裁剪**：先按分区裁剪；分区内按指定的时间戳列物理有序，二分查找后连续扫描。
- **乱序写入（O3）**：
  - 迟到的行在暂存区做基数排序；提交时把受影响的分区范围拆成前段、合并段、后段，用 memcpy/SIMD 重写。
  - 重写后的分区是带版本后缀的新目录，旧版本留给正在读的读者，之后再清理（`O3PartitionJob`、`O3PartitionPurgeJob`）。
  - 已有前段大于 50 MB 且超过新数据加后段时，改为拆分分区，而不是整段重写。
  - 写放大定义为「实际写入行数 ÷ 提交行数」，有对应监控指标。
- **物化视图**：`IMMEDIATE` 刷新只重算新数据碰到的时间片；对基表做 UPDATE、TRUNCATE 或删分区会触发全量重建。

### 3.4 ClickHouse MergeTree 家族（检查 tag v24.8.4.13-lts）

- **架构**：
  - 每次插入生成一个不可变的 part，后台多路合并，单个 part 默认上限 150 GB；不同分区的 part 不会合并在一起。
  - 小 part 用 Compact 格式（全部列在一个文件，小于 10 MiB），大 part 每列一个文件。
  - 每个分区的活跃 part 超过 1000 个就延迟插入，超过 3000 个就报错「Too many parts」（`MergeTreeSettings.h`）。
  - 来源：[VLDB 2024 论文](https://www.vldb.org/pvldb/vol17/p3731-schulze.pdf) §3.1。
- **格式**：
  - 行按 8192 行切成 granule；`.mrk` 文件把 granule 号映射到压缩块偏移和块内偏移。
  - 每列可以串联编码：Delta、DoubleDelta、Gorilla、T64，再接 LZ4 或 ZSTD。
  - `LowCardinality` 是字典编码，官方建议 1 万个取值以下使用，超过 10 万个「可能更差」（置信度中）。
- **索引**：稀疏主键索引，每个 granule 只存首行的主键，800 多万行只需约 1000 项，常驻内存。
  - 第一列的过滤条件可以二分；后续列只有前一列基数低时才裁剪得有效。
  - 另有分区 min/max、跳数索引（minmax、set、bloom_filter），以及按另一种排序存一份数据的 projection。
- **迟到数据**：就是另一个 part，合并时排进去。改写已有数据（mutation）要重写受影响的 part，代价高；轻量删除用隐藏的位图列标记。
- **计数器预聚合**：
  - **SummingMergeTree**：合并时把主键相同的行合成一行，数值列相加；求和结果全为 0 的行在合并时删除（`SummingSortedAlgorithm.cpp`）。合并不保证做完，所以查询仍要 `sum() GROUP BY`。
  - **AggregatingMergeTree**：存部分聚合状态，通常由增量物化视图写入，每个新 part 只处理一次。
  - **TTL 的 `GROUP BY`** 可以把过期数据卷成粗粒度；`ttl_only_drop_parts` 按整个 part 删除。

### 3.5 Apache IoTDB / TsFile（检查 IoTDB v1.3.2、TsFile v1.1.0）

- **顺序与乱序分离**：写入时只做一次比较，`time > lastFlushTimeMap.getFlushedTime(partition, device)` 时进顺序文件，否则进乱序文件（`DataRegion.java:887-890`；[VLDB 2020 论文](https://www.vldb.org/pvldb/vol13/p2901-wang.pdf) §2.3）。压实分三种：顺序文件内部、乱序文件内部、乱序合入顺序。
- **TsFile 层级**：文件 → ChunkGroup（一个设备一段时间）→ Chunk（一个序列，读取单位）→ Page（解码单位，默认 64 KiB 或 10,000 个点）。每页的页头带计数、起止时间、最小/最大值、首末值和总和。
- **索引**：文件末尾有元数据索引树（度 256）和设备布隆过滤器，按文件、chunk、页三级裁剪。
- **迟到数据的代价**：乱序文件的时间窗口会和顺序文件重叠，查询时要对多个 chunk 做归并排序；压实做完之前查询延迟会上升（论文 §2.3–2.4）。
- **预聚合**：只靠页、chunk、文件级的统计值（含总和）。时间范围上的聚合可以整页取统计值、不用解码，前提是该页没有被乱序数据重叠（这个前提是推断）。

### 3.6 TDengine（简述）

- 每个数据采集点一张表，单写者无锁写入。按时间窗口分文件组（`DURATION` 默认 10 天）：
  - `.head` 是块范围索引（BRIN）；
  - `.data` 是按列压缩的块，每块 100–4096 行；
  - `.sma` 存每块的总和、最小、最大；
  - `.stt` 存待合并的碎片；
  - `.tomb` 存删除范围。
- 「每个组合一张表」对我们意味着 60 万张表，切分方向不对。可借鉴的是两点：每块带总和统计，以及按时间窗口分文件、保留期到了就删整个文件。

## 4. 嵌入式与参考格式

### 4.1 DuckDB（检查 tag v1.4.0）

- 单文件，块大小 256 KiB；每 122,880 行（60 × 2048）一个 row group，每列一个列段（`storage_info.hpp`）。
- 每个列段先分析数据再选压缩：Constant、RLE、BitPacking、FOR、Dictionary、FSST、ALP 或 Zstd。选轻量压缩是因为数据在内存中时，通用压缩的解压太慢（[博客](https://duckdb.org/2022/10/28/lightweight-compression.html)）。
- 每列自动建 min/max 区域映射，数据越有序越有用。
- 对我们：组合 id 在桶内均匀分布，区域映射帮不上忙；时间上的裁剪我们已经靠桶前缀做到了。可以借鉴它的布局思路，但不必嵌入 DuckDB 本身。

### 4.2 Parquet 与 Arrow IPC

- **Parquet**：文件 → row group → 连续存放的 column chunk → page。元数据在文件尾。字典页放在 column chunk 开头，字典过大时写入器退回 PLAIN。页索引（ColumnIndex 和 OffsetIndex）让读者不读每个页头就能跳页。推荐的 row group 大小（512 MB–1 GB）是为 HDFS 调的，不适合嵌入式。
- **Arrow IPC**：按 8 字节（推荐 64 字节）对齐的平坦缓冲区，可以不复制直接读，可选 LZ4 或 ZSTD；**没有统计信息和索引**。
- **对我们**：定宽对齐的 `[u32 id][u64 up][u64 down][u64 conn]` 本质上是一个单批的 Arrow 缓冲区，能直接在 redb 的页上求和，不用解码。一旦压缩，就失去了这个不复制读取的好处。

### 4.3 LSM（RocksDB / LevelDB）与 B 树（redb / LMDB / SQLite）

- **LSM 结构**：WAL 加 memtable，落盘为有序 SST，逐级压实。第 0 层文件越多，每次读要合并的文件越多。
- **RocksDB 的合并算子**：专门为计数器设计，把「先读再写」变成追加一个操作数，在读取或压实时折叠；不实现 `PartialMerge` 时，所有操作数都要放在内存里（[Merge Operator wiki](https://github.com/facebook/rocksdb/wiki/Merge-Operator)）。
- **对我们**：LSM 的长处是不读就写，但我们只有一个进程内写者，读出当前桶再改写本来就便宜。我们的热路径是读扫描，而 LSM 恰好在读扫描上更贵。B 树加上「每个桶一个大值」，既拿到了批量的好处，又没有读放大。

## 6. 共性模式

1. **索引批次，不索引行。** 所有系统都把每条索引项的成本摊到几千到十几万行上。redb 每条约 45 ns，摊薄后剩下的就是对连续内存的顺序扫描。
2. **查询怎么扫，就按什么顺序存。** 「少数序列 × 长时间」用序列优先，「所有序列 × 一段时间」用时间优先。InfluxDB 从 TSM 走到 IOx，又在企业版退回序列优先，说明两种负载很难用一种布局同时照顾好。
3. **可变的头部加不可变的冷数据。** Gorilla 的开放块、Prometheus 的 Head、TSM 的 Cache、IOx 的内存缓冲、TimescaleDB 的行存都是这样：最近的数据放在便宜的可变结构里，到点封存。
4. **迟到数据走单独的路径，之后再合并。** IoTDB 用乱序文件，Prometheus 用乱序缓冲加重叠块，ClickHouse 和 VictoriaMetrics 写新 part，TimescaleDB 用暂存区，QuestDB 重写分区范围。成本都是「读时合并」加「后台压实」，并且都随迟到数据涉及的历史跨度增长。
5. **可加的聚合在合并时相加。** SummingMergeTree、RocksDB 合并算子、TsFile 页总和、TDengine `.sma`。求和满足交换律和结合律，增量不需要排序，也不需要按时间戳去重。
6. **维度值用字典编码；高基数时字典是长期风险。** LowCardinality、Parquet 字典、QuestDB SYMBOL、Prometheus 符号表都在高基数下给出警告。VictoriaMetrics 和 Prometheus 的教训是：序列频繁更替时，索引和字典的增长比样本字节更要紧。
7. **保留按整单元删除。** 整块、整分区、整文件，从不逐行删除。
8. **压缩为空间服务，并优先轻量编码。** DuckDB、TimescaleDB 选轻量编码和 FastLanes，就是因为数据在内存中时解码速度比压缩率更重要。

## 7. 映射到我们的存储

### 7.1 可选设计

| 方案                      | 做法                                                                                             | 借鉴来源                                                             | 读                             | 写                                            | 复杂度 |
| ------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- | ------------------------------ | --------------------------------------------- | ------ |
| A. 每桶一条，整条重写     | 键为桶，值为按 id 排序的定宽数组；flush 读出、归并相加、写回                                     | ClickHouse granule、IOx 时间块                                       | 已测：快 17 倍                 | 已测：最近一小时 0.5 ms；旧桶也要整条重写     | 低     |
| B. 每桶按 id 范围分段     | 键为 `(bucket, segment)`，每段最多 N 个组合                                                      | TimescaleDB 的 1000 行 batch、QuestDB 拆分分区                       | 与 A 接近，多几次查找          | 一次只重写碰到的段                            | 低到中 |
| C. 已封存的记录加一层增量 | 当前桶照 A 写；更早的桶封存，迟到写入追加到 `(bucket, seq)` 增量记录，读时相加，每小时维护时折叠 | IoTDB 顺序与乱序分离、SummingMergeTree                               | 多读增量记录，合并是数组相加   | 迟到写入只追加小记录                          | 中     |
| D. 加日桶层级             | 小时卷成日，长范围读日桶                                                                         | ClickHouse TTL `GROUP BY`、Gorilla 的 ODS 卷积、IOx 小文件上限的教训 | 7 天和「全部」的记录数降到天数 | 迟到写入要同时加到日桶                        | 中     |
| E. 内存窗口累计和         | 为 24 小时、7 天维护每个组合的累计和：flush 时加，桶移出窗口时减                                 | InfluxDB 3 Last Value Cache、TimescaleDB 实时聚合                    | 轮询不读库                     | 每次写入维护；60 万组合 × 24 B ≈ 14 MB / 窗口 | 中     |

说明：

- **我们的迟到写入不需要负增量。** 两份子调研假设连接关闭时要把用量从「临时组合」挪到「最终组合」，所以建议用有符号增量或墓碑。本仓库不是这样：活跃连接的分时用量只在内存和 `active` 表里，关闭时才按最终维度写入用量表（`accounting.rs:61-77`、`:344-370`）。用量表只做加法，所以 C 方案的增量记录用无符号累加即可，也不需要 SummingMergeTree「和为 0 就删行」的规则。
- **A 的风险在长连接。** 一个持续 N 小时的连接关闭时，会碰到 N 个旧小时桶。A 方案要把每个旧桶整条重写，在 M 库规模下每个小时桶约 110 KB；如果一次 flush 里有连接跨 7 天，就要重写约 168 × 110 KB ≈ 18 MB。这个数字是 M 库规模下的推算。第 1.1 节的真实库组合少、每桶小，整桶重写最多 110 KB，p99.9 为 11 KB；高基数的网关场景仍可能接近上面的推算。B 把每次重写限制在一段之内，C 把它变成追加，都是 QuestDB、IoTDB 已经付过代价的做法。
- **D 和 E 解决的是另一件事。** A、B、C 降低每条记录的成本；D 减少长范围要读的记录数；E 让轮询不读库。E 和 review 文档里的 #2（actor 缓存已写库的行）都在消除重复读库：#2 更简单，但拼表那 25 ms 还在。E 连拼表都省了，但要维护一套窗口状态，内存随组合数增长，InfluxDB 3 的文档对这一点有同样的警告。

### 7.2 其他可借鉴的细节

- **组合 id 保持稠密、可复用。** 打包格式下 id 只出现在桶记录里。回收组合时，只要没有任何桶记录还引用某个 id，就可以复用它，不需要重写记录。保留期删桶后，未被引用的 id 自然空出来，这与 VictoriaMetrics 按分区删 indexdb 的思路一致。
- **按维度排序分配 id。** Prometheus 让序列 id 的顺序等于标签顺序，VictoriaMetrics 在 TSID 前面放分组字段，目的都是让同组数据存在一起。我们现在按维度值编号聚合，用不上这一点；只有将来要在桶内按维度裁剪时才有价值。
- **编码先不压缩。** 每条记录最多几万个组合，定宽格式能直接在页上求和。要省空间时，再对有序 id 做差值加位打包（类似 Parquet 的 DELTA_BINARY_PACKED、DuckDB 的 FOR），对计数器做 T64 式的高位裁剪。上线前要测解码对 2 s 轮询的影响。
- **SoA 还是 AoS，按测量决定。** 只有查询只读部分计数器（例如只要字节、不要连接数）时，按列存放才明显更好。
- **分钟层的记录很小，逐条读的代价也小。** 6 小时只有 360 条分钟记录，读取次数本来就少，可以先只改小时层。

### 7.3 与第 8 节的关系

7.1 的五个方案不互斥。第 8 节把它们组合进一个独立的存储层：

- 分段（B）和增量块（C）作为时序表的写入策略；
- 日层级（D）作为可选的汇总层；
- 窗口缓存（E）退为有界的范围结果缓存。

只改存储格式、不拆层的做法（直接在 `redb.rs` 里实现 A），在第 8.15 节的落地顺序里作为对照组保留。

## 8. 存储层设计：`nyanpasu-tsdb`

### 8.1 目标与边界

**负载假设：**

- 软件常开时每天 10–20 万个连接，每月约 600 万个；作为家庭或工作室网关时更多。实测的一台桌面机每天 1.7–4.4 万个（第 1.1 节）。
- 组合基数跨度很大：实测桌面机只有 1,300 个；网关场景按合成库的 9 万–60 万个作上界。设计要同时照顾两端：低基数时空间几乎全是明细，高基数时读库和字典成为瓶颈。
- 查询以「一段时间内的全部组合」为主，界面每 2 s 轮询。
- 单进程、单写者，actor 每 30 s flush 一次（`actor.rs:23`）。
- 除流量外，内核日志和任务日志也是目标负载：只追加，按时间、级别和文本查询，按字节预算保留（第 8.5、8.8 节）。

**目标：**

- 读：读库成本只随要读的块数增长，不随条目数增长；打开库时不再逐个解 JSON。
- 写：一次 flush 的成本有上界，长连接关闭也不例外。
- 空间：明细和用量都能压缩；保留期到了整块删除。
- 可替换：底层先用 redb，以后可以换 LMDB、LSM 或自研段文件，换的时候上层格式不变。
- 可单独测：存储层是独立 crate，自带合成数据生成和基准，不依赖应用。

**暂定性能目标**（同一台机器，codex 提出，作为验收线而非预测）：

| 项目                | 目标                   |
| ------------------- | ---------------------- |
| M 库 7 天按组合求和 | ≤ 5 ms                 |
| L 库全部按组合求和  | ≤ 20 ms                |
| M 库 7 天完整总览   | ≤ 15 ms                |
| L 库全部完整总览    | ≤ 60 ms                |
| 打开库              | M ≤ 150 ms，L ≤ 400 ms |

**不做：**

- SQL 或查询语言，任意表结构，分布式。
- 自己的 WAL：底层引擎已有事务。
- crate 内的后台线程、定时器、线程池或全局单例：维护工作由 actor 发命令驱动，符合 `docs/development/architecture.md` 的规则。

### 8.2 分层：参照 TiDB 与 TiKV

```text
nyanpasu-traffic        流量业务：连接核算、活跃连接与速率、排行与拓扑的语义
        │
        ▼
nyanpasu-tsdb           时序层：表结构、字典与目录、时序表、事件表、块编码、
        │               写入暂存、快照读、范围规划、聚合内核、汇总、保留、维护
        ▼
engine（trait）         事务型有序字节 KV：命名空间、快照、原子写、有序扫描、持久性级别
        │
        ▼
redb（先做）/ memory（测试）/ heed、fjall、自研段文件（以后）
```

一句话概括：**按时间分区的嵌入式列式存储，在它上面同时承载时序统计（预聚合）和事件明细，两者共用一套字典。**`nyanpasu-tsdb` 内部是三根支柱，下面是一层可替换的底座：

| 层               | 做什么                                                                                                   | 对应现在的数据                            | 详见      |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------- | --------- |
| 字典与目录       | 每个维度的取值编号；组合（序列）= 一组标签编号；复用最小空闲 id；回收不再被引用的组合和标签值            | `tuples` 表，以及本分支内存里的维度值编号 | 8.6       |
| 时序表（预聚合） | 键为（层级，桶，段），值为按组合 id 排序的列式块；合并时求和；分钟、小时、可选的日层级；按桶删除过期数据 | `minute_usage`、`hour_usage`              | 8.7、8.9  |
| 事件表（明细）   | 只追加；按时间切块、列式存放，维度只存组合 id 或字典编号；封存后压缩；从新到旧翻页；按时间或字节预算保留 | `closed` 表；以后是内核日志、任务日志     | 8.5、8.8  |
| 存储引擎（底座） | 事务型有序 KV：命名空间、快照、原子写、有序扫描、空间回收；先用 redb，以后可换                           | redb 文件本身                             | 8.3、8.11 |

**列式和时序各自负责的范围：**

- **列式**只用在已封存的块内。当前桶和最新的明细块要频繁改写，保持定宽、不压缩；封存时再转成列式并压缩。TimescaleDB 热数据用行存、冷数据转列存，是同一个思路。
- **时序**负责按时间分区、分层汇总和保留期：查询按时间范围选块，长范围用粗层级，过期数据整块删除。

**刻意不做：**

- SQL 和任意表结构。
- 倒排索引：每个维度一列编号，60 万个 u32 在内存里扫一遍远低于 1 ms，需要时再加。
- 求和以外的聚合方式：块头先留出聚合方式和编码字段，以后加 last、min、max 不用改格式。

**照搬的部分：** 上层把逻辑数据编码成有序键值写进下层，下层不认识序列、标签、桶、字段，只负责有序存取和事务。TiKV 自己也是一个只提供原始 KV 和事务 KV 的存储层（[TiKV 架构](https://tikv.org/docs/5.1/reference/architecture/overview/)）。

**不照搬的部分：**

- 不要 Raft、region、调度和网络 RPC。
- 不要 coprocessor 那种「把计算下推到存储节点」的边界。TiKV 这样做是为了解决分布式执行问题（[coprocessor 说明](https://tikv.github.io/tikv-dev-guide/understanding-tikv/coprocessor/intro.html)）。我们在同一个进程里，所谓下推就是时序层直接对借来的块字节运行聚合循环；这段循环写在 `nyanpasu-tsdb` 里，不写进各个引擎适配器。

**为什么底层是 KV 而不是更窄的「块存储」：** 字典、空闲 id、批次标记，以及流量自己的会话表、活跃连接表，都必须和时序数据在同一个事务里提交。只能存块的接口装不下这些，通用有序 KV 刚好够用。

### 8.3 引擎契约

**必须提供：**

- 跨命名空间的一致快照，并且可以交给其他线程；
- 串行的写事务，能读到自己刚写的数据；
- 读单个值；
- 按范围正向或反向扫描；
- 写入和删除；
- 跨命名空间原子提交或放弃；
- 显式的持久性级别。

范围删除可以由时序层逐条删除来实现，不要求后端原生支持。

**空间回收**也要进契约，作为一个可选操作，由维护命令触发。redb 删除数据后文件不会收缩：真实库 156 MB，整理后只剩 89 MB（第 1.1 节）。redb 的实现是 `Database::compact()`，它需要独占的 `&mut Database`，没有读写事务时才能执行，所以只能放在打开库时或空闲时做。LSM 后端靠后台压实回收空间；按文件分区的后端直接删文件（第 8.8 节）。

**零复制读用回调表达**：引擎在回调期间持有 redb 的 `AccessGuard` 或 LMDB 的事务，时序层借用字节、只返回聚合结果。这样不需要强制复制块，不需要装箱迭代器，每条数据也没有动态分发。

```rust
pub trait Engine: Send + Sync + 'static {
    type Snapshot: ReadTxn + Send + 'static;
    type Write<'db>: WriteTxn where Self: 'db;

    fn snapshot(&self) -> Result<Self::Snapshot>;
    fn begin_write(&self) -> Result<Self::Write<'_>>;
}

pub trait ReadTxn {
    fn with_value<T>(
        &self,
        ns: Namespace,
        key: &[u8],
        read: impl FnOnce(Option<&[u8]>) -> Result<T>,
    ) -> Result<T>;

    fn scan(
        &self,
        ns: Namespace,
        range: KeyRange<'_>,
        direction: Direction,
        visit: impl FnMut(&[u8], &[u8]) -> Result<ControlFlow<()>>,
    ) -> Result<()>;
}

pub trait WriteTxn: ReadTxn {
    fn put(&mut self, ns: Namespace, key: &[u8], value: &[u8]) -> Result<()>;
    fn delete(&mut self, ns: Namespace, key: &[u8]) -> Result<()>;
    fn commit(self, durability: Durability) -> Result<CommitReceipt, CommitFailure>;
}
```

- 事务类型用关联类型和 GAT 表达。只有调用方确实需要在回调之外持有值时，才再加 GAT 形式的值守卫或游标。
- 动态分发只放在粗粒度的边界上，比如流量的 `TrafficStore` 端口；块解码循环里不用。
- redb 4.4.0 的 `ReadTransaction` 是 `Send + Sync`，可以在写入并发进行时读（[文档](https://docs.rs/redb/latest/redb/struct.ReadTransaction.html)）。LMDB/heed 要用不绑定线程的读事务（[`Env`](https://docs.rs/heed/latest/heed/struct.Env.html)、[`RoTxn`](https://docs.rs/heed/latest/heed/struct.RoTxn.html)）。
- 持久性至少区分两种：提交即落盘，和只保证对后续读可见。redb 对应 `Durability::Immediate` 和 `Durability::None`（[文档](https://docs.rs/redb/latest/redb/enum.Durability.html)）。

### 8.4 事务与原子性

现在一次 flush 在同一个事务里写会话元数据、活跃连接、两层用量、明细，并做清理；组合缓存在提交成功后才更新（`redb.rs:285-345`）。拆层后保持这一点：**事务归调用方所有，时序层只往里写，从不提交。**

```rust
let mut tx = engine.begin_write()?;
write_session(&mut tx, &batch)?;
write_active_changes(&mut tx, &batch)?;
let prepared = tsdb.write_in(&mut tx, &batch.usage, &batch.closed)?; // 字典、块、清理、汇总
write_flush_marker(&mut tx, batch.id)?;
let receipt = tx.commit(Durability::Immediate)?;
tsdb.publish(receipt, prepared); // 不会失败的所有权交换
```

**三条规则：**

1. **暂存的变化在提交前不可见。** 新分配的 id、字典项、当前桶缓存和结果缓存的变化，都先留在 `PreparedUpdate` 里，提交成功后才发布。
2. **出错只能放弃。** 时序层写到一半出错，整个事务只能放弃，调用方不能吞掉错误后继续提交。
3. **发布不会失败。** 新目录需要的内存在提交前就分配好，提交后的发布只是交换指针。

**提交结果不确定时：** 引擎契约区分「确定没提交」「已提交」和「结果未知」三种情况。现在 actor 在 `flush` 返回任何错误时都会把批次放回去重试（`actor.rs:187-198`）。如果提交其实已经成功、只是报错，重试会把同一批用量再加一次。新设计在同一个事务里写入单调递增的批次号；重试前先核对批次号，确认上次没有提交再重放。

**快照与目录的一致性：** 写入方在提交和发布目录期间持有一个发布门。读取方在门内同时拿到引擎快照和对应代号的目录，所以不会出现「看到新块却拿着旧目录」的情况。持门时间包含 fsync，需要实测。

### 8.5 数据模型

一个数据集有一份不可变的表结构：

```rust
pub struct Schema {
    pub labels: Vec<LabelSpec>, // 字符串维度，按维度各自做字典编码
    pub fields: Vec<FieldSpec>, // 目前只有 u64、可加、饱和加法
    pub tiers: Vec<TierSpec>,   // 桶宽与保留期
    pub events: Option<EventSpec>,
}
```

- **字段：** 目前只支持「可加的 u64 增量，饱和加法」。表结构和块头都预留「聚合方式」和格式版本字段。以后要支持 last、min、max 或平均值，就新增块版本和对应的聚合循环；现在不做插件框架，也不为它付运行时开销。
- **标签身份：** 字典里存的必须是能还原原始维度的值，不能是展示用的字符串。现在规则的展示键用逗号连接类型和内容，策略链用箭头连接，订阅缺失和空字符串都显示为空（`model.rs:44-50`、`:190-205`），这些都会丢信息。流量的映射应当是：
  - 报表用的 13 个展示维度；
  - 加上能还原原始维度的规范标签：规则类型、规则内容、完整策略链、带「有没有」标记的订阅。
  - 这些标签都由流量层构造。
- **流量的字段：** 上传字节、下载字节、连接数。连接数只计入关闭时所在的桶（`accounting.rs:362-372`）；字节数按连接经过的每个桶计入。
- **事件表：** 每个事件 = 时间键 + 若干类型化的列。列类型是通用的，不为某一种负载定制：

  | 列类型             | 编码                            | 例子                     |
  | ------------------ | ------------------------------- | ------------------------ |
  | 时间戳             | 块内差值或差值的差值，varint    | 关闭时间、日志时间       |
  | 有符号或无符号整数 | 差值或帧参考，加位打包或 varint | 时长、字节数、序号       |
  | 组合 id            | 引用字典目录里的组合，位打包    | 已关闭连接的维度         |
  | 低基数字符串       | 按列字典编码                    | 日志级别、来源、模块     |
  | 定长字节           | 原样存放                        | 连接 id（UUID，16 字节） |
  | 长文本             | 按块 zstd，可带预置字典         | 日志正文                 |
  - **已关闭连接**：关闭时间、开始时间、首次看到的时间、上传、下载、组合 id、连接 id。真实库里连接 id 100% 是 UUID；遇到不是 UUID 的 id 时退回文本列。
  - **内核日志**：现在每条单独用带预置字典的 zstd 压缩，另有一张按级别的索引表，按字节预算删除最旧的分片文件，重启时清掉上次会话的文件（`backend/tauri/src/core/logs/redb.rs`）。映射为：序号或时间、级别（字典）、正文（长文本）。
  - **任务日志**：`nyanpasu-jobs` 的 redb 存储在 `nyanpasu-runtime` 子模块自己的 workspace 里。要接入就得把 `nyanpasu-tsdb` 放到两个 workspace 都能依赖的位置，这一点留待以后决定。

### 8.6 字典与目录

| 命名空间                     | 内容                                           |
| ---------------------------- | ---------------------------------------------- |
| `schema`                     | 表结构和格式版本                               |
| `label_values`               | `(维度, 编号) → UTF-8 值`                      |
| `label_lookup`               | `(维度, 值) → 编号`                            |
| `series`                     | `组合 id → 定长的标签编号数组`                 |
| `series_lookup`              | `标签编号数组 → 组合 id`                       |
| `free_series`、`free_labels` | 空闲 id 的有序区间或位图                       |
| `liveness`                   | 每个组合在各层、在事件表里最后被引用的桶或时间 |
| `blocks`、`events`           | 时序块（基础块与增量块）、事件块               |
| `bucket_meta`、`rollup_meta` | 桶的代号、封存状态、增量序号；汇总覆盖范围     |
| `commit_meta`                | 目录代号、已应用的批次号                       |

**id 分配：**

- 组合 id 用 `u32`，耗尽时显式报错。按用户的选择复用最小的空闲 id：持久化空闲区间，分配时取最小值，没有空闲时推进高水位。
- 不按标签顺序分配 id。那样和「复用最小空闲 id」冲突，字典变化时也要重排。

**内存中的目录：**

- 每个维度一列标签编号，按组合 id 索引，以 SoA 形式放在不可变、可共享的分页里。写入时只复制改动的页。
- 字符串只在查找输入和返回结果时才用。
- 打开库时读的是定长数字记录，每个不同的字符串只读一次，不再逐个解析组合的 JSON。

**快照安全：**

- 一个组合 id 只有配上它所属的目录快照才有意义。每个查询都持有「引擎快照 + 不可变目录快照 + 代号」。
- 删掉的 id 可以在新代号里立刻复用：旧读者手里仍是旧块和旧目录，结果缓存也绑定了目录代号。

**回收：**

- 不用引用计数。保留期只按前缀删除、数据只加不减，所以每个组合只需记「在各层和事件表里最后被引用的位置」。所有这些位置都落到各自的保留下限以下、并且调用方没有钉住（活跃连接和 pending 引用的组合）时，这个组合就可以回收。
- `liveness` 和块写入在同一个事务里更新。
- 回收组合时同时删除反查项、释放 id，并递减它用到的标签值的引用计数；引用计数归零的标签值才释放编号。
- 现在的做法（`redb.rs:429-464`）是每小时全量扫一遍两张用量表。新设计把全量标记清除降为完整性检查和修复手段。
- 注意：明细也引用组合，所以明细的保留期同样决定组合能否回收。这一点 codex 的方案没有覆盖。

### 8.7 时序表

**键**（大端编码；有符号的桶号先翻转符号位，保证字节序就是数值序）：

```text
tier: u8 | bucket: i64 | segment: u32 | kind: u8（基础块 / 增量块）| seq: u64
```

**分段：**

- 段号 = 组合 id / 段宽。段宽是格式参数，不随 flush 变化。
- 候选值 16,384：满载时 id 加三个 u64 字段约 448 KiB，加上块头也在 512 KiB 以内。
- 要和 2,048、4,096、不分段三种做对比测试。段太窄会把稀疏的桶切成很多小值，失去打包的好处。

**块格式：**

```text
magic | format_version | schema_fingerprint | header_len | payload_len
row_count | min_id | max_id | block_generation
每个字段：encoding | offset | length | 饱和总和
checksum (CRC32C) | padding
series_ids[] | field_0[] | field_1[] | ...
```

- 默认 SoA；当前桶用原始定宽的小端整数。块内 id 有序、唯一，列偏移按 8 字节对齐。
- 解码前严格校验边界、长度、顺序和表结构指纹。
- 块内对齐不保证 redb 值的起始地址对齐。通用解码器用安全的小端读取；只有检查过对齐和字节序后，才走类型化切片的快速路径。所以「零复制」指不强制分配和复制，不是不需要解码指令。
- 块头里的字段总和，可以让「无筛选的全量总计」不用解码；分组和筛选仍要逐个组合解码。
- SoA 还是 AoS 要实测：仓库还没有对两者做过对比。

**写入路径：**

1. 时序层的「头部」只包含等待本次 flush 的已关闭连接用量。活跃连接仍归流量层管：它们的维度在观测期间会变，结果也要带速率。
2. 解析和登记标签与组合，合并同一个（层，桶，组合）的重复增量，按桶和段分组，生成有序的列块。
3. **当前桶：** 已解码的当前桶段可以留在写入方私有的缓存里。每次只重写本次碰到的段。这个缓存可以随时丢弃，里面绝不能有尚未提交的数据。
4. **已封存的桶：** 封存只表示换一种写入策略，内容仍可增加。迟到增量追加成增量块，序号递增，不读旧块。
5. **读取永远是「基础块 + 所有可见增量块」**，正确性不依赖维护是否做完。这与 SummingMergeTree 的规则相同。

**折叠（把增量块并入基础块）：**

- 每段增量块达到 4 个，或增量字节接近基础块大小时，请求维护。
- 硬上限 8 个：达到上限时，下一个增量写入前先同步折叠该段。
- 维护由 actor 发命令、带工作量预算，每次只折叠有限的段。时序层不起定时器，也不起后台写线程。
- 折叠在一个事务里原子地替换基础块、删除用掉的增量块；MVCC 下的旧读者继续看到旧版本。
- 以上阈值都是待测参数。

**写放大的上界：**

- 段宽限制了基础块大小，增量块数量有硬上限，单次折叠的工作量也就有上限。
- 对「大量很小的迟到增量」，折叠的放大比约等于基础块大小 / 增量大小，不是常数。
- 读放大、flush 延迟、存储增长三者不能同时任意压低。维护跟不上时，硬上限会把代价显式地转到 flush 上。

### 8.8 事件表与压缩

**规模**（每条大小是第 1.1 节在真实库上的实测；每月的总量是按连接数推算的）：

| 数据           | 现在每条                                                | 新格式每条（实测）         | 每月 300 万–600 万连接时           |
| -------------- | ------------------------------------------------------- | -------------------------- | ---------------------------------- |
| 已关闭连接明细 | 527 B JSON 值 + 44 B 键（`model.rs:333`、`redb.rs:34`） | 25.0 B（列式 + zstd）      | 现在 1.7–3.4 GB，新格式 75–150 MB  |
| 小时用量       | 28 B                                                    | 8.3–8.9 B                  | 取决于每小时的组合数，与连接数无关 |
| 组合           | 374 B JSON                                              | 约 52 B 编号数组，外加字典 | 取决于基数；实测每天新增 49–343 个 |

**事件块：**

- **写入与封存**：事件按时间只追加。当前块保持原始格式，攒满 4,096 个事件或一个时间窗后封存。封存时按列编码（第 8.5 节的列类型），然后整块 zstd。在真实库上，已关闭连接的列式编码是 30.3 B/条，加 zstd 后 25.0 B/条；整块 JSON 直接 zstd 是 44.3 B/条。所以"只存组合 id + 列式"本身就贡献了大部分收益。
- **块头统计**：
  - 事件数、时间的最小值和最大值；
  - 每个低基数字典列的取值位图，比如这一块出现过哪些日志级别、哪些组合 id 区间。

  这些统计让查询整块跳过，可以替代内核日志现在单独维护的级别索引表。

- **翻页**：从新到旧按块倒序读，按块头时间跳过不相关的块。筛选先在目录里把条件换成"满足条件的组合 id 位图"，再逐个事件检查，比现在逐条解 JSON 便宜。
- **文本搜索**：先按块解压后扫描。需要时再在块头加 n-gram 布隆过滤器；倒排全文索引不做。
- **保留**：支持两种策略。
  - 按时间（流量）：只删除完全过期的块；跨越截止时间的块在读取时按时间过滤，等整块过期再删。Prometheus 也是这样做的。
  - 按字节预算（日志）：超出预算时删除最旧的块。
- **分区落在独立文件上（可选）**：一个数据集可以按时间或大小拆成多个引擎实例，每个实例一个文件。保留期到了就直接删文件，不留空闲页，也不需要 `compact()`。内核日志现在的分片文件、QuestDB 的分区目录、TDengine 的文件组都是这个做法。代价是跨分区的查询要打开多个实例，跨分区的写入也不再是一个事务。所以流量这种"明细要和用量同一事务提交"的数据集默认单文件，日志这种独立数据集可以按文件分区。
- **单页扫描上限**：现在一页最多扫描 `MAX_CLOSED_SCAN` 条（`model.rs:360`）。改成按块扫描后，这个上限改按块数计算。

**用量块的压缩：**

- 当前桶和增量块不压缩，保留在页上直接求和的能力。
- 基础块在封存或折叠时改用轻量编码：有序 id 做差值加位打包；字段用常量编码，或帧参考加位打包。解码速度在 GB/s 量级。
- 选不选压缩编码，按「省下的 IO 和缓存」是否超过「解码代价」实测决定。块头记录编码方式，新旧编码可以共存。
- 字节数在不同组合之间没有顺序，所以按时间做差值的差值、XOR 这类时序常用编码不适合做默认值。

**需要产品决定的两件事：**

- **降采样保留**：例如小时数据保留 N 天，更早的只留日数据。这会降低旧数据的时间精度。
- **粗层级的基数约束**：网关场景下源 IP × 目标会让组合数成倍增长。可以让日层级把源 IP 归并到设备组、把目标归并到主域名，但这会改变统计口径。

### 8.9 分层汇总与保留

- **分钟层和小时层各自写入。** 不能由分钟数据推导小时数据：活跃连接会丢弃分钟层范围以外的旧分钟桶，只保留小时桶（`accounting.rs:210-221`），长连接关闭时分钟历史已经不完整。
- **日层级可选**：
  - 一天结束后，由这一天的小时快照生成，并记录覆盖范围和来源代号。
  - 生成之后，凡是落进这一天的小时增量，在同一个 flush 事务里同时加到日数据上。还没生成的日子不用管，生成时自然包含。
  - 重建是替换，不是再加一次；折叠只是重新组织数据，不会向上层级传播增量。
- **范围规划**：完整落在范围内的天读日数据，其余部分读小时数据，需要分钟精度的地方读分钟数据；同一段时间绝不同时读父层和子层。粗层级回答不了部分覆盖的桶时，要显式返回精度信息或拒绝，不能悄悄把整个桶算进去。
- **保留边界不变**：恰好在截止点上的桶保留（`redb.rs:490-512`）。迁移期间沿用现在按桶取整的范围语义（`bucket.rs:30-57`）。
- **日层级的收益要实测。** 如果大多数组合一天里只出现几个小时，日数据比小时数据省不了 24 倍。

### 8.10 读取路径

**查询放到 actor 外面执行**（相当于 review 文档的 #5）：

1. actor 在一次处理中捕获：持久化快照（引擎快照 + 目录）、pending 增量、活跃行和速率、当前时间边界，然后返回。
2. `TrafficClient` 在 `spawn_blocking` 里扫描并计算报表。

mailbox 仍是唯一的串行化点，只是不再在消息处理里做重计算；这也符合「不在 actor 里另建调度层」的规则。只靠 MVCC 解决不了 mailbox 阻塞，因为现在的消息处理会一直等到聚合做完（`actor.rs:309-335`）。

**核心原语是按组合求和：**

- 返回稠密的 SoA 字段、存在位图、实际碰到的 id，以及对应的目录快照。存在位图用来区分「有一行但值全为 0」和「没有这一行」。
- id 稀疏时，累加数组按页懒分配；从持久化数据创建数组之前，先检查内存预算。

**可下推的部分**（在时序层里实现）：只读部分字段、标签编号的等值筛选、按一个或几个标签分组求和。

**留在流量层的部分：**

- 排行忽略自身维度的筛选（`query.rs:146-190`）；
- 拓扑先选节点再累加边、跳过空的策略链（`topology.rs:38-57`、`:101-127`）；
- 前 k 名并列时的排序、连接范围（全部 / 已关闭 / 活跃）、速率。

**不再每次重建 `UsageTable`：**

- 流量层的视图 = 已存用量 + 目录里的标签列 + pending 覆盖层 + 活跃覆盖层（带速率）。M 库 7 天那约 25 ms 的拼表成本由此消除。
- 现在表内重新编号的好处（短范围的分组数组按实际出现的值分配）以懒方式保留：只为真正参与分组的维度建紧凑映射。

**缓存：**

- 先做一个有界的已存范围聚合缓存。缓存键包含数据集、规范化后的范围和精度、所选字段、数据和目录代号。这个缓存涵盖 review 文档的 #2。
- 一开始只要时序数据有任何提交就整体失效；以后可以按桶代号只失效被改动的范围。pending 和活跃数据不进缓存。
- 增量窗口（24 小时、7 天）可选。因为加法会饱和，不能从饱和后的 u64 总和里做减法：内部要用更宽的整数并检查溢出，只在对外边界处饱和；否则就重算。

### 8.11 后端可替换性

| 后端         | 适配要点                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| redb         | 先做。命名空间映射为字节表；流量和时序的写入共享一个事务。页大小、表句柄类型、持久性枚举都留在适配器内部                                                                        |
| LMDB / heed  | 同一个环境、多个命名数据库，事务模型一致。要处理 map 大小、读者数上限、事务能否跨线程、读者钉住的页                                                                             |
| fjall（LSM） | 用跨 keyspace 的快照和原子批写，写入串行化，能读到自己的写入（[文档](https://docs.rs/fjall/latest/fjall/)）。基准里要算上 WAL 持久性和压实。不能假定它有 RocksDB 那样的合并算子 |
| 自研段文件   | 必须提供同样的原子事务边界，包括流量的元数据；或者让不可变块文件由一个在事务中发布的清单引用。只会写块文件是不够的                                                              |

- **合并算子不进必选契约。** LSM 的合并算子可以在读取或压实时折叠增量块（RocksDB 支持），但必须保持饱和加法、快照、保留和字典生命周期的语义。可移植的实现仍是显式增量块。
- **换后端要整体搬迁**：流量的全部表必须一起搬到同一个事务域里，不在两个数据库之间做两阶段提交。

**每个引擎适配器都要通过的一致性测试：**

1. 跨命名空间（时序 + 流量）的原子提交和放弃；
2. 写入和删除后能读到自己的写入；
3. 并发提交期间，跨命名空间快照保持稳定；
4. 字节序、范围边界、前缀隔离、反向扫描；
5. 借出值的生命周期安全，扫描可以提前终止；
6. 崩溃恢复后得到完整的已提交前缀；
7. 提交结果未知时，能按批次号核对；
8. 清理和 id 复用期间旧读者仍然正确；
9. 持久性级别的行为；
10. 磁盘满、值损坏、后端限制时的失败处理。

**时序层的性质测试**（用一个小的参考映射作为预言机）：

- 增量任意拆分后，结果与参考一致；
- 折叠不改变存在性和数值；
- 汇总的范围规划从不重叠；
- 迟到增量对已生成的父层级恰好生效一次；
- 重新打开后，最小空闲 id 分配保持一致；
- 回收从不释放仍被引用的组合或标签值；
- 不同引擎上饱和与溢出的规则完全一致。

### 8.12 crate 布局与 API

按用户要求放在一个独立 crate 里，后端用 feature 区分：

```text
backend/nyanpasu-tsdb/
  src/
    lib.rs
    engine.rs        引擎契约
    engine/redb.rs   feature = "redb"（默认）
    engine/memory.rs 测试和基准用的内存引擎
    schema.rs  catalog.rs  dictionary.rs  series.rs
    block.rs   codec/      bucket.rs
    write.rs   snapshot.rs query.rs  rollup.rs
    events.rs  retention.rs maintenance.rs error.rs
  benches/           criterion：编码、聚合循环、字典、当前桶合并
  src/bin/ 或 examples/ 合成 S/M/L 库的生成器与端到端基准
```

**依赖方向与规范：**

- 依赖方向：`nyanpasu-traffic → nyanpasu-tsdb`，由宿主组装具体引擎。
- 两个 crate 都是中立 crate，不依赖 Tauri、ractor、tokio，不读时钟，没有全局单例、线程池或后台任务（`docs/development/backend-packages.md`、`architecture.md`）。
- 流量继续拥有自己的 `TrafficStore` 端口，具体实现改为组合 `nyanpasu-tsdb`。

**codex 给的另一种布局：** 把 redb 适配器拆成独立的 `nyanpasu-storage-redb`，并把流量的具体存储实现移到 `nyanpasu-platform`，理由是存储基准完全不依赖应用、具体基础设施实现放在平台层。这里选单 crate 加 feature，满足「单独 crate、单独 bench」即可；以后要加第二个后端，或者平台层规则要求时，再拆。

**API 草图**（示意，不是最终代码）：

```rust
impl Tsdb {
    pub fn open<R: ReadTxn>(read: &R, schema: Schema) -> Result<Self>;

    pub fn write_in<W: WriteTxn>(
        &self,
        write: &mut W,
        series: &AddBatch<'_>,
        events: &EventBatch<'_>,
    ) -> Result<PreparedUpdate>;

    pub fn publish(&mut self, receipt: CommitReceipt, prepared: PreparedUpdate);

    pub fn snapshot<R: ReadTxn>(&self, read: R) -> Result<TsdbSnapshot<R>>;

    pub fn maintain_in<W: WriteTxn>(
        &self,
        write: &mut W,
        budget: MaintenanceBudget,
    ) -> Result<PreparedUpdate>;
}

impl<R: ReadTxn> TsdbSnapshot<R> {
    pub fn sum_by_series(&self, q: &SumQuery<'_>, scratch: &mut Scratch) -> Result<SeriesSums>;
    pub fn group_sum(&self, q: &GroupQuery<'_>, scratch: &mut Scratch) -> Result<GroupSums>;
    pub fn events(&self, q: &EventQuery<'_>, visit: impl FnMut(EventRef<'_>) -> ControlFlow<()>) -> Result<()>;
    pub fn catalog(&self) -> &Arc<Catalog>;
}

pub struct SeriesSums {
    pub catalog: Arc<Catalog>,
    pub fields: Vec<Vec<u64>>,
    pub present: Bitmap,
    pub touched: Vec<SeriesId>,
}
```

`CommitReceipt` 和 `PreparedUpdate` 要绑定同一个数据库、同一个事务和同一个目录代号；提交和发布的顺序由流量的存储实现统一把关，普通调用方无法漏掉发布这一步。

### 8.13 基准与验收

- **工具**：criterion 测编码、聚合循环、字典操作、当前桶合并；自定义的 release 程序测打开、混合负载、事务延迟、恢复、磁盘增长和长时间维护。
- **数据形状**：
  - 复现 S/M/L 三个合成库（约 9 万、24 万、60 万个组合；16 万、59 万、254 万条小时用量）。
  - 现有的 `usage_scan_500k_hour_rows`（500 个组合 × 1000 小时，`redb.rs:1503`）保留作低基数用例。
- **补充用例**：
  - 固定复现的组合，与高更替的稀疏组合；
  - 大量回收之后的稀疏 id；
  - 跨小时、跨天、跨整个保留期的单个连接；
  - 长连接集中关闭；
  - 对同一个旧段反复迟到写入；
  - 跨提交和回收持有的并发读者；
  - 饱和值；
  - 保留期变更和时钟回拨；
  - 维护故意落后；
  - 每月 600 万连接的明细写入、翻页与筛选。
- **分项测量**：
  - 打开：引擎打开、目录加载、反查表构建；
  - 读取：扫描、校验、解码、累加、结果生成；
  - 写入：登记、编码、引擎写入、fsync；
  - 维护：折叠耗时、重写字节数、积压量；
  - 内存：目录、字典、头部、查询临时空间、缓存、被快照钉住的数据；
  - 磁盘：实际分配字节和回收情况。
- **对照组**：现格式、整桶 AoS、整桶 SoA、分段基础块、分段 + 增量块、各种可选编码、可选日层级。同样的数据、同样的持久性设置。
- **统计口径**：报告中位数和 p95/p99，不只报预热后的最小值。

### 8.14 迁移

现在的策略是「统计数据可丢弃」：库格式不符就删掉重建，从不迁移（`redb.rs:22`、`:193-205`）。新格式要不要迁移，需要用户决定：

- **沿用可丢弃策略**：最简单，升级时历史统计清零。
- **迁移**（codex 的方案）：
  1. 独占打开旧库，冻结写入；
  2. 写一个带版本号文件名的新库，包含流量的全部表；
  3. 每个旧组合只解码一次，编码标签，映射旧 id；
  4. 按桶顺序把用量流式写成打包块；
  5. 复制会话、活跃连接和明细（明细同时转成事件块），不重放活跃连接的用量；
  6. 逐桶、逐组合校验数值，抽样核对报表输出；
  7. 校验通过后写就绪标记，切换到新文件；
  8. 旧文件按备份策略保留。

  带版本号的文件名还能防止旧版本程序按「格式不符」的规则把新库删掉。

### 8.15 落地顺序

每步一个 PR，前一步的测量决定下一步做不做：

1. **测真实库（已完成，第 1.1 节）。** 测到了每天的连接数、各层每桶的组合数和编码后大小、连接时长和迟到写入的分布、新组合的出现速率、明细大小，以及文件的空闲空间。还没测的有两项：
   - 网关场景的高基数负载，这台机器上没有；
   - flush p99 延迟、内存和并发查询的预算，需要产品给定。
2. **定期整理 redb 文件（独立的小改动，现在就能做）。** 在打开库时，或者空闲页占比超过阈值时，调用 `compact()`。真实库能从 156 MB 降到 89 MB。这一步与新设计无关，换格式之前也有收益。
3. **`nyanpasu-tsdb` 最小完整切片**：
   - 引擎契约、redb 与内存引擎、持久化字典与目录；
   - 时序表：先做整桶写入。真实库的迟到写入最多重写 110 KB，分段放在基准里作对照；
   - 事件表：通用的列类型、块统计、两种保留策略；
   - 调用方事务集成、一致性与性质测试；
   - 基准：S/M/L 合成库和真实库副本，都对比现格式。

   验收标准：报表和明细的结果一致、崩溃后恢复为原子状态、测量上确有提升，而不只是块的微基准更快。真实库上空间收益最大的是事件表，所以它和时序表放在同一个切片里。

4. **流量接入**：
   - 用量、组合、已关闭连接明细都改走 `nyanpasu-tsdb`；
   - 报表计算移出 actor；
   - 用目录列视图替代逐次拼表；
   - 加有界的范围结果缓存。
5. **日志接入**：内核日志改用事件表；按文件分区，按字节预算保留。任务日志要先解决 `nyanpasu-runtime` 子模块的依赖位置。
6. **按测量启用扩展**：

   | 扩展         | 启用条件                                           |
   | ------------ | -------------------------------------------------- |
   | 增量块与折叠 | 旧桶重写的延迟或写放大超出预算                     |
   | 用量块压缩   | 省下的 IO 和缓存超过解码代价                       |
   | 日层级       | 打包和缓存之后，长范围扫描仍然明显                 |
   | 增量窗口     | 重复的范围聚合仍是主要成本                         |
   | 换后端       | 全负载基准证明有优势                               |
   | 自研段文件   | 现有引擎有一个实测的限制，值得为此自己承担恢复机制 |

### 8.16 待决策

- 新格式要迁移，还是沿用「统计可丢弃」（8.14）。
- 降采样保留：小时数据留多久，更早的是否只留日数据（8.8）。
- 网关场景下粗层级要不要归并高基数维度（8.8）。
- 单 crate 加 feature，还是拆出独立的 redb 适配器 crate（8.12）。
- flush 延迟和内存预算的具体数值（真实库测完仍需产品给定）。
- 已关闭连接明细的默认保留期。真实库里它占实际数据的 98%，保留期直接决定库的大小。
- `nyanpasu-tsdb` 放在哪个 workspace，才能让 `nyanpasu-runtime` 子模块里的任务日志也用上（8.5）。

## 9. 未验证与局限

- **没有实测这些数据库。** 没有在本机运行文中这些时序数据库；压缩比全部来自厂商或论文，和数据关系很大。
- **单一来源与未核实的数字：**
  - VictoriaMetrics「每个样本约 0.4 字节」的原文无法访问，未核实。
  - TDengine 的 MINROWS、MAXROWS、KEEP 默认值只来自搜索摘要。
  - TimescaleDB「chunk 约占内存 25%」的规则只在搜索摘录中确认过。
- **文档与代码不一致：**
  - InfluxDB 3 Core 的快照阈值，代码是 600 个 WAL 文件，文档写的是 900 个 / 15 分钟。
  - Prometheus 的乱序缓冲上限，v3.15 代码是 32，2022 年的博客写的是 30。
- **测量范围有限。**
  - 性能测量都在合成库上做。合成库的组合 id 是连续的，没有长连接的迟到写入；第 7 节里涉及长连接的成本都是推算。
  - 第 1.1 节的真实库只有一位用户、一台桌面机、8 天的数据，组合基数低，代表不了网关场景。
  - 编码大小用的是分析程序里的简化编码。位打包的大小是按每列最大位宽算出的估计值，没有实现真正的编解码器。
  - 跨越小时数的统计取「首次看到」到「关闭」之间的小时数，是上界：连接没有流量的小时不会产生写入。
- **redb 只读了源码，没测重写成本曲线。** 大值单独占页、更新时整页重写，这两点来自读源码；不同记录大小下的重写成本曲线没有测。
- **第 8 节是设计，不是测量结果。**
  - 性能目标、段宽 16,384、折叠阈值 4 和 8、事件块 4,096 条，都是待测参数。
  - 明细和用量的压缩后大小是按字段宽度推算的，没有真实数据支撑。
  - 「mihomo 连接 id 是 UUID」没有在 mihomo 源码中核对，所以设计保留了字符串列作退路。
- **codex 分析的范围。** codex 只读本仓库代码和公开文档，没有运行任何程序；它引用的本仓库行号已由主线程抽查核对。它把已关闭连接明细留在流量层，第 8.8 节的事件表是主线程按用户对压缩和规模的关注加入的。
