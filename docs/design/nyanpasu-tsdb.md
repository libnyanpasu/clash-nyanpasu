本文定义 `nyanpasu-tsdb` 的抽象：数据模型、存储端口、写入与成块、块格式、可见性与恢复、查询、保留与维护、资源档位，以及各个使用方怎样映射上来。代码草图只示意形状，不是最终 API。

性能目标不是「当前桌面够用」，而是在**一级平台**上做到最好：桌面、移动端、x86 设备。其中最受限的是 iOS 的 Network Extension，扩展进程和 mihomo 共享 50 MiB 内存，所以内存设计以它为准。64 位的低端设备（例如 aarch64 路由器）列为**二级平台**：参照 Rust 的 tier 2，只保证能编译、能运行，不做测试，也不为它们牺牲一级平台的设计。32 位设备上 mihomo 本身就跑不好，完全不在支持范围内（第 0.2 节）。

## 0. 设计驱动

### 0.1 负载

| 负载               | 形态                                                                          | 实测或预期规模                                                                           |
| ------------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 流量用量（时序）   | 按「层级 × 桶 × 组合」累加 3 个 u64；查询是「一段时间内全部组合求和，再分组」 | 实测桌面机 1,297 个组合，每个小时桶的中位数 58 条；网关场景按合成库估计 9 万–60 万个组合 |
| 已关闭连接（事件） | 只追加，按时间倒序翻页，按维度筛选                                            | 实测每天 0.2 万–4.4 万条；网关每天可达数十万条                                           |
| 内核日志（事件）   | 按会话分代、按序号双向翻页，按级别和关键字筛选，按字节预算保留                | 现有实现：`backend/tauri/src/core/logs/`                                                 |
| 任务日志（事件）   | 按运行 id 分组的日志流                                                        | 现有实现：`nyanpasu-runtime` 子模块的 `nyanpasu-jobs`                                    |
| 流量的辅助状态     | 会话元数据、活跃连接；每次 flush 只改动脏的几条                               | 实测 55 个活跃连接，每个 JSON 约 1.1 KB                                                  |

真实库的细节见调研报告第 1.1 节。

### 0.3 由约束推出的硬规则

1. **内存有显式上界。**
   - 每个缓存都显式设定大小，不继承库的默认值：redb 默认页缓存 1 GiB（`redb-4.4.0/src/db.rs:2045`），流量库现在就没有设置它（`nyanpasu-traffic/src/redb.rs`）。
   - 内存预算以 iOS 扩展为准。
   - 头部、目录、查询各有预算；查询的临时内存是 O(分组数)，不为每个组合或每一行建中间数组（第 8.2 节）。
   - 内存峰值要算上暂存、快照、编码缓冲、恢复时的重建。
2. **写入量最少。** 移动端和 SSD 同样在意写入：iOS 上的 fsync 代价更高，移动设备也在意电量。
   - 每次提交只写增量（日志记录），不重写整个当前桶；
   - 块只写一次，之后不再改写，迟到写入另成增量块；
   - 保留期到了，整个区段删除。
3. **整数编码；SIMD 只走运行时检测的快速路径。**
   - 编码全部是整数运算：差值、varint、位打包。
   - x86_64 和 aarch64 上可以用 SIMD，但只能是运行时检测到之后才走的路径；编译期不要求 AES 等特性。
   - 哈希：整数键用 `rustc-hash`；外部可控的字符串用带种子的 SipHash（标准库）。时序层不需要 gxhash，这样二级平台也不必开启 AES 编译特性。
4. **只支持 64 位小端。**
   - crate 里对非 64 位或大端目标给出 `compile_error!`，把这个前提写成显式的规则。
   - 磁盘格式仍然写明小端，读取时在检查对齐后可以直接把字节当作类型化切片，不必逐个字段解码。
   - 不依赖 mmap：redb 从 0.14.0 起就不再使用 mmap。
   - C 版 zstd 在所有一级平台都能交叉编译（Android NDK、iOS 的 Xcode），可以作为默认编解码器。
5. **任何时刻崩溃都一致。** 每次提交都保持崩溃一致；持久性级别显式指定，并有最大持久丢失间隔；提交结果未知或后端失效时走恢复流程；iOS 上的挂起处理见第 7.5、10.2 节。
6. **格式有版本号。** 所有落盘格式都带版本号，不靠 serde 的默认值来兼容旧数据。postcard 这类二进制格式不自描述（第 6.4 节）。

## 1. 术语

| 术语                       | 含义                                                                                                                                                                                                                       |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 数据集                     | 一份 `Schema` 描述的全部数据：标签字典、组合目录、若干**流**                                                                                                                                                               |
| 流                         | 一个序列层级（例如流量的分钟层、小时层），或一个事件流（例如已关闭连接、内核日志）                                                                                                                                         |
| 区段（extent）             | 一个流在一个时间窗（或一个代）内的数据，是**保留的单位**：保留期到了，整个区段删除。每个流有自己的区段，互不牵连                                                                                                           |
| 日志记录（journal record） | 还没有成块的增量，写在小状态命名空间里，只追加                                                                                                                                                                             |
| 头部（head）               | 某个快照里**仍然存在的全部日志记录**在内存里的视图：打开的序列桶的累加器、事件流的行缓冲。它的大小有上界（第 4.2 节）                                                                                                      |
| 块（chunk）                | 不可变的写入单位：一组列，带块头。分两级：**L0 块**由日志记录成块而来，体积小，不压缩或只做轻量编码；**整理块**由一个区段的全部 L0 块整理而来，按列压缩。L0 块又分基础块和增量块，二者格式和代码路径相同，只在块头标明类型 |
| 有序段（sorted run）       | 键范围互不重叠的一组块。每个 L0 块单独是一个有序段；一轮整理输出的一组块是一个有序段。事件扫描的归并路数等于所涉的有序段数（第 4.3、8.3 节）                                                                               |
| 列块（column block）       | 块里的一列，是**压缩的单位**，未压缩时 16–64 KB，上限 128 KB（第 6.3 节）                                                                                                                                                  |
| 片段（fragment）           | 物理存储单位：块按片段写进存储后端，每段不超过 256 KB（第 3.3 节）                                                                                                                                                         |
| 发布号（publication）      | 每次发布递增的编号；快照、结果缓存都绑定发布号                                                                                                                                                                             |
| 实例号（incarnation）      | 每次打开存储加一；事件序号在同一个实例号内单调（第 8.3 节）                                                                                                                                                                |
| 代（epoch）                | 一个流被清空重建时加一；游标带代，代不符即失效。内核日志的「会话代号」就是它                                                                                                                                               |
| 事件序号（event seq）      | 事件在**进入使用方、对查询可见之前**就分配的序号，在同一个实例号内单调；和键、实例号一起组成事件的全序与游标（第 8.3 节）                                                                                                  |

## 2. 数据模型

一个数据集由一份不可变的 `Schema` 描述：

```rust
pub struct Schema {
    pub version: u32,
    pub labels: Vec<LabelSpec>,       // 字符串维度，每个维度一本字典
    pub series: Option<SeriesSpec>,   // 预聚合的序列
    pub events: Vec<EventStreamSpec>, // 零到多个事件流
}

pub struct SeriesSpec {
    pub dimensions: Vec<LabelId>, // 组成组合键的标签；事件独有的标签不进组合
    pub fields: Vec<FieldSpec>,   // 目前只有 u64、可加、饱和加法
    pub tiers: Vec<TierSpec>,     // 每层：桶宽、区段宽度
    pub fold: Vec<Vec<LabelId>>,  // 折叠阶梯：每一级要换成溢出标记的维度；最后隐含「整个组合溢出」
}

pub struct EventStreamSpec {
    pub name: &'static str,
    pub key: EventKey,              // 时间戳，或单调序号
    pub columns: Vec<ColumnSpec>,
    pub extent: ExtentSpec,         // 按时间窗，或按代再按大小切分
}

/// 保留策略不进 Schema：它由应用层配置，运行时传入（第 9.1 节）。
pub struct RetentionPolicy {
    pub tiers: Vec<Retention>,   // 按层级
    pub streams: Vec<Retention>, // 按事件流
}

/// 两个上限可以同时设置，是「与」的关系：保留的数据必须同时满足两者。
pub struct Retention {
    pub max_age: Option<Duration>, // None 表示按时间永久保留
    pub max_bytes: Option<u64>,    // 按字节预算；None 表示不限
    pub coarsen_after: Option<Duration>, // 仅序列层级：早于它的数据降采样到更粗的层级（日层级扩展项，第 8.4 节）
}

pub enum ColumnType {
    Timestamp,       // i64 毫秒
    Int,             // i64 / u64
    Series,          // 引用目录里的组合
    Label(LabelId),  // 引用某个维度的字典
    Dict,            // 本列自己的低基数字典
    Fixed(u16),      // 定长字节
    Identity,        // 带标记的标识：16 字节 UUID，或回退为文本
    Text,            // 长文本；超过阈值的值走溢出片段（第 6.5 节）
}
```

- **标签**：字典里存能还原原始值的规范值，不存展示用的字符串。流量现在的展示键会丢信息：规则用逗号连接类型和内容，策略链用箭头连接，订阅的「没有」和「空字符串」显示成一样（`nyanpasu-traffic/src/model.rs:44-50`、`:185-200`）。
- **序列字段**：只支持可加的 u64、饱和加法。表结构和块头预留「聚合方式」字段；以后加 last、min、max，就新增块版本和对应的聚合循环，不做插件框架。
- **每个层级和每个事件流各自定义区段，各自执行保留。** 它们的区段互不牵连，到期各删各的。
- **结构进 Schema，保留期由应用层配置。** Schema 只描述数据的结构：维度、字段、桶宽、区段宽度，改了它就要换格式。保留多久是用户和产品的选择，不属于存储层：tsdb 只提供机制（`RetentionPolicy`），具体数值由使用方从应用配置读出，每次维护时传入，改设置不需要重开存储。这与现在的做法一致：流量的保留期来自应用配置 `traffic_retention`（`nyanpasu-config/src/application/traffic.rs`），经端口 `RetentionPolicy` 在每次 flush 时传给存储（`backend/tauri/src/core/traffic/actor.rs:191`）。

数据集之间彼此独立。默认一个使用方一个存储实例：流量的明细必须和用量、和流量的辅助状态在同一个事务里提交；日志可以放在独立的文件里。

## 3. 存储端口

### 3.1 分层

```text
使用方（nyanpasu-traffic、内核日志、任务日志）
    │  定义 Schema，提交批次，发起查询；业务语义留在使用方
    ▼
nyanpasu-tsdb
    ├─ catalog   字典与组合目录
    ├─ head      日志记录的内存视图（有界）
    ├─ chunk     块的构建、编码、校验、读取
    ├─ query     范围规划、下推聚合、事件扫描
    ├─ write     暂存、发布、恢复
    ├─ maintain  成块、合并增量块、保留、空间回收；每次调用都带预算
    └─ profile   资源档位
    │
    ▼  存储端口（由 nyanpasu-tsdb 定义，使用方注入实现）
存储后端：内存（测试）/ redb（第一版）/ 段文件（以后）
```

参照 TiDB 与 TiKV 的分工：上层把逻辑数据编码后交给下层，下层只管存储和事务，详见调研报告第 8.2 节。分布式那一套（Raft、coprocessor 下推）不照搬，聚合循环就在 `nyanpasu-tsdb` 里。

crate 内没有后台线程、定时器、线程池或全局状态。所有维护都是使用方的 actor 发起的同步调用，并带工作量预算，符合 `docs/development/architecture.md` 的规则。

### 3.2 契约

存储端口提供两类状态，二者在同一次提交里原子生效：

- **小而可变的状态**：带命名空间的有序 KV。用来存目录、日志记录、元数据（发布号、批次号、实例号、各流的代、删除水位线），以及使用方的辅助状态。
- **不可变的块**：只写一次，按片段存放，按块删除。

```rust
pub trait Storage: Send + Sync + 'static {
    type Snapshot: StorageRead + Send + 'static;
    type Batch<'s>: StorageWrite where Self: 's;

    fn snapshot(&self) -> Result<Self::Snapshot>;
    fn batch(&self) -> Result<Self::Batch<'_>>;
}

pub trait StorageRead {
    fn get<T>(&self, ns: Ns, key: &[u8], f: impl FnOnce(Option<&[u8]>) -> T) -> Result<T>;
    fn scan(&self, ns: Ns, range: KeyRange<'_>, dir: Direction,
            f: impl FnMut(&[u8], &[u8]) -> ControlFlow<()>) -> Result<()>;
    /// 读一个片段；redb 直接借出页上的字节。
    fn fragment<T>(&self, id: FragmentId, f: impl FnOnce(&[u8]) -> T) -> Result<T>;
}

pub trait StorageWrite: StorageRead {
    fn put(&mut self, ns: Ns, key: &[u8], value: &[u8]) -> Result<()>;
    fn delete(&mut self, ns: Ns, key: &[u8]) -> Result<()>;
    /// 逐个写入片段；整块不必一次性放在内存里。
    fn put_fragment(&mut self, id: FragmentId, bytes: &[u8]) -> Result<()>;
    /// 删除一个块的全部片段：片段键以块号为前缀，后端可以按前缀扫描逐个删除。
    fn delete_chunk(&mut self, chunk: ChunkId) -> Result<()>;
    fn commit(self, durability: Durability) -> Result<CommitReceipt, CommitFailure>;
}

pub enum Durability {
    /// 提交返回时已落盘。
    Durable,
    /// 只保证崩溃一致：崩溃后回到上一个已落盘的提交；要靠后续的 Durable 提交才持久。
    Consistent,
}

pub enum CommitFailure {
    /// 确定没有生效。
    NotApplied(Error),
    /// 可能已经生效，也可能没有；必须走恢复流程（第 7.5 节）。
    Unknown(Error),
}

pub enum ErrorKind {
    /// 只影响这一次操作：输入不合法、预算不足、查询被撤销。后端继续可用。
    Local,
    /// 后端实例已经失效，必须关闭重开（第 7.5 节）。可以出现在任何操作上，包括读取。
    BackendFailed,
    /// 数据校验失败。
    Corrupted,
}
```

- **「这一批是否生效」和「后端是否还能用」是两件事。** `CommitFailure` 只回答前者；任何操作返回的 `ErrorKind::BackendFailed` 回答后者。redb 的读、写、扩容只要有一次 I/O 失败，就把实例标记为失败，此后所有操作都返回 `PreviousIo`，直到关闭重开（`redb-4.4.0/src/tree_store/page_store/cached_file.rs:195-256`）。这可以发生在 `stage` 写片段时（例如扩容遇到磁盘满），也可以发生在查询读取时，根本不经过 `commit`。redb 后端把这类错误映射为 `BackendFailed`。不要把提交前的失败伪装成 `Unknown`。
- **零复制**用回调表达：后端在回调期间持有 redb 的访问守卫，或自己的缓冲区。
- **不要求**的能力：mmap、合并算子、原生范围删除。
- **物理整理**（redb 的 `compact()`）不属于这个接口，见第 9.3 节。

### 3.3 片段

块按片段写进存储，每段不超过 256 KB，键为（块，片段号）：

- redb 里一个不小于页大小的值会单独占一个叶子（`redb-4.4.0/src/tree_store/btree_base.rs:1053`），读取时整个值一起读出。如果整块存成一个值，即使列块只有 16–64 KB，一次读取或写入也会放大到整块。
- **片段 0 是块头**：块头、列目录，以及每个列块所在的位置。查询先读片段 0，再按需读数据片段。
- **列块不跨片段**：列目录里每个列块记（行区间，片段号，片段内偏移，长度），读一列只读它所在的片段。
- **大值跨多个片段**：超过阈值的单个值另开一串连续片段，记（起始片段号，片段数，总长度），这些片段属于同一个块，随块一起删除（第 6.5 节）。
- **块的构建是流式的**：列块一编码好就写出所在片段，不需要把整块放在内存里。片段 0 最后写。

### 3.4 后端

| 后端   | 小状态                        | 块                     | 定位                                               |
| ------ | ----------------------------- | ---------------------- | -------------------------------------------------- |
| 内存   | `BTreeMap`                    | `Vec<u8>`              | 所有一致性测试先在它上面跑通                       |
| redb   | redb 表                       | 片段存成 redb 值       | 第一版，覆盖所有一级平台                           |
| 段文件 | 内存有序表 + 追加写的事务日志 | 每个区段一个或多个文件 | 以后；是否值得做，由 redb 后端实测的每天写入量决定 |

**redb 后端：**

- 必须显式设置缓存大小。redb 默认 1 GiB（`db.rs:2045`）。
- 写时复制的 B 树每次提交至少重写从叶到根的路径，外加系统树和分配器树（来自设计文档，属推断）。所以要实测每次提交实际写入的字节数（第 12 节）。

**段文件后端：** 真要做时，至少要先定下这些规则：

- 事务日志的每条记录带校验和，包含这次提交的全部 KV 变化和清单变化；
- 新文件名要持久化，也就是对目录做 fsync；
- 恢复时截掉日志尾部写坏的记录；
- 没有被任何清单引用的文件视为孤儿；
- 一个文件要等到既没有可恢复的持久根引用它、也没有活着的快照引用它，才能物理删除，否则 `Consistent` 级别的删除回滚后会找不到文件；
- Windows 上文件被打开时不能删除，要单独处理。

这些规则写进一致性测试，再动手实现。

### 3.5 一致性测试

每个后端都要通过：

- 跨命名空间的原子提交与放弃；
- 写入、删除后能读到自己的写入；
- 并发提交期间，跨命名空间的快照保持稳定；
- 字节序、范围边界、前缀隔离、反向扫描；
- 借出值的生命周期安全，扫描可以提前终止；
- 崩溃恢复后得到一个完整的已提交前缀；
- 提交结果未知后，重开数据库能核对批次号；
- 任何操作（含读取、`stage` 写片段）遇到 I/O 失败后，后端报告 `BackendFailed`，重开后可以继续；
- 片段的写入、读取和删除；
- 持久性级别的行为；
- 磁盘满、值损坏、超出后端限制时的失败处理。

## 4. 写入：日志、头部、成块与整理

### 4.1 一次提交写什么

每次提交（流量每 30 s 一次）写这些内容：

- 本批次的**日志记录**：序列增量（每个桶内按组合 id 排好序的数组），以及事件行；
- 目录增量：新标签值、新组合；
- 使用方脏了的辅助状态；
- 元数据：批次号、发布号；
- 可能还有：本批次触发的**成块**（第 4.2 节）。

普通情况下，提交不重写整个当前桶，也不写列式块，写入量约等于增量本身。

### 4.2 头部、日志与成块

**不变量：头部 = 某个快照里仍然存在的全部日志记录。** 日志记录离开头部只有两条路，二者都在一个事务里完成：

- 被**成块**：写入块，并删除**恰好**被吸收的那些日志记录；
- 被**保留期删除**：随所在区段一起删除。

所以同一个增量在任何快照里，要么还是日志记录（出现在头部），要么已经在某个块里，不会两边都有，也不会两边都没有。这里不用全局的「已成块序号」：不同来源可以各自成块，比如桶 A 成块时桶 B 仍然打开，前缀水位线描述不了这种状态。

头部在内存里的结构：

- **序列**：每个打开的（层级，桶）一个累加器，只为这个桶里出现过的组合分配，SoA 布局、按组合 id 排序；
- **事件**：每个事件流一个行缓冲。

头部有硬上界，由档位给出（第 10.1 节）。满足下面的条件时，就把对应的日志记录成块：

| 来源     | 成块条件                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| 序列桶   | 桶结束后再静默 Q 时间（默认一个桶宽）；或者这个桶的累加器超过大小上限                                      |
| 事件流   | 缓冲满 4,096 行或 64 KB；或者缓冲里最老的一行超过 T 时间（默认 1 小时）                                    |
| 内存压力 | `stage` 先按本批次的大小**预留**头部空间；预留不下时，就在**同一个提交里**先把最大的来源成块，再写入本批次 |

**日志字节数单独设上限。** 头部的内存上界约束不了重启时要回放的日志量：同一个（层级，桶，组合）每 30 s 更新一次，在累加器里只占一项，在日志里却留下一条又一条记录。例如一个小时里 1,000 个组合每 30 s 更新一次，累加器约 28 KB，日志记录却约 3.4 MB。所以：

- 存储里尚未成块的日志记录总字节数，另设一个上限（档位给出）；
- 接近上限时，先**折叠**：把同一个桶的多条日志记录替换成一条汇总记录，与成块一样在一个事务里删除恰好被替换的记录。折叠不够时，再成块；
- 每次提交后检查两个上限（头部内存、日志字节），重启回放量因此不超过日志字节上限。

**批次大小由使用方约束。** 一个批次是一个事务，tsdb 不能把它拆成多个事务：流量的增量与对应的累计计数基线必须原子地一起提交。所以：

- 档位给出单批次的字节上限；使用方在待提交的数据接近上限时**提前 flush**，而不是把一个批次拆开。流量的会话元数据、已关闭连接的辅助删除、序列增量和关闭事件必须一起提交，提前 flush 不破坏基线的原子性。活跃连接的辅助记录是例外：每条记录自带累计计数和自己的桶，其用量在连接关闭前不进入序列；首个事务容纳尽可能多的活跃记录，其余由使用方在后续事务中提交，每个事务都受单批次上限约束并使用下一个 batch_id。事务之间崩溃，只会使部分活跃记录落后一次 flush；恢复后下一次采样从这些计数计算增量，不会重复计数；
- 批次在上限之内、但头部预留不下时，这个批次的序列增量和事件行直接在这次提交里成块，不进头部；成块的输出同样受块大小上限约束（第 4.3 节）；
- 超过上限的批次返回 `Local` 错误，属于使用方的程序错误。

### 4.3 两级块与迟到写入

日志记录成块得到 **L0 块**：序列按（桶，组合 id 区间）成块，事件按缓冲成块。L0 块不压缩，只做轻量编码。

区段结束、再静默一段时间后（序列：区段结束后 Q；事件：区段结束后 T），维护把这个区段的全部 L0 块**整理**成一个整理块：

- 同一列跨多个桶放在一起，切成 16–64 KB 的列块，再按第 6.3 节的规则决定压不压缩；
- 整理在一个事务里写新块、删除旧的 L0 块、递增发布号；
- **块有大小上限**：一个块最多 M 行、最多 B 字节（默认 65,536 行、4 MB），块头和列目录也因此有上限，片段 0 放得下。块的构建在**任何**一个上限（行数、字节数、片段 0 的目录大小）将要超出时就结束当前块、开始下一块。所以一个桶可以是多个块，按组合 id 区间切分（10 万个组合的桶就是两块）；一个区段整理后也可以是多个整理块，事件区段的块数没有上限（同一个组合可以有任意多事件）。
- **整理的工作量有上界**：一轮整理的输入不超过 F 个块、合计不超过 I 字节（默认 64 个、16 MB），已有的整理块重新参与整理时也计入。超出时分几轮做，每轮都是完整的原子替换。

**迟到写入**（序列桶已经成块后又来的增量，典型情况是长连接关闭）仍然先写成日志记录，成块时得到这个桶的 **L0 增量块**，不改写已有的块：

- **读取**：永远是「整理块 + L0 基础块 + L0 增量块 + 头部」，正确性不依赖整理是否完成，与 SummingMergeTree 的规则相同。
- **合并**：区段整理之前，增量块和基础块一起参与整理。整理已经做过的区段，一个桶的增量块超过 4 个时，只把这些**增量块合成一个增量块**，不动整理块：整理块跨多个桶，把迟到增量并进去就得重写其他桶的行。
- **替换规则**：任何一轮整理或合并，被删除的旧块里所有仍有效的行，都必须完整地出现在新块里，再在同一个事务里删除旧块。不允许「只取出旧块里的一个桶」。
- **只做加法**：流量的迟到写入只做加法（调研报告第 7.1 节），所以增量块不需要负数。
- **裁剪按块进行**：每个块（包括增量块）都有自己的块头统计，查询逐块判断能否跳过。块头里的字段总和只代表这一块，「整桶总和」要把相关的所有块相加。

**事件流**按键追加。键可能乱序到达（例如连接的关闭时间），所以块之间的键范围可以重叠，扫描时按键归并，归并路数等于所涉的**有序段**数（第 1 节）。只统计 L0 块不够：多批迟到事件都覆盖同一个时间窗时，每轮整理各自产出一个有序段，它们之间仍然重叠，L0 降到 0 时归并路数照样可以很大。

第一版**不承诺归并路数的硬上界**，而是：

- 维护按有序段计数，不只看 L0。一个区段的有序段超过 R 个（默认 8）时，维护从最小的有序段开始合并，每轮输入仍受 F、I 约束；
- 归并需要的内存在查询准入时按路数预留（第 7.4 节）。路数超出预算时，查询返回 `BudgetExceeded`，不会悄悄超用内存。

要硬上界，就得引入 LSM 那一套分层归并：中间结果的发布、部分替换的键范围、写入方为维护让出多少吞吐。现有使用方用不着：流量的关闭事件按观测时间到达，只在 pending 的 30 s 窗口内轻微乱序，区段整理（区段结束后 T）之后基本不再有迟到事件；内核日志以单调序号为键，根本不重叠。真实负载里出现大量有序段时，再按实测决定。

**积压**：维护跟不上时（L0 块、增量块或有序段超过档位上限），下一次提交在同一个事务里先做最紧迫的一轮整理，把代价显式地转到写入上。这只保证积压时每次提交都附带一轮受 F、I 约束的维护，不保证积压一定收敛：新输入持续超过每轮的处理量时，积压会增长，表现为上面的 `BudgetExceeded` 和写入变慢，并计数上报。

### 4.4 写入接口

```rust
let mut batch = storage.batch()?;
let prepared = tsdb.stage(&mut batch, &Input {
    series: &usage_increments,         // (tier, bucket, labels, fields)
    events: &[("closed", &closed_rows)],
    aux: &aux_changes,                 // 使用方的辅助状态，写进同一个事务
    batch_id,                          // 必须大于最后一次已提交的批次号
})?;
// 登记待发布版本 → 提交（不持锁）→ 发布；提交失败则撤销登记。
let receipt = tsdb.commit(batch, prepared, durability)?;
```

- **`stage` 不修改任何共享状态。** 新标签、新组合、头部变化、成块结果、发布号都只写进 `prepared` 和事务里。出错时整个批次放弃，共享状态保持原样。
- **`stage` 检查批次号**：批次号必须大于本写事务读到的 `last_committed_batch_id`，防止同一批增量被计入两次。这里的「已提交」包括成功的 `Consistent` 提交：最后一次 `Durable` 是 10、批次 11 已经以 `Consistent` 提交成功时，再提交 11 必须被拒绝。每次提交都把批次号写进元数据，所以写事务读到的就是这个值。
- **`commit` 负责登记与发布**（第 7.1 节）。发布不会失败：它需要的内存在 `stage` 里就分配好了，发布只是一次所有权交换。提交返回 `NotApplied` 时撤销登记；返回 `Unknown` 时走恢复流程（第 7.5 节）。`prepared` 被丢弃时也会自动撤销登记。
- **`prepared`** 绑定同一个存储实例、同一个事务、同一个发布号；不匹配时直接 panic，因为这是程序错误。

## 5. 字典与目录

### 5.1 结构

在 iOS 扩展里目录也要很小，所以不用 `HashMap<Arc<str>, u32>` 这种每项带几十字节开销的结构：

- **标签值**：每个维度一块连续的字符串堆加偏移数组；查找表是只存 u32 下标的开放寻址哈希表，比较键时回到堆里取字符串。每个值额外占约 8–12 B。
- **组合**：每个维度一列标签编号，按组合 id 索引。列宽按这个维度**目前用到的最大编号**在 u8、u16、u32 之间选择，不按存活的取值数选：回收之后，存活的值可能少于 256 个，但某个仍在用的编号可能大于 255。越界时整列加宽，加宽时的复制计入目录预算。
- **反查**（标签编号组 → 组合 id）：只存组合 id 的哈希表，持久化在存储里，写入路径用它查找。
- **持久化**：目录的增量随每次提交写入，定期合并成目录块。打开数据库时读的是定长的数字记录，每个不同的字符串只读一次，不再逐个解析组合的 JSON。

第一版目录整个常驻内存。真实库只有约 1,300 个组合；60 万个组合按估算约 10–18 MB。按页加载是扩展项（第 13 节）。

**目录预算按峰值计，不按稳态计。** 列宽加宽、字符串堆扩容、哈希表扩容时，新旧两份短暂共存；回收留下的空洞也占空间。这些峰值在 `stage` 里先从目录预算预留，预留不下就走溢出（第 5.2 节）。上面这几种紧凑结构对外只是同一个目录接口；实施时可以先用简单的表示，等基准量出它在移动端档位上确实超预算、并且量出哪一部分最大，再逐项换成紧凑结构。契约（字节预算、溢出、id 复用条件）不随表示变化。

### 5.2 预算与溢出

目录的上限按**字节**计，不按组合数计：

- **标签值保持完整。** 字典里存的是能还原原始维度的规范值（第 2 节），不截断、不哈希；长值和短值一样计入目录预算。
- **目录总字节数有上限**，由档位给出。
- **溢出组合在建表时就预留。** 每个维度预留编号 0 作为「溢出」标记。它和用户的字面值 `"(other)"` 不同，后者照常编号。每个层级还预留一个溢出组合，其所有维度都是溢出标记。预留的这些项不占用运行时的预算。
- **超出上限时，按折叠阶梯降级**，并计数上报。写入不会因此失败。如果改成拒绝写入，流量会把整批放回去重试，被拒期间还会丢弃新帧（`nyanpasu-traffic/src/accounting.rs:119`、`:236-244`），等于永远卡住。
- **折叠阶梯由使用方在 `SeriesSpec` 里声明**，是一个固定的顺序，不由 tsdb 按基数动态选择（动态选择会让同一份输入在不同时刻落进不同的维度组合，结果无法解释）。新组合放不进目录时：
  1. 把阶梯第一级列出的维度换成溢出标记，查找或登记这个折叠后的组合；
  2. 仍然放不下时，进入下一级；
  3. 最后一级永远是整个组合溢出，它在建表时就预留了，所以一定能写入。

  流量的阶梯是两级：先折叠目标，再整个组合溢出（第 14.1 节）。折叠后的组合也是普通的组合，同样占目录预算，同样按第 5.3 节回收。

- **候选值不泄漏。** 判定溢出之前登记的候选标签值、候选组合，只存在于本批次的 `prepared` 里；判定溢出后丢弃，不进入目录。

这是有损的：被折叠的维度只保留在溢出标记下的总量里。一个值的流量，一部分可能记在完整的组合里（预算满之前），一部分记在折叠的组合里（预算满之后），所以按被折叠维度筛选或排行时会少算后者。查询结果因此带一个「涉及折叠数据」的标记（只要扫描到任何含溢出标记的组合就置位），由使用方显示出来。总量和未折叠的维度仍然精确。哪些情况会走到这一步，由档位预算决定，需要实测。

### 5.3 id 复用与回收

组合 id 用 u32，复用最小的空闲 id（用户已选定）。复用的安全条件：

1. **只看当前提交仍然可达的引用。** 一个组合只有在**所有**引用它的地方都从当前已提交的状态里删除之后才能回收：
   - 所有序列层级的整理块、L0 块、增量块；
   - 所有含 `Series` 列的事件流；
   - 日志记录；
   - 使用方钉住的组合。tsdb 看不懂不透明的辅助状态，所以辅助状态里引用的组合（例如流量的活跃连接）由使用方显式钉住：`pin` / `unpin` 是批次里的操作，和辅助状态的修改写进同一个事务；钉住集合持久化在 tsdb 自己的命名空间里，恢复时随其他状态一起读出。

   「删除」指从当前已提交的清单和日志里不可达，不要求从 redb 文件或更早的 MVCC 版本里擦除。逻辑上过期、但所在区段还没删的块，仍然算作引用。

2. **标签值同理。** 一个标签值只有在没有任何组合、也没有任何 `Label` 列引用它时，才能回收。
3. **删除水位线只增不减。** 每个流持久化一个「已删除到」的水位线，读取时按「当前截止点」和「水位线」中较晚的那个过滤。这样，用户调大保留期或时钟回拨时，已经过期的数据也不会以新组合的身份重新出现。
4. **一个事务完成回收。** 删除引用、删除反查项、加入空闲 id、释放标签值，都在同一个事务里。
5. **旧快照不受影响。** 快照持有它那一版的目录；依赖目录的东西（结果缓存、对外暴露的组合 id 句柄）绑定目录的发布号。事件游标不依赖目录，绑定流实例号和逻辑位置（第 8.3 节）。复用 id 不影响已经拿到快照的查询。

为什么不改成 id 单调递增、永不复用（antigravity 的建议）：在上面的条件下，复用是安全的（codex 第 2 轮的评估结论相同）。好处是 id 保持紧凑，按下标的累加数组和目录列都不会随运行时间变得稀疏。这只是一种倾向，不是保证：一个仍然存活的大 id 也会在它下面留下空洞。所以查询不依赖 id 稠密，而是按分组聚合（第 8.2 节）。

## 6. 块、编码与压缩

### 6.1 块格式

```text
片段 0（块头）：magic | format_version | schema_fingerprint | 块类型（L0 基础 / L0 增量 / 整理） | row_count | 时间或桶范围 | 片段数 | 块头校验和
列目录：每个列块一项：列号 | 行区间 | encoding | compression | 片段号 | 片段内偏移 | 长度 | 解压后长度 | stats
大值目录：每个大值一项：起始片段号 | 片段数 | 总长度
数据片段 1..n：列块与大值，每个片段带校验和
```

- **统计信息**：整数列记最小、最大值；低基数列记取值位图；序列块记每个字段的总和。查询靠这些整块跳过。
- **校验**：XXH3 或 CRC32C；运行时检测到硬件指令时用硬件实现。
- **对齐**：块内列偏移按 8 字节对齐。所有受支持平台都是小端（第 0.3 节第 4 条），所以检查过地址对齐后，定宽列直接用 `zerocopy` 的不对齐小端类型（例如 `U64<LittleEndian>`）当切片读。redb 值在页里的起始地址通常不按 8 字节对齐，用这类类型就不需要对齐，也不用退回逐个读取，在 x86_64 和 aarch64 上都编译成普通的不对齐加载。不手写 `unsafe` 转换。
- **压缩标记**：每个列块带 1 字节的编解码器标记，「原样存放」也是一种取值。新旧编解码器可以共存，以后换默认值也不必重写旧数据。Arrow IPC 用长度 −1 表示「未压缩」，Prometheus 的 WAL 也逐条标记，都是同样的做法。

### 6.2 列编码

| 编码                         | 适用                   |
| ---------------------------- | ---------------------- |
| 原样定宽                     | 随机值，例如 UUID      |
| 常量                         | 整列同一个值           |
| 差值 / 差值的差值，加 varint | 时间戳、有序 id        |
| 帧参考 + 位打包              | 范围窄的整数           |
| 字典                         | 低基数字符串、标签编号 |
| 文本                         | 偏移数组 + 字符串堆    |

这些都是整数运算。位打包和差值解码在 x86_64 和 aarch64 上可以有 SIMD 快速路径，但必须是运行时检测到之后才走。

### 6.3 压缩的粒度与级别

在真实库上实测（i9 单线程；调研报告第 1.1 节为同一份数据）：

| 方案                                                 | 已关闭连接，每条大小 |
| ---------------------------------------------------- | -------------------- |
| JSON 每条单独 zstd，不带字典                         | 398 B                |
| JSON 每条单独 zstd，带训练字典（内核日志现在的做法） | 89 B                 |
| JSON 按行块 zstd（≥1,024 条）                        | 44 B                 |
| 列式 + 轻量编码，不用 zstd                           | 30.3 B               |
| 列式，每 4,096 条一块，每列单独 zstd                 | 25.0 B               |
| 列式，整列 zstd                                      | 24.9 B               |

| 方案                | 分钟用量，每条大小    | 小时用量，每条大小 |
| ------------------- | --------------------- | ------------------ |
| 轻量编码            | 6.1 B                 | 7.2 B              |
| 每个桶单独 zstd     | 6.6–8.1 B（反而变大） | 7.2–7.5 B          |
| 每列跨 24 个桶 zstd | 4.4 B                 | 6.1 B              |
| 整列 zstd           | 3.5 B                 | 5.9 B              |

zstd 级别对已关闭连接的影响：级别 -5 是 27.2 B（解压快约 3 倍），级别 1 是 25.2 B，级别 3 是 25.0 B，级别 19 是 24.7 B。

**各数据库在什么粒度上压缩**（专项调研，出处见文末）：

| 系统                   | 压缩单位             | 单位大小（未压缩）                 | 默认算法                               | 为什么                                                   |
| ---------------------- | -------------------- | ---------------------------------- | -------------------------------------- | -------------------------------------------------------- |
| PostgreSQL TOAST       | 单个字段值           | 只处理超过约 2 KB 的行             | pglz；14 起可选 lz4；zstd 至今只是提案 | 要支持原地更新、按值访问；代价是压缩率差，小行根本不压缩 |
| InnoDB `COMPRESSED`    | 16 KB 页             | 16 KB                              | zlib                                   | 页还要被改写，带来反复重压缩和页分裂的开销               |
| RocksDB / MyRocks      | SST 数据块           | 4 KB（MyRocks 16 KB）              | 上层 LZ4，最底层 zstd                  | 支持点查；冷数据压得更狠；字典只对 ≤ 16 KB 的块有用      |
| ClickHouse             | 每列的压缩块         | 64 KB–1 MB                         | LZ4，或 zstd 级别 1                    | 按 granule 跳过数据；先做专用编码，再接通用压缩          |
| Parquet（arrow-rs）    | 列块里的页           | 1 MB                               | 不压缩，或 zstd 级别 1                 | 页是最小的编码单位                                       |
| DuckDB                 | 列段                 | 256 KB 块                          | 轻量编码；只对 ≥ 4 KB 的字符串用 zstd  | 解压慢，所以优先用轻量编码                               |
| VictoriaMetrics        | 块内的一列           | ≤ 8,192 行                         | 差值编码后 zstd 级别 1–5               | 小于 128 B，或省不到 10%，就不压缩                       |
| TimescaleDB            | 1,000 行的列数组     | ≤ 1,000 个值                       | 专用编码；只有数组和字典列再走 TOAST   | 只对专用编码后仍有冗余的列做通用压缩                     |
| Loki                   | 块（chunk 内）       | 约 256 KB                          | gzip                                   | 先写入不压缩的头块，满了再压缩                           |
| Lucene / Elasticsearch | 多文档的块，分成子块 | 8–48 KB 子块；ES 为 14 KB / 240 KB | LZ4；DEFLATE 或 zstd                   | 块内共享上下文；读一条只解压一个子块                     |

几乎所有系统都只压缩一个**有界的单位**（4 KB–1 MB），并且是这次读取必须解码的最小单位。整列或整个区段一起压缩的做法只用在导出和备份上，例如 pg_dump。原因有三：这样会破坏随机访问，解压内存随窗口增长，也和追加写入冲突。

**zstd 自身的指引**：数据越小越难压缩。字典的收益主要在前几 KB：zstd README 上，约 1 KB 的记录不带字典压缩比是 2.86，带字典是 9.92。DuckDB 公布的数据显示，zstd 的压缩比在 16 KB 时是 2.21，64 KB 时是 2.41，1 MB 时是 2.73；而 1–4 KB 时下降得很快。

由此定出的规则：

1. **先做轻量编码。** 规范化（只存组合 id）加列式编码拿到了绝大部分收益，zstd 只在此之上再压一层。TimescaleDB 和 DuckDB 也是先用专用编码，再对剩下仍有冗余的部分做通用压缩。
2. **压缩只发生在区段整理时，单位是「整理块里一列的一个列块」，未压缩时约 16–64 KB，上限 128 KB。** L0 块不压缩（第 4.3 节）。
   - 整理时，同一列跨这个区段的所有桶放在一起。一个区段的一列不足 16 KB 时，整列就是一个列块。真实库正是这种情况：一天的小时用量只有千余条，每列几 KB。
   - 超过上限就切成多个列块，保留随机访问能力。
   - 不按桶压缩：真实库的桶太小，按桶压缩反而变大。也不按记录压缩。
   - 列块小于约 4 KB 时只做轻量编码。不把几列合成一个压缩单位：列目录描述不了各列在同一个解压缓冲里的位置，收益也小。
3. **按列块决定压不压。** 少于 128 B 不压缩；只有「压缩后的总大小（含帧头）≤ 0.9 × 轻量编码后的大小」时才保留压缩结果，否则原样存放。这是 VictoriaMetrics 的规则。随机列（UUID）直接原样存放。
4. **级别低。** 整理时用 zstd 级别 1；ClickHouse、Parquet（arrow-rs）、InfluxDB 3 的默认值也都是级别 1。级别 19 在 1 MB 输入上需要约 18 MB 的压缩上下文，不在设备上使用。
5. **用一次性 API，并复用上下文。** 用带显式上下文的一次性接口（`ZSTD_compressCCtx` / `ZSTD_decompressDCtx`，在 Rust 里是 `zstd::bulk::Compressor` / `Decompressor`），并给出内容大小，让窗口跟着块大小走：64 KB 的块，窗口也只有 64 KB。上下文归调用方所有：写入方持有一个压缩上下文，每个查询的临时空间里放一个解压上下文；不用线程局部的全局状态。解压上下文约 94 KB（zstd 1.5.7 实测），计入内存峰值。
6. **热数据不压缩。** 头部和日志记录保持原样，不要每次追加都重新压缩。InnoDB 的修改日志和压缩失败分裂就是反例。
7. **列块不用训练字典。** 16–64 KB 的列块自带足够的上下文；低基数字符串已经字典编码，跨记录的冗余基本消除了。训练字典只留给凑不成块、只能单条落盘的行式文本，例如日志尾部。真实库上，能攒成块时按块压缩更好：44 B 对 89 B。真要用字典时：
   - 每列或每种类型一本，大小 16–32 KB；
   - 记录或块里存字典 id；
   - 被引用的字典永不删除。
8. **编解码器。** 默认用 C 版 zstd（`zstd` crate）：所有一级平台都能交叉编译，内核日志也已经在用它（`backend/tauri/src/core/logs/codec.rs`）。LZ4 作为备选，只有实测发现解压成为瓶颈时才启用；x86 上它的解压速度约为 zstd 的 2.5 倍，压缩比低约 27%。

### 6.4 可变小记录的格式

使用方的辅助状态，例如活跃连接、会话元数据，每次 flush 都会改写，不进列块。它们用「版本号 + 二进制」格式。真实库实测：postcard 存完整的已关闭连接记录是 222 B，JSON 是 528 B；组合表 postcard 是 189 B，JSON 是 374 B。改写的数据量减半，写入量和 CPU 都更省。代价是 postcard 不自描述：字段的增删要靠版本号显式迁移，不能像现在这样靠 `#[serde(default)]`。

### 6.5 大值与解码校验

- **大值**：文本值超过 16 KB 时，不放进列块，而是在所属块里另开一串连续的数据片段（每段 ≤ 256 KB），列里只存它在大值目录里的下标；大值目录记（起始片段号，片段数，总长度）（第 3.3 节）。内核日志单条最大约 1 MiB（`backend/tauri/src/core/logs/model.rs:4`），会占 4–5 个片段。大值随所属的块一起删除。
- **解码前先校验**：
  - 块头和列目录里的长度、偏移、行数，都和片段的实际长度、**格式上限**比对。格式上限是写进格式版本的常量（片段 ≤ 256 KB、列块解压后 ≤ 128 KB、块 ≤ M 行），不随档位变化；档位的预算只用于准入，不用来判断损坏，否则换一个更小的档位，原本合法的块就会被误判为损坏；
  - 解压前检查声明的解压后大小不超过上限。zstd 明确说明帧里的内容大小不可信；
  - 组合 id、标签编号都要在目录范围内；
  - 块头和每个片段各带校验和，校验失败返回 `Corrupted`，不 panic；
  - 读块时先只读片段 0，列目录和大值目录的大小也受上限约束；
  - 只有通过这些检查之后，才做类型化切片的转换。

## 7. 快照、可见性与恢复

### 7.1 快照与发布

快照由三部分组成：存储快照、目录快照、头部快照。目录和头部都是不可变的，按发布号共享；头部有上界，复制它的成本也有上界。

**发布门不跨 fsync。** 如果写入方从提交一直到发布都持有锁，iOS 上的 `F_FULLFSYNC` 会让所有查询等上几十到几百毫秒。改用一个**版本登记表**（读写锁保护，持锁时间都很短）：

- **写入方**（`tsdb.commit`）：
  1. 写锁内：把 `stage` 准备好的目录和头部登记为「待发布 P+1」（P+1 已写进事务的元数据）；
  2. 不持锁：提交，包括 fsync；
  3. 写锁内：成功则把 P+1 设为当前版本；`NotApplied` 则撤销登记；
  4. 旧版本在没有快照引用后释放。
- **读取方**（捕获快照）：在**读锁内**完成两步：打开存储快照并读出已提交的发布号 Q；按 Q 取出并钉住对应的目录和头部。持读锁期间写入方不能发布或释放版本，而 Q 只可能是当前版本，或者已登记的待发布版本，所以一定取得到。读锁里只有打开存储快照这一个存储操作，不含 fsync。
- **恢复时**（第 7.5 节）清空登记表和结果缓存，从恢复状态重新登记。

快照因此不会出现「看到了新块，却拿着旧头部」，反过来也不会。

**为什么不靠使用方的 actor 串行化。** 一种更简单的做法是：使用方的 actor 串行地执行写入和快照捕获，tsdb 就不需要登记表。不这样做，是因为它把 tsdb 的一致性契约绑在了某个使用方的线程模型上：

- tsdb 是通用的存储层，单独做基准。快照捕获与发布的一致性是它自己的契约，不能要求每个使用方都用一个 actor 同时负责写入和捕获；
- 内核日志这类使用方，内存里没有需要和快照配对的业务状态，查询只需要 tsdb 的快照。登记表让这类查询的捕获不必排在 fsync 后面；
- 登记表本身很小：一把读写锁、当前版本和至多一个待发布版本。

这个选择不影响使用方怎样处理**自己的**内存状态。流量的 pending 和活跃行在它自己的 actor 里，捕获它们仍要经过这个 actor，会排在正在进行的提交后面（第 11.1 节）。要消除这段等待，是流量自己发布内存状态的问题，与 tsdb 无关。

**新旧版本共享未改动的部分。** 目录和头部用按页共享的不可变结构：P+1 只复制改动过的页。所以新旧两个版本同时存在时，多出来的内存只是改动的页，它计入暂存预算；仍被快照引用的旧版本计入查询预算（第 7.4 节）。

### 7.2 恰好一次

可见性完全由第 4.2 节的不变量保证：头部等于快照里仍然存在的日志记录；成块、整理、保留都在同一个事务里删除恰好被吸收或过期的日志记录和旧块。查询把「块」和「头部」相加，同一个增量只会被计入一次。

### 7.3 查询结果缓存

- **缓存的是什么**：「块」那部分的查询结果。头部、pending 数据和活跃数据永远实时计算。
- **缓存键**：存储实例号、规范化后的查询本身（时间范围、层级、全部分组请求及其筛选、字段）、生效的保留截止点、目录发布号，以及所涉区段的版本。任何成块、整理、合并或删除，都会递增所涉区段的版本。
- **为什么要带实例号**：`Consistent` 提交在恢复时可能被回滚，之后发布号和区段版本会重新出现，但内容不同。实例号每次打开都会持久地加一，所以不同实例号下的同一个发布号不会混淆。缓存只接受当前实例号的写入：恢复前就在运行的查询，结果算完后也不会写进缓存。对外暴露的、绑定发布号的句柄同样带实例号。
- **预算**：缓存的内存计入档位预算，超出时按最近最少使用淘汰。

### 7.4 内存预算的统一记账

档位预算（第 10.1 节）是一个**总**预算，所有分项都从中预留：头部、目录、redb 缓存、暂存、编码缓冲，以及**仍被快照引用的旧版本和正在运行的查询**。

- **暂存**：`stage` 先预留本批次需要的空间；预留不下时，就在同一个提交里成块（第 4.2 节）。
- **查询**：查询在开始前，从一个由使用方 client 持有的共享预算里申请空间，申请不到就返回 `BudgetExceeded`。这是在 client 边界上的准入控制，不在 actor 内部另建调度。

几项容易漏算的分配：

- **后端在缓存之外的开销。** redb 的 `set_cache_size` 只限制页缓存；分配器状态、事务的页跟踪，以及非持久提交累积的页集合（`UnpersistedState`，`redb-4.4.0/src/tree_store/page_store/page_manager.rs:384`）都在缓存之外。「每 5 min 一次 `Durable`」只限制了时间，没有限制这段时间里累积了多少页。所以：
  - 档位单列一项「后端固定开销」，由基准实测后定值；
  - 单个事务的写入量受批次上限（第 4.2 节）和维护的 F、I 约束；
  - 上次 `Durable` 之后累计写入的字节数超过档位阈值时，提前做一次 `Durable`，不等时间间隔。
- **旧快照的保留成本在捕获之后才出现。** 快照刚捕获时和当前版本共享所有页；之后的写入逐步替换头部和目录的页，旧快照最终可能独占它们。拒绝新查询释放不了旧快照手里的页，成块也释放不了旧头部。但一个快照能独占的，只可能是**捕获时已经存在**的页，所以它的保留成本不超过捕获时头部与目录的实际字节数。做法：捕获时按这两个实际字节数（不是档位上限）预留，预留不下就返回 `BudgetExceeded`；快照丢弃时归还。这是保守的重复计算（与当前版本共享的页也算了一次），换来确定的上界。
- **归并的输入侧。** 流式输出解决不了输入侧：如果每一路都保留一个完整的解码列块，64 路 × 128 KB 就是 8 MiB。查询准入时按下式预留：

  ```text
  M_merge = 路数 × (每路解码缓冲 + 每路片段缓冲) + 归并堆 + 输出列 + 解压上下文
  ```

  其中「每路片段缓冲」按 redb 访问守卫所持有的值大小计（片段 ≤ 256 KB）。路数来自规划阶段统计的有序段数（第 4.3 节）。单轮维护同样按这个式子预留，F 和 I 只限制输入，不限制内存。

- **恢复时新旧状态共存。** 关闭再重开之后，旧查询可能还持有旧目录、旧头部和解码缓冲。恢复流程先撤销所有快照，**等它们的预留全部归还**之后，再重建目录和头部（第 7.5 节）。这个等待是有界的：快照只在一次查询调用期间存在，不跨调用持有；查询在列块、行批的边界检查撤销标记，关闭后的下一次读取也会立刻失败。

### 7.5 提交结果未知或后端失效时的恢复

redb 的语义：提交报 `TransactionPoisoned` 时事务已回滚，可以继续写；报其他错误时，事务可能已经持久化，数据库拒绝新的写事务，必须关闭再打开（`redb-4.4.0/src/transactions.rs:1745-1753`）。另外，任何一次 I/O 失败都会让实例此后一直返回 `PreviousIo`（第 3.2 节），这不一定经过提交。

| 情况                                                   | 处理                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------- |
| `Local`：输入不合法、预算不足、查询被撤销              | 结束这一次操作，后端继续使用                               |
| 提交返回 `NotApplied`                                  | 放弃这一批，撤销登记，后端继续使用                         |
| 提交返回 `Unknown`                                     | 走下面的恢复流程                                           |
| 任何操作返回 `BackendFailed`（含 `stage`、维护、查询） | 走下面的恢复流程                                           |
| 重开失败，或重开后校验确认损坏                         | 进入「不可用」状态，明确报告给宿主；不假定反复重开就能修好 |

**查询发现后端失效时**：查询在 actor 外执行，它把错误返回给调用方的同时，在 tsdb 的共享句柄上置一个「需要重开」标记。之后所有者的任何写入或维护调用都立即返回 `BackendFailed`，所有者据此走恢复流程，不会继续持有一个失效的实例。

**不可用之后**：所有者在宿主下一次按计划提交时（流量是 30 s 一次）再尝试一次重开，不另设重试循环。例如磁盘满导致失效，用户清出空间之后，下一个周期就能恢复。

恢复流程按「进程重启」处理：

1. 停止接受新的写入和快照，撤销所有快照；
2. 关闭存储，再重新打开。关闭靠所有者丢弃 `Database`：redb 规定这时会释放文件锁，所有未结束的读事务此后都返回 `DatabaseClosed`（`redb-4.4.0/src/db.rs:718-727`）。前提是快照只持有读事务，不持有 `Database` 本身；写事务只由所有者使用，关闭前已经结束。注意关闭本身也有写入：实例没有失效时，redb 的 `Drop` 会提交分配器状态、收缩文件、写关闭头并刷盘两次（`db.rs:1885-1930`、`page_manager.rs:2373-2398`）；实例已经失效时跳过这些写入；
3. 等旧快照的内存预留全部归还（第 7.4 节）；
4. 读出恢复后的状态：批次号、发布号、目录、日志记录（重建头部），以及**使用方的辅助状态**；
5. **使用方从同一份恢复状态重建自己的内存状态**。对流量来说，就是像冷启动一样，从恢复出的会话元数据和活跃连接重建 `Session`（`nyanpasu-traffic/src/accounting.rs:104` 的恢复路径）；
6. 内存里还没持久化的批次一律丢弃，不重放。它们是在恢复后已经不存在的状态之上算出来的。

不重放会不会丢数据：流量的计数器是**累计值**，活跃连接的计数基线也在辅助状态里一起恢复。下一帧会按恢复后的基线重新计算增量，所以丢失的那几次提交里的流量会被重新计入，而不是丢失。已经关闭、但关闭记录在丢失的提交里的连接，会损失最后一段增量，上限是一个最大持久丢失间隔（第 10.1 节）。

现在的 actor 对任何存储错误都整批重试（`backend/tauri/src/core/traffic/actor.rs:187-198`）。改用新存储后，必须改走这个流程。

## 8. 查询

### 8.1 接口

```rust
pub enum Query<'a> {
    /// 时间范围内分组求和；一次扫描服务多个分组请求，各带一组筛选。
    SeriesGroup {
        range: TimeRange,
        tier: TierId,
        requests: &'a [GroupRequest<'a>],
        fields: FieldMask,
    },
    /// 时间范围内的事件，按（键，事件序号）的方向翻页。
    EventScan {
        stream: StreamId,
        range: TimeRange,
        direction: Direction,
        cursor: Option<EventCursor>,
        predicate: &'a EventPredicate,
        limit: usize,
    },
}

pub struct GroupRequest<'a> {
    pub filters: &'a [LabelFilter], // 作用在标签编号上
    pub key: GroupKey<'a>,
}

pub enum GroupKey<'a> {
    /// 只求总和。
    Total,
    /// 按一个或几个维度的标签编号分组。
    Labels(&'a [LabelId]),
    /// 先按查找表把每个维度的编号映射成节点号，再按映射后的节点组合分组。
    /// 查找表里没有的编号统一映射成「其他」；可以指定某个编号跳过这一层。
    Mapped(&'a [LabelMap<'a>]),
}
```

- **排行**：排行要「忽略自身维度的筛选」（#5807 引入的行为），所以每个排行是一个带不同筛选的分组请求。它们共用同一次块扫描。
- **拓扑**：
  1. 第一遍，每层一个 `Labels` 分组请求，选出每层要保留的节点。这一层要跳过的值（空的策略链）用筛选**排除在外**，不参与选点，否则一个很大的空值会占掉保留名额（现在的实现在建路径时就跳过空的策略链，`nyanpasu-traffic/src/topology.rs:56`）；
  2. 第二遍，用 `Mapped` 分组请求，把每层的编号映射成「保留的节点」或「其他」。「跳过」对应空的策略链：这一层被跳过，相邻两层直接相连。
  3. 按映射后的节点组合累加，使用方再拆成边（现在的实现见 `topology.rs:53-66`、`:105-125`）。

  两遍用同一个快照，保证一致。第二遍的分组数不超过各层保留节点数的乘积，又不超过组合数。

### 8.2 内存上界

查询的临时内存是 **O(分组数 + 解码缓冲)**，与块里的行数无关。但分组数本身可能接近组合数：比如按目标排行，每个组合就是一组；排行又忽略自身的筛选，筛选也缩小不了它。所以：

- 每个查询开始前，从共享预算里申请空间（第 7.4 节）；
- 运行中分组数超出申请的空间时，返回 `BudgetExceeded`，不会无限增长；
- 要求的分组本身就超出预算时，第一版直接报错，不做溢写到磁盘、也不做近似。只要前 k 名并不能降低内存：精确的前 k 名仍然要先把所有分组累加完（`nyanpasu-traffic/src/query.rs:247` 对全部分组排序）。

### 8.3 事件扫描与游标

- 按块头的键范围和低基数列的取值位图整块跳过。
- 块之间键范围重叠时，按键 k 路归并。路数等于所涉的有序段数，它的内存在准入时预留（第 4.3、7.4 节）。
- 文本谓词先解压再扫描。n-gram 布隆过滤器是扩展项。
- **游标是逻辑的**：（键，事件序号）。
  - 事件序号在**事件进入使用方、对查询可见之前**就分配：使用方创建事件时向 tsdb 申请序号。流量里就是连接关闭、进入 pending 的那一刻（`accounting.rs:344-380`）。
  - **每次打开存储，流实例号加一**，并在打开时以 `Durable` 提交。序号在同一个实例号内单调递增。数据放在 tmpfs、靠闪存备份恢复的档位（第 10.1 节），实例号不能只存在数据库里：从同一份备份恢复两次，会得到同一个实例号。这类档位把实例号计数器单独存成闪存上的一个小文件，打开时先在那里递增并 fsync，再写进数据库。恢复（第 7.5 节）本身就是一次重新打开，所以恢复前分配出去、已经被客户端看到、但随丢弃的批次一起丢掉的序号，不会在恢复后被另一个事件复用：新事件的实例号不同。
  - 事件的完整顺序是（键，实例号，序号），对已存储的事件是稳定的全序。游标的字段是（代，键，实例号，序号）。游标就是这样一个位置，跨成块、整理、重启都保持有效，和现在 `(closed_at, id)` 能跨 flush 翻页的性质一致（`nyanpasu-traffic/src/model.rs:398`）。
  - 流被清空重建时，流的**代**加一；游标带代，代不符时返回「游标已失效」，与内核日志现在按会话代号报告过期的行为一致。
  - **保证的范围**：已存储的记录，位置不随成块、整理、重启变化。不保证的是：`Consistent` 提交在恢复时回滚后，回滚掉的记录会消失；使用方在恢复后重建的事件是新记录，有新的位置，内容也可能不同。以流量为例：10:00 的 `Durable` 保存了活跃连接 A；A 在 10:02 关闭，关闭事件以 `Consistent` 提交并对外可见；随后恢复回到 10:00，A 重新成为活跃连接；10:20 的下一帧发现它已消失，再次关闭它，关闭时间、连接数所在的桶和游标位置都可能与原来不同（`nyanpasu-traffic/src/accounting.rs:104`、`:344-380`）。所以跨恢复继续翻页时，不保证业务事件不重复、不遗漏。需要更强的翻页体验时，使用方可以在恢复后让旧游标失效并刷新。

### 8.4 范围规划

- 第一版只有分钟层和小时层，沿用现在按桶取整的范围语义（`nyanpasu-traffic/src/bucket.rs:30-57`）。
- 分钟层和小时层各自写入，不能由分钟推出小时：活跃连接会丢弃分钟层范围以外的旧分钟桶（`accounting.rs:210-221`）。
- 日层级是扩展项，服务于网关场景（第 14.2 节）。要做时，必须先有覆盖范围、来源发布号，以及把迟到的小时增量原子地传播到日数据的规则（调研报告第 8.9 节）；精度不够时显式报错，不能悄悄把整个桶算进去。
- **降采样由策略决定，不由数据量临时触发。** 是否降采样、小时数据保留多久之后降为按天，都是应用层传入的保留策略的一部分（第 2 节），例如网关档位「小时数据保留 30 天，之后按天」。这样同样的设置总是得到同样的结果，用户能预期；降采样有没有发生、从哪天开始，由降采样水位线给出（第 9.4 节）。

## 9. 保留、维护与空间回收

### 9.1 保留

- **按时间**：整个区段都早于截止点时，删除这个区段；跨越截止点的区段，读取时按「当前截止点」和「删除水位线」中较晚的那个过滤。
- **按字节预算**：超出预算时，从这个流最旧的区段删起。
- **两者可以同时设置，是「与」的关系**：保留下来的数据必须既不早于时间截止点、总字节数也不超过预算；任何一个超出都会触发删除，两者都从最旧的区段删起，所以组合起来没有冲突。例如「保留 30 天，且不超过 256 MB」：平时按 30 天滚动；某段时间连接特别多、30 天的数据超过 256 MB 时，按字节先删。
- **字节数怎么来：记账，不监视文件。** 每个块的字节数在写入时就知道（各片段的长度之和），日志记录的字节数也一样。每个流、每个区段的字节数存在元数据里，和块的写入、删除在同一个事务里更新。维护时（流量就是每次 flush 时）比较这个计数和上限（已过期、尚未清理完的区段不再计入，否则会多删），不需要 watcher 线程，也不需要读文件大小。现有的内核日志就是这样做的：按分片记账，写入时淘汰最旧的分片（`backend/tauri/src/core/logs/redb.rs:124-138`）。开销是每次提交多更新几个计数，删除仍按第 9.1 节的两步做，每轮最多 D 块。
- **计的是数据的字节数，不是文件大小。** redb 删除数据后，空闲的页会被后续写入复用，文件本身不收缩，除非做物理整理（第 9.3 节）。所以文件大小会稳定在「字节上限 + 页内空余 + B 树元数据」附近，不会超出上限后继续增长。真实库从不整理，文件是 156 MB，整理后是 89 MB，其中已关闭连接实际存储约 70 MB；新格式下这个倍数要在基准里实测。用户如果要求文件大小也受控，就在打开时或空闲时做一次物理整理。
- **删除的粒度是区段。** 按字节删除一次删掉最旧的一整个区段，所以实际占用会比上限低最多一个区段。区段太大时（例如网关一天 7.5 MB，而上限只有 16 MB），这个误差就太粗。所以设置了字节上限的事件流，区段按「时间窗，再按大小」切分，单个区段不超过字节上限的八分之一。内核日志的区段本来就是按大小切分的（第 11.2 节）。
- 每个层级、每个事件流各自执行自己的保留策略；策略由使用方在每次维护调用时传入（第 2 节）。调长保留期不会让已经删除的数据回来（第 5.3 节第 3 条的删除水位线）；调短时，下一轮维护就会过期多出来的区段。

**删除分两步：先过期，再分批清理。** 目录约束的是组合的个数，约束不了同一个组合被引用多少次：只有一个组合、每天大量事件时，一个区段可以有任意多块和片段。在一个事务里删完整个区段，工作量就没有上界。所以：

1. **过期**：一个小事务推进这个流的删除水位线，并删除这个区段里的日志记录（它们的总量受日志字节上限约束，第 4.2 节），头部随之释放。从这个事务开始，查询就看不到过期数据；
2. **清理**：之后每一轮维护最多删除 D 个块（默认 64），每轮一个事务，预算用完就停，下次继续，重启后从持久化的水位线和剩余的块接着做；
3. 尚未清理的块仍算作对组合的引用（第 5.3 节），最后一个引用删除之后，组合 id 才能回收。

迟到写入落在删除水位线之前时，`stage` 直接丢弃并计数，不重建已经过期的区段。

### 9.2 逻辑维护（按预算执行）

成块、整理、合并增量块、执行保留、回收组合，都是使用方 actor 发起的同步调用，每次带工作量预算：

- 每一轮都是一个完整的原子事务，工作量有上界：整理与合并的输入不超过 F 个块、I 字节（第 4.3 节）；清理一轮最多删除 D 个块（第 9.1 节）；内存按第 7.4 节的式子预留；
- 预算用完就停在两轮之间，下次继续；
- 积压超过档位上限时，在下一次提交里先做最紧迫的一轮（第 4.3 节）。

### 9.3 物理整理（独占的生命周期操作）

redb 的 `compact()` 需要 `&mut Database`，并且检查是否还有活着的读写事务和保存点（`redb-4.4.0/src/db.rs:1086-1116`）；它也没有可以分段执行的预算接口。所以：

- 它不在 `Storage` 接口里，而是由存储的所有者在**确认已经静默**时执行：打开数据库时，或者空闲且没有任何快照时；
- 「静默」以实际释放为准：所有快照都已经**丢弃**，它们持有的 redb 读事务都已释放。只把快照标记为作废还不够。这与挂起、恢复不同：关闭数据库可以让读事务失效，整理却需要读事务真的不存在；
- 结果有三种：已执行、已推迟（还有快照）、不支持（后端不需要整理）；
- 不承诺执行时长上限（真实库 156 MB 用了 0.2 s），所以**移动端挂起时不做整理**。

### 9.4 可观测性

有损或降级的操作（折叠、降采样、按时间或字节删除、丢弃迟到写入）都必须能被开发者和用户看到，不能只体现为「数字变少了」。四个渠道，从近到远：

1. **查询结果自带精度与降级信息。** 每个查询结果附带：
   - **分辨率分段**：结果覆盖的时间范围里，哪一段由哪个层级给出，例如「早于 8 月 1 日按天，之后按小时」。界面据此标注，并让「按小时看一天」这类图表在按天的那一段不可选，而不是悄悄把一整天画成一个点；
   - **涉及折叠数据**：扫描到任何含溢出标记的组合就置位（第 5.2 节）；
   - **被保留期截断**：请求的范围早于删除水位线时置位，并给出水位线的位置。现在的流量页已经有「范围超出保留期」的提示（`frontend/nyanpasu/src/utils/traffic-retention.ts`），以后改为直接读这个字段，不再在前端按设置推算。

   这是用户最直接的渠道：看到图表的那一刻就知道精度和完整性。

2. **存储状态接口** `status()`。按流、按层级给出：行数、字节数（第 9.1 节的记账值）、最旧和最新的桶或键；删除水位线；**降采样水位线**（早于它的数据只剩按天的精度；为空表示从未降采样）；折叠的组合数、落进溢出组合的流量；按原因分开的累计删除量（时间、字节）；被丢弃的迟到写入数；维护积压。现有的内核日志已经有同类接口（`CoreLogStatus`，`backend/tauri/src/core/logs/model.rs:119-127`）。应用把它显示在设置页的「流量存储」状态里。**判断「降采样是否发生过」，就看降采样水位线是否为空。**
3. **有损操作记录。** tsdb 在元数据里保留最近的有损操作（固定条数，例如 64 条，环形覆盖），每条记时间、操作（降采样一轮、开始折叠、按字节删除）、范围和数量，与操作本身在同一个事务里写入。这样事后也能看到「什么时候开始折叠」「哪天删了哪些区段」，不依赖当时开着日志。`status()` 一并返回。
4. **日志。** 每一轮有损维护输出一条 `tracing` 的 info 级日志（层级、范围、行数从多少到多少）；首次进入折叠、首次降采样时输出 warn 级日志。开发者从应用日志里就能看到。

**开发者怎样在桌面上看到它们**：桌面的默认档位几乎不会触发降采样和折叠，所以测试和调试时用档位覆盖（第 10.1 节，所有数值都可单独覆盖）调低阈值，例如把目录预算设成几 KB、降采样时限设成 1 小时，再用合成的网关规模库（调研报告与第 12 节的 S/M/L 库）跑一遍，四个渠道都应该出现对应的记录。第 12 节的性质测试也断言：每次有损操作之后，`status()` 的水位线和计数、有损操作记录都相应变化。

## 10. 资源档位与移动端生命周期

### 10.1 档位

档位是一组预算，由宿主选择并注入；所有数值都可以单独覆盖。下表是**建议的初始值**：一级平台的值要在基准里测量后修订，二级平台的值只是保守的默认，不做测试。

**总预算**涵盖第 7.4 节列出的全部分项，各分项从总预算里预留，加起来不超过总预算：

| 项目                                             | 桌面           | 移动（iOS 扩展 / Android）                                           | x86 设备       | 二级：低端 64 位设备                                                                                                    |
| ------------------------------------------------ | -------------- | -------------------------------------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **总预算**                                       | 192 MB         | **8 MiB**                                                            | 96 MB          | 16 MB                                                                                                                   |
| 头部                                             | 32 MB          | 1.5 MiB                                                              | 16 MB          | 3 MB                                                                                                                    |
| 目录                                             | 32 MB          | 1.5 MiB                                                              | 16 MB          | 3 MB                                                                                                                    |
| redb 缓存                                        | 64 MB          | 1.5 MiB                                                              | 32 MB          | 3 MB                                                                                                                    |
| 查询（所有并发查询合计，含旧版本快照、结果缓存） | 56 MB          | 2.5 MiB                                                              | 28 MB          | 5 MB                                                                                                                    |
| 暂存、编码缓冲、zstd 上下文                      | 8 MB           | 1 MiB                                                                | 4 MB           | 2 MB                                                                                                                    |
| 日志字节上限（存储，不占内存）                   | 64 MB          | 4 MiB                                                                | 32 MB          | 8 MB                                                                                                                    |
| 提交间隔                                         | 30 s           | 30 s                                                                 | 30 s           | 30 s                                                                                                                    |
| 持久性                                           | 每次 `Durable` | 每次 `Consistent`；最多每 5 min 一次 `Durable`；挂起前一次 `Durable` | 每次 `Durable` | 数据放在 tmpfs；每 15–60 min 由所有者在两次提交之间、`Durable` 提交之后复制到闪存，复制期间不开写事务；备份的写法见表后 |
| 最大持久丢失间隔                                 | 30 s           | 5 min                                                                | 30 s           | 15–60 min                                                                                                               |
| 编解码器                                         | zstd 级别 1    | zstd 级别 1                                                          | zstd 级别 1    | zstd 级别 1                                                                                                             |

- 最大持久丢失间隔与提交频率无关：`Consistent` 提交要靠后续的 `Durable` 提交才会持久。
- 表里没有列出、但要单独定值的项：单批次字节上限（第 4.2 节）；后端在缓存之外的固定开销，以及「上次 `Durable` 之后累计写入多少字节就提前 `Durable`」的阈值（第 7.4 节）；有序段上限 R、单轮清理块数 D（第 4.3、9.1 节）。它们都在基准里实测后定值。
- **tmpfs 备份的写法**：在目标所在目录写临时文件；fsync 临时文件；rename 覆盖目标；fsync 父目录；这之后才把这份备份记为成功的检查点。rename 之后的目录 fsync 才能确认替换后的目录项已经持久化。实例号计数器不放在备份里（第 8.3 节）。
- 移动端的数值以 iOS 扩展的 50 MiB 进程上限为准（与 mihomo 共享），要在真机上测完再定。

### 10.2 移动端

- **单进程持有。** 数据库只由一个进程打开：iOS 上是 Network Extension，Android 上是 VpnService 所在的进程。界面进程通过 IPC 查询，不直接打开文件。这样主 App 被挂起时手里没有文件锁，避开 0xdead10cc。
- **iOS 上数据库放在扩展自己的容器里，不放 App Group 共享容器。** 既然只有扩展打开它，就不需要共享容器。有开发者在 Apple 论坛报告，0xdead10cc 只发生在共享容器（例如 App Group）里的文件上（单一来源，非 Apple 官方说法）。如果真机验证属实，扩展挂起时持有自己容器里的文件锁不会被终止，下面的挂起协议就只关乎持久性，不再是避免被杀的硬条件。
- **挂起与恢复的触发点**由宿主的生命周期适配器提供：
  - iOS：packet tunnel provider 的 `sleep` / `wake` 回调，以及停止隧道的回调；需要额外执行时间时，用 `ProcessInfo.performExpiringActivity`。它在活动执行期间也可能触发过期回调，所以挂起流程必须能在任一步中止；
  - Android：VpnService 的停止回调，以及 `onTrimMemory`。
- **挂起协议**（宿主向存储所有者发消息，所有者按顺序执行）：
  1. 停止接受新的快照和写入；
  2. 撤销未结束的快照：查询的扫描循环在**每个列块、每批行**的边界检查取消标记，发现被撤销就立即返回 `Closed`；
  3. 做一次 `Durable` 提交；
  4. 丢弃 `Database`，关闭存储，释放文件锁。这一步不依赖快照先释放：redb 关闭后，未结束的读事务只会收到 `DatabaseClosed`（`redb-4.4.0/src/db.rs:718-727`）；第 2 步只是让查询尽快结束、少做无用功。

  **关闭本身也有不可取消的 I/O。** redb 的 `Drop` 会提交分配器状态、收缩文件、写关闭头，并刷盘两次（`redb-4.4.0/src/db.rs:1885-1930`、`tree_store/page_store/page_manager.rs:2373-2398`）。第 3 步已经持久化了数据，但第 4 步仍然要写盘。所以：

  - 不承诺「过期回调一到，就能立即释放文件锁」。`performExpiringActivity` 可能第一次回调就是过期，也可能在活动中途通知过期；已经开始的同步写事务和 fsync 都中断不了，套一层 timeout 或丢弃等待方也没用。所有者仍然把已经开始的步骤做完；
  - 测量的范围是从「停止接受操作」到「文件锁实际释放」的全程，包含 `Drop` 内部的工作，在真机上取 p99；
  - 关闭前进程被杀时，redb 下次打开会按「需要修复」处理，重建分配器状态，耗时随文件大小增长。这一项也要测；
  - **暂不处理，留给 iOS 的实际接入（用户已决定）。** 第一版照上面的四步实现，不为 iOS 另做设计。接入 iOS 时再做第 12 节的验证：如果「数据库放在扩展自己的容器」验证属实，挂起协议就降为尽力而为的持久化，做第 1–3 步，第 4 步可以省掉，恢复时也不必重开；如果实践中仍会因持锁被终止，再设计解决方案，例如一条经过验证、关闭时不写盘的后端路径（以后的段文件后端）。redb 默认的 `Drop` 承担不了这个角色。

  挂起时不做物理整理（第 9.3 节）。恢复时重新打开存储（流实例号加一），从持久化状态重建目录和头部。

- **被系统杀掉**：Android 的 LMK、iOS 的 jetsam 随时可能杀进程，最多丢失一个最大持久丢失间隔的数据。

## 11. 各使用方的映射

### 11.1 流量

- **序列**：
  - 维度：13 个报表维度，加上能还原原始维度的规范标签（规则类型和内容、完整策略链、带「有无」标记的订阅）；
  - 字段：上传、下载、连接数；
  - 层级：分钟层（区段 1 小时，保留 6 小时）、小时层（区段 1 天，按用户设定保留）。
- **事件流 `closed`**：
  - 列：关闭时间（键）、开始时间、首次看到的时间、上传、下载、组合 id、连接 id；
  - 另有一列「折叠的目标」：只有当这条连接的组合里目标被折叠时才填写，否则为空。它用块内的局部字典，不进全局目录，也就不占目录预算。这样用量里的目标即使折叠了，单条连接的目标仍然完整；未折叠时这一列几乎不占空间；
  - 连接 id 用 `Identity` 列：是 UUID 就存 16 字节，否则回退为文本。现在的 `id` 是 `String`，代码并不保证它是 UUID（`nyanpasu-traffic/src/model.rs:321`）；
  - 事件序号在连接关闭、进入 pending 时分配（第 8.3 节）；
  - 区段 1 天，保留期另设。
- **辅助状态**：会话元数据、活跃连接，用「版本号 + 二进制」格式，每次只写脏的那几条，与日志记录在同一个事务里。
- **报表语义**（排行、拓扑、速率、活跃行、pending 行）留在 `nyanpasu-traffic`。查询在 actor 外执行：actor 只负责捕获快照和 pending、活跃行。因为 pending 和活跃行在 actor 里，这次捕获会排在 actor 正在执行的提交后面；tsdb 的版本登记表只让 tsdb 自己的快照不必等 fsync（第 7.1 节）。这段等待在移动端能否接受，要实测；不能接受时，由流量把 pending 和活跃行也按版本发布出来，与 tsdb 无关。
- **提前 flush**：actor 每次观察帧后，若必须一起提交的会话元数据、辅助删除、序列增量和关闭事件达到单批次字节上限的一半，就立即 flush，不等 30 s（第 4.2 节）。首个事务同时容纳尽可能多的活跃辅助记录，余下记录可放到后续有界事务中；活跃记录自带累计计数和自己的桶，事务之间崩溃只使部分记录落后一次 flush，下一次采样从这些计数计算增量，不会重复计数。
- **钉住组合**：活跃连接引用的组合，随活跃连接的写入一起 `pin` / `unpin`（第 5.3 节）。

### 11.2 内核日志

- **事件流**，字段对应 `backend/tauri/src/core/logs/model.rs:48-56` 的 `CoreLogRecord`：
  - 序号（键）、接收时间、原始时间（可空文本）；
  - `log_type`：字典列。级别是从它派生的编码（`backend/tauri/src/core/logs/redb.rs` 写入时用 `level_code` 计算），作为单独的低基数列存放，供块头的取值位图使用；
  - 来源：`capture`、`instance_id`、`core_kind`，都是字典列；
  - 正文：文本列。
- **截断标记不存储**：它是查询时生成预览才得到的结果（`backend/tauri/src/core/logs/redb.rs:271`），不是记录本身的字段。
- **区段**：按会话代号，再按大小切分，对应现在的分片文件。
- **保留**：按字节预算。
- **大记录**：现在单条记录最大约 1 MiB（`MAX_RECORD_BYTES`，`model.rs:4`），超过列块上限，作为大值跨多个片段存放（第 3.3、6.5 节）。
- **压缩**：现在有三种模式：不压缩、预置字典、训练字典（`backend/tauri/src/core/logs/codec.rs`）。改成按块压缩的收益，要用真实日志测量后再定。
- **查询**：级别筛选改用块头的取值位图，替代单独维护的 `levels` 索引表；关键字搜索按块扫描；游标是（会话代号，序号），会话代号就是第 8.3 节所说的流的代。

### 11.3 任务日志

按运行 id 分组的事件流。`nyanpasu-jobs` 在 `nyanpasu-runtime` 子模块自己的 workspace 里。`nyanpasu-tsdb` 先放在本仓库（第 14 节）；真要接入任务日志时，再把它移到 `nyanpasu-runtime` 下，两边才都能依赖。这一项不进第一版。

## 12. 验证计划

- **一致性测试**：每个存储后端都要通过（第 3.5 节）。
- **性质测试**：以内存参考模型为准，覆盖：
  - 任意拆分的批次；
  - 成块与合并不改变结果，包括存在性；
  - 迟到写入；
  - id 复用加上保留期变化、时钟回拨；
  - 旧快照在回收、成块、整理之后仍然正确；
  - 游标跨成块、跨合并继续翻页。
- **故障注入**：崩溃点覆盖成块、整理、合并、回收的每一步；提交结果未知后重开；`Consistent` 删除被回滚；维护积压；块损坏或超大。
- **针对第 2 轮反例的确定性用例**：
  - 非前缀成块：日志依次是「桶 A、桶 B、桶 A」，只把 A 成块后，A、B 各计一次；
  - 保留期删除了尚未成块的日志记录；
  - 更早的几次 `Consistent` 提交在恢复后丢失，使用方从恢复状态重建（第 7.5 节）；
  - pending 事件跨 flush 翻页，游标不变；
  - 多个发布号的快照同时存在，内存按第 7.4 节记账；
  - 跨多个片段的大值；
  - 目录写满后进入溢出组合，候选值不泄漏；
  - 读取方在打开存储快照后被抢占、写入方连续发布两次，读取方仍取得匹配的版本；
  - pending 事件的序号已被客户端看到，随后提交失败并恢复，新事件不复用它的位置；
  - 同一个桶被反复更新，日志字节数达到上限时先折叠；
  - 拓扑里空的策略链流量最大时，不占用保留名额。
- **针对第 5 轮审计的确定性用例**：

  | 用例                  | 输入或故障点                                    | 必须验证的结果                                                         |
  | --------------------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
  | 多轮重叠的事件整理    | 多批乱序事件都覆盖同一个时间窗，总量是 I 的数倍 | 统计全部有序段（不只 L0）；归并内存按准入预留，超出时 `BudgetExceeded` |
  | 大区段过期            | 只有一个组合、大量事件，触发过期                | 过期后立即不可见；每轮清理不超过 D 块；重启后接着清理                  |
  | 提交前后端失效        | `stage` 读取、扩容或写片段时注入 I/O 错误       | 报告 `BackendFailed` 并进入恢复，不依赖走到 `commit`                   |
  | 查询导致后端失效      | 未缓存的读取失败                                | 所有者得知需要重开，之后的写入走恢复                                   |
  | 关闭时的写入延迟      | 在分配器状态提交、关闭头刷盘时注入延迟          | 测出从停止到释放锁的全程；暴露过期后仍持锁的路径                       |
  | 旧快照逐渐独占页面    | 查询持有 P，之后的写入逐步替换全部头部和目录页  | 保留成本不超过捕获时的预留，没有未记账的分配                           |
  | 恢复时旧查询未退出    | 暂停旧查询，再关闭并重开                        | 旧预留归还之前不开始重建；峰值符合预算                                 |
  | 稀疏更新触及全部页    | 小批次分散地修改每一页                          | 按实际复制的页预留，不按输入字节估计                                   |
  | 已整理区段的迟到增量  | 整理块跨 A、B 两个桶，只给 A 加增量             | A 正确相加，B 不变；合并只合增量块                                     |
  | `Consistent` 批次重提 | 同一个批次号连续提交两次                        | 第二次被拒绝，统计只增加一次                                           |
  | tmpfs 反复恢复        | 从同一份闪存备份启动两次                        | 两次的实例号不同                                                       |

- **可执行的上界**（不只是测量）：重启回放量不超过日志字节上限；单轮整理的输入不超过 F 个块、I 字节；块不超过 M 行、B 字节；单轮清理不超过 D 块；查询和维护的内存不超过准入时的预留。
- **基准**：
  - 数据：S/M/L 合成库、真实库副本、日志负载。
  - 指标：
    - 中位数与 p99 延迟；
    - 内存峰值（按第 10.1 节的口径）；
    - 每天实际写入存储的字节数；
    - 打开时间；
    - 最大回放字节数。
  - 一级平台全部要测：Windows、macOS、Linux 桌面，x86_64 Linux（glibc 与 musl），Android 与 iOS 真机。移动端以 iOS 扩展的预算为准。
  - **逐级加机制的对照**，分清收益来自哪里：
    1. 现有实现；
    2. 规范化（只存组合 id）、减少序列化和中间行对象；
    3. 列式布局加轻量编码；
    4. 再加 zstd 和区段整理。

    每一级都同时计入目录、块头、redb 页分配、日志、整理的写放大，以及查询与写入的延迟。例如已关闭连接从轻量编码的 30.3 B/条到 zstd 的 25 B/条，只省了约 17.5%，单凭这个数字不足以证明整理的生命周期值得。

  - **iOS 接入时的验证**（不阻塞第一版）：扩展私有容器里的文件锁在挂起时是否触发 0xdead10cc；从停止到释放锁的全程耗时；被杀后下次打开的修复耗时（第 10.2 节）。
- **测试与构建矩阵**：
  - 一级平台跑测试和基准：
    - `x86_64-pc-windows-msvc`、`aarch64-pc-windows-msvc`；
    - `x86_64-apple-darwin`、`aarch64-apple-darwin`；
    - `x86_64-unknown-linux-gnu`、`aarch64-unknown-linux-gnu`、`x86_64-unknown-linux-musl`；
    - `aarch64-linux-android`、`aarch64-apple-ios`。
  - 二级平台（例如 `aarch64-unknown-linux-musl`）不进测试矩阵。
  - 32 位目标由 `compile_error!` 拒绝。

## 13. 范围

**第一版：**

- 存储端口，以及内存、redb 两个后端；
- 目录，整个常驻内存；超出预算时按使用方声明的折叠阶梯降级（第 5.2 节）；
- 分钟层和小时层，包括日志、头部、成块、增量块、合并与区段整理；
- 事件流，包括游标、溢出片段、两种保留策略；按有序段计数并预留归并内存，不承诺归并路数的硬上界（第 4.3 节）；
- 区段先过期、再分批清理（第 9.1 节）；
- 轻量编码，加 zstd 级别 1，遵守「省 10% 才保留」的规则；每个压缩单位只含一列；

### 14.1 只折叠某些维度的代价

真实库（8 天，1,297 个组合）把一个维度折叠成溢出标记后，剩下的组合数：

| 折叠的维度                             | 剩下的组合数 | 减少  |
| -------------------------------------- | ------------ | ----- |
| 目标                                   | 319          | 75%   |
| 目标 + 进程                            | 119          | 91%   |
| 目标 + 进程 + 策略链                   | 99           | 92%   |
| 源地区 / 进程 / 目标地区 / 策略链之一  | 1,014–1,250  | 4–22% |
| 规则、来源、入站、协议、订阅、定位依据 | 1,297        | 0     |

各维度的取值数：目标 665、进程 65、策略链 27、目标地区 27、规则 21，其余都不超过 3。前 100 个目标占了 80% 的小时行，277 个目标只出现在一行里。所以组合数几乎完全由目标这一个长尾维度决定。

收益：超出预算时，「整个组合溢出」把规则、进程、策略链等所有维度一起丢掉；只折叠目标，其余维度仍然精确，组合数降到四分之一。

代价：

- **语义**：一个目标的流量，一部分记在完整的组合里（预算满之前），一部分记在折叠的组合里（预算满之后）。按目标筛选、按目标排行都会少算后者，所以结果要带一个「有部分数据已折叠」的标记，界面显示出来。总量和其他维度仍然精确。「整个组合溢出」也有同样的问题，只是丢得更多。
- **预算**：折叠后的组合本身也是组合，同样占目录预算。所以折叠只能是一个固定的阶梯，最后一级仍然是整个组合溢出，保证写入不会失败。
- **阶梯由使用方声明，不由 tsdb 按基数动态选择**：动态选择会让同一份输入在不同时刻落进不同的维度组合，结果无法解释。
- **实现**：只在预算满时多做几次查找（每一级一次）；溢出标记已经预留为每个维度的编号 0（第 5.2 节），查询、拓扑（映射成「其他」）、回收都不用改。tsdb 里大约一两百行，加上每一级的性质测试；流量这边要显示折叠标记。
- **明细不受影响**：已关闭连接可以把目标另存为事件流自己的列，用块内的局部字典，不进全局目录，也就不占目录预算。这样即使用量里的目标折叠了，单条连接的目标仍然完整。

结论（用户已同意）：第一版就支持，阶梯取两级：先折叠目标，仍然超出时整个组合溢出。真实库在桌面和移动端的预算下都不会触发折叠，它主要服务于网关场景。

### 14.2 保留期与降采样

**每天的数据量**（真实库；新格式按第 6.3 节的实测换算）：

| 数据             | 每天的条数               | 新格式每条 | 每天        | 7 天     | 30 天     | 90 天     | 1 年    |
| ---------------- | ------------------------ | ---------- | ----------- | -------- | --------- | --------- | ------- |
| 小时用量         | 满一天的约 1,500–2,000   | 约 6 B     | 约 10 KB    | 约 70 KB | 约 0.3 MB | 约 0.9 MB | 约 4 MB |
| 已关闭连接       | 满一天的约 1.8–4.4 万    | 约 25 B    | 0.44–1.1 MB | 3–8 MB   | 13–33 MB  | 40–100 MB | —       |
| 已关闭连接，网关 | 每天数十万（按 30 万估） | 约 25 B    | 约 7.5 MB   | 约 53 MB | 约 225 MB | 约 675 MB | —       |

对照：现在的格式每条已关闭连接约 571 B（值 527 B + 键 44 B），每天 1.8–4.4 万条时，30 天就是 0.3–0.75 GB。

**降采样成日数据**：真实库里按天合并后，小时用量的行数降到 31%（8,516 行变成 2,605 行；按周则是 1,741 行）。但小时用量本身每年只有约 4 MB，降采样一年只省约 3 MB。代价是：

- 要多一个日层级，它的正确性规则还没有设计：覆盖范围、来源发布号、迟到的小时增量要原子地传播到日数据（第 8.4 节）；
- 超过降采样时限的数据只剩按天的精度，「按小时看一天」的图表就不能用于更早的日子；
- 长范围查询的收益也小：90 天的小时数据约 13.5 万行，按列扫描在毫秒级。

只有网关这种每小时上万个组合的场景，小时数据才会大到值得降采样，而这正是第 13 节「日层级」扩展项的启用条件。

**建议（常规情况下的最优解）**：

- **常规场景不降采样，网关场景可以降采样**（用户已确认）。常规场景的小时数据太小，降采样省下的空间抵不上新增的正确性规则和精度损失。网关场景由保留策略指定「小时数据保留多久之后降为按天」，作为日层级扩展项实现；降采样是否发生、从哪天开始，见第 9.4 节。
- **小时用量和已关闭连接分开设置保留期**：已关闭连接占了约 98% 的空间，小时用量几乎不占空间。现在两者共用一个 `traffic_retention`（默认 7 天）。建议小时用量默认 90 天（约 0.9 MB），已关闭连接默认 7 天（3–8 MB），后者仍可由用户调长。
- **已关闭连接另设一个按字节的上限**，由档位给出，作为时间保留之外的保护，例如桌面 256 MB、移动端 16 MB。网关场景设长保留期时，按字节的上限先生效，从最旧的区段删起（第 9.1 节）。
- 分钟层保持 6 小时：它服务于「最近一小时」这类范围，由流量的查询语义决定（`nyanpasu-traffic/src/bucket.rs:9`），不暴露给用户。

具体的默认值和设置界面属于应用层，由流量和设置页决定；tsdb 只负责执行传入的策略。

**分开设置的实施代价**（约半天到一天，不依赖 tsdb，可以在现有存储上先做）：

| 位置                         | 改动                                                                                                                                                                         | 规模              |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `nyanpasu-config`            | `traffic_retention` 改为只管用量，新增已关闭连接的保留期字段。旧配置文件没有新字段时，沿用原来的 `traffic_retention`，用户原有的行为不变                                     | 约 40 行，加测试  |
| 流量的保留端口与 `Prune`     | 端口返回两个值，`Prune::new` 分别算出小时和明细的截止点。现有存储本来就分开删（`hours_before`、`closed_before`，`nyanpasu-traffic/src/accounting.rs:36-58`），存储本身不用改 | 约 20 行，改测试  |

**按字节上限的实施代价**：

- **tsdb**：每个流、每个区段的字节计数，维护时的触发判断，以及按大小切分事件区段，约一两百行，加性质测试（维护之后不超过上限；与时间上限同时生效时两者都满足）。不需要后台线程（第 9.1 节）。
- **性能**：每次提交多更新几个计数，判断是 O(1)；删除按区段分批进行，每轮最多 D 块，不会造成写入尖刺。
- **现有存储上不建议做**：现有的明细表没有字节计数，要补一张计数表，并在每次写入、删除时维护，工作量约一天，tsdb 上线后就要丢掉。
- **应用层**：只用档位给的默认值时，不需要改设置；要让用户可调，就再加一个配置字段和一个选择器（例如「不限 / 256 MB / 1 GB」），约半天。

### 14.3 迁移的工作量

现有库可以无损迁移：组合表存的是结构化的 `Dimensions`（规则的类型与内容分开存，策略链是列表，订阅区分「没有」和「空字符串」，`nyanpasu-traffic/src/model.rs:56-80`），丢信息的只是查询时生成的展示键。实测真实库里所有已关闭连接的维度都能在组合表里找到。

**耗时**（i9，单线程，真实库副本，三次运行）：打开 1–3 ms；读出 1,297 个组合 2 ms；读出 14,729 行用量 1.4 ms；读出并解码 122,147 条已关闭连接 212–260 ms（每条约 2 µs）。写入新格式是同一个量级，所以桌面上整个迁移在 1 s 以内。按每月 600 万条的重度用户估算，读取约 13 s，整体在半分钟到一分钟。移动端和路由器上没有旧库，不需要迁移。

**工作量**：约一天，几百行，包括测试：

- 只读打开旧库，校验 schema 版本为 3；更早的版本按现有策略直接丢弃（`nyanpasu-traffic/src/redb.rs:21-22`）；
- 组合表映射到目录的规范标签；用量按桶分批写成序列输入；已关闭连接按（关闭时间，id）顺序写成事件，用一个专门的导入实例号分配序号；会话元数据和活跃连接转成新的辅助状态格式（结构相同，只换编码）；
- 分多个批次提交，每批受单批次上限约束（第 4.2 节）；导入进度记在辅助状态里，中断后从断点继续；全部完成后才删除旧文件；
- 验收用例：同一份 v3 夹具，用旧实现和导入后的新实现分别生成报表，结果逐字节一致。这需要在删除旧实现之前，先把旧实现的报表结果保存为测试数据。

任何一步失败时，退回「统计可丢弃」：删除旧库，直接重建。
