# schema 世代、manifest v2 与升级预检

[sing-box 内核接入设计](design.md) 的子设计。回答需求 ④：内核更新带来的 schema 变动从最近的版本开始兼容，并设计进 manifest v2，防止旧版应用更新到新内核后无法使用。

路径缩写：`U/` = `backend/nyanpasu-updater/src/`，`Q/` = `backend/nyanpasu-config/src/`，`C/` = `backend/nyanpasu-core/src/`，`S/` = `scripts/src/`。

---

## 1. 问题

1. **sing-box 按次版本移除配置项。** 官方弃用表里，1.11 弃用的旧 inbound 字段在 1.13 移除，1.12 弃用的旧 DNS 服务器格式在 1.14 移除，1.15 弃用的 TUN `stack` 计划在 1.17 移除。未知字段与已移除字段会让内核拒绝整份配置。
2. **Nyanpasu 自己往配置里写片段。** 受管设定（入站、API 服务、日志、之后的 TUN）是 Nyanpasu 生成的。某个世代里合法的写法，在下一个世代可能被移除。
3. **内核与应用分开更新。** 用户可以长期不升级应用而一直点“更新内核”。现在的清单 v1 只有每个内核一个 `latest`（`manifest/version.json`），应用会无条件装到最新。
4. **结果。** 一个只会写 1.14 片段的旧应用，装上 1.16 内核后写出的配置被拒绝，内核起不来，而用户没有做任何“错误”的操作。

Clash 系内核目前没有这个问题的现实案例，但同样没有防护。

---

## 2. schema 世代

**定义。** 世代是一段内核版本，在这段版本内 Nyanpasu 写出的受管片段保持合法。

| 家族       | 世代的取法                  | 理由                                                                                       |
| ---------- | --------------------------- | ------------------------------------------------------------------------------------------ |
| `sing-box` | 版本号的 `主.次`，如 `1.14` | 上游的弃用与移除都发生在次版本边界；补丁版本不改 schema。取法是机械的，不需要人判断        |
| `clash`    | 常量 `1`                    | 这些内核滚动发布，没有按版本的 schema 契约。常量世代等于“不门控”，与现状一致，但保留了开关 |

**应用声明自己支持的世代。** 每个内核家族一个编译期常量集合：

```rust
/// 本应用会写的 sing-box schema 世代，升序。
pub const SUPPORTED_SING_BOX_GENERATIONS: &[SingBoxGeneration] = &[SingBoxGeneration::V1_14];
```

```rust
/// sing-box 的 schema 世代。工作区内枚举，保持穷尽。
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum SingBoxGeneration {
    V1_14,
}
```

- 起点是 `1.14`。它是当前稳定线，也是硬下限：API 服务从 1.14.0 才有（主设计 §1.3），而控制面依赖它。更早的版本不支持，也不为它们写兼容分支。这就是“从最近的版本开始做兼容”。
- 新增世代 = 新增一个枚举变体。所有按世代的穷尽 `match` 在编译期报错，逼作者逐处判断新世代的写法。
- 一个世代从集合里移除，需要在发布说明里声明；届时仍装着该世代内核的用户会在构建时得到明确的错误与升级指引。
- `SingBoxGeneration` 与 `CoreFamily` 一样放在 `nyanpasu-config`。

## 3. 构建时按世代写

### 3.1 世代从哪里来

构建运行配置之前，调用方解析“将要启动的那个二进制”的世代，作为输入传给构建器。这与端口的处理相同：IO 在调用方，构建器是纯函数（`backend/nyanpasu-profile-transform/src/runtime_builder.rs:1-5`）。

- 读版本用现有端口 `CoreVersionReader`（`backend/nyanpasu-contracts/src/core_version.rs:11-15`）；它已经由 `nyanpasu-os` 实现并注入。sing-box 的探测参数与解析在 S4 补上。
- 版本解析成世代是纯函数：`1.14.4` → `V1_14`；`1.15.0-alpha.13` → 按 `1.15` 处理；解析不出版本 → 错误。
- 读版本有成本（起一次子进程）。按二进制路径与修改时间缓存，做法参照 core-manager 的 `VersionCache`（`backend/nyanpasu-runtime/crates/nyanpasu-core-manager/src/capability.rs:34-83`）。缓存的归属是内核生命周期工作流，不是全局状态。

这偏离了 `core-specific-config.md` §2 对“按版本判断能力”的否决。那里的理由是“现在先构建配置、后解析 `CoreSpec`”与“收益不抵成本”。对 sing-box，收益变成了“能不能启动”，而顺序问题由“调用方先解析世代”解决，构建器本身的形状不变。Clash 家族不解析世代，行为与现在完全一样。

### 3.2 不支持的世代

二进制的世代不在 `SUPPORTED_SING_BOX_GENERATIONS` 里时，构建入口返回专用错误，不进入 pipeline：

```rust
/// 已安装的内核版本超出了本应用会写的 schema 范围。
#[snafu(display("the installed {core} {version} is outside the supported schema generations"))]
UnsupportedCoreGeneration {
    core: CoreId,
    version: String,
    supported: Vec<String>,
},
```

- 太新：提示升级 Nyanpasu，或把内核换回受支持世代的最新版（清单里有，见 §4）。
- 太旧：提示更新内核。
- 这也是对用户自行替换二进制的回答：不在范围内就拒绝，不猜。

### 3.3 写入器的形状

sing-box 受管设定写入器接收世代，对（世代, 设定）做无通配的穷尽 `match`，写法延续 `core-specific-config.md` §3.2：

```rust
fn mixed_inbound(generation: SingBoxGeneration, port: u16, listen: &str) -> ConfigValue {
    match generation {
        // 1.14: `listen` / `listen_port` 直接在入站上；旧的入站级 sniff 字段已在 1.13 移除，不写。
        SingBoxGeneration::V1_14 => { /* … */ }
    }
}
```

- 每个分支旁用注释写明上游依据：字段在哪个版本加入、哪个版本移除，附弃用表或迁移文档的条目。
- 每个世代一套 golden 测试，输入相同，期望输出各自一份。
- 世代之间写法相同的设定也要显式列出每个世代，不用 `_`。

### 3.4 弃用警告

sing-box 的 gRPC `GetDeprecatedWarnings` 返回当前运行配置里用到的、已弃用但尚未移除的项，带弃用版本与计划移除版本（`daemon/started_service.proto` 的 `DeprecatedWarning`）。

- 应用在内核就绪后取一次，经 `get_core_deprecation_warnings` 给前端（[`core-api.md`](core-api.md) §9.1）。
- 警告指向 Nyanpasu 写的片段时，说明写入器落后于该世代，是应用的缺陷：测试里用真实二进制断言“空白 Profile 加全部受管设定”不产生任何弃用警告。
- 警告指向用户 Profile 的内容时，在检视页提示，由用户处理。Nyanpasu 不改写用户内容。

## 4. manifest v2

### 4.1 目标

1. 应用只会被引导到它支持的世代里的最新版本。
2. 上游发布新的次版本后，旧应用继续拿到旧世代的补丁更新，直到上游停止发布。
3. 清单的结构不再把内核名写死在字段里，新增内核不需要改结构。
4. 旧应用不受影响。

### 4.2 与 v1 的关系

| 方面     | v1                                                 | v2                                 |
| -------- | -------------------------------------------------- | ---------------------------------- |
| 文件     | `manifest/version.json`                            | `manifest/v2/cores.json`           |
| 生成     | `S/manifest/generate-latest-version.ts`，保持不变  | 新脚本，同一个定时工作流里多跑一步 |
| 内容     | 七个 Clash 系内核，结构冻结                        | 全部内核，含 sing-box              |
| 读取方   | 已发布的全部应用版本，以及仍在维护的 v1 `dev` 分支 | 切换之后的应用版本                 |
| sing-box | 永不加入                                           | 有                                 |

- v1 的结构体对七个字段是写死的（`U/updater/mod.rs:39-48`），旧应用对未知字段宽容但也用不上。往 v1 里加 sing-box 没有读者，只会增加出错面。
- 应用在一个版本里把全部内核的更新来源从 v1 切到 v2，不做“v2 失败回退 v1”的双读。切换是一次可迁移的破坏性变更（`architecture.md` 的兼容策略）。
- 镜像与获取路径沿用现有机制（`U/updater/instance.rs:101-134`、`U/updater/mirrors.rs`），只换文件路径。
- 键名用 kebab-case，完成 `U/updater/mod.rs:37` 的 TODO。

### 4.3 结构

```json
{
  "manifest-version": 2,
  "updated-at": "2026-11-11T00:00:00.000Z",
  "cores": {
    "sing-box": {
      "family": "sing-box",
      "releases": [
        {
          "version": "1.15.2",
          "channel": "stable",
          "generation": "1.15",
          "artifacts": {
            "linux-x86_64": {
              "name": "sing-box-1.15.2-linux-amd64.tar.gz",
              "binary": "sing-box-1.15.2-linux-amd64/sing-box",
              "sha256": "…"
            }
          }
        },
        {
          "version": "1.14.6",
          "channel": "stable",
          "generation": "1.14",
          "artifacts": {}
        }
      ]
    },
    "mihomo": {
      "family": "clash",
      "releases": [
        {
          "version": "v1.19.33",
          "channel": "stable",
          "generation": "1",
          "artifacts": {}
        },
        {
          "version": "alpha-478af2a",
          "channel": "alpha",
          "generation": "1",
          "artifacts": {}
        }
      ]
    }
  }
}
```

示例里的版本号只为说明结构，`artifacts` 为空的条目是省略。

| 字段                 | 含义                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `manifest-version`   | 结构版本。应用遇到比自己认识的更大的值时停止解析并报告“清单需要更新的应用”，不尝试部分读取      |
| `cores` 的键         | 内核的分发标识，对应应用里去掉通道后的内核名：`mihomo`、`clash-rs`、`clash`、`meow`、`sing-box` |
| `family`             | 内核家族。应用核对它与自己对该内核的认识一致，不一致则忽略该条目                                |
| `releases`           | 该内核当前可安装的发行版列表。对每个（通道, 世代）组合只保留最新的一个                          |
| `version`            | 上游的版本标识，原样                                                                            |
| `channel`            | `stable` 或 `alpha`。对应现有的 `mihomo` 与 `mihomo-alpha` 这种成对的内核身份                   |
| `generation`         | §2 的世代，字符串                                                                               |
| `artifacts` 的键     | 平台标识，kebab-case 的 `<os>-<arch>`，取值集合与现有 `arch_template` 的键对应                  |
| `artifacts.*.name`   | 发行资产的文件名，已经是完整名，不再用 `{}` 模板                                                |
| `artifacts.*.binary` | 归档内可执行文件的路径；单文件资产省略。解包时不再靠内核名猜                                    |
| `artifacts.*.sha256` | 资产的 SHA-256，上游提供时填写。有则下载后校验，无则保持现有行为                                |

应用忽略不认识的字段与不认识的内核键。这是向前兼容的唯一约定；结构性的变化通过提升 `manifest-version` 表达。

### 4.4 应用怎么选版本

对某个内核身份（例如 `sing-box`，稳定通道）：

1. 取 `cores[<内核>].releases` 里 `channel` 相符的条目。
2. 留下 `generation` 在应用支持集合内的。
3. 取其中版本最大的。这就是“可更新到”的版本。
4. 另外计算清单里该通道的最大世代。如果它大于应用支持的最大世代，界面显示一条说明：有更新的内核版本，但需要先升级 Nyanpasu。这个版本不可安装。

Clash 家族的支持集合是 `{"1"}`，清单里它们的世代也恒为 `1`，所以第 2 步不筛掉任何东西，行为与 v1 相同。

版本比较：sing-box 用 semver；Clash 系沿用现有的比较与滚动版本解析（`U/updater/instance.rs:326-336` 的 `resolve_rolling_versions`）。v2 不改变 alpha 通道“清单滞后时由客户端解析滚动发行版”的机制。

### 4.5 生成规则

新脚本放在 `S/manifest/`，从根 `package.json` 的命名任务调用（`scripts.md`）。

| 内核       | 规则                                                                                                                                |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `sing-box` | 取上游全部稳定发行版，按 `主.次` 分组，每组取最新补丁版。保留最近的若干组，组数是脚本里的一个常量，初值 3。世代低于 `1.14` 的不收录 |
| Clash 系   | 每个通道取最新一个，世代 `1`。解析逻辑复用 `S/manifest/manifest.ts` 现有的 `resolve*` 函数                                          |

- 新的次版本出现时自动成为新的一组，世代随之是新的值。**没有人工步骤**，也因此没有“忘了标记破坏性变更”的失误：新的次版本对旧应用默认不可见，直到某个应用版本把它加入支持集合。
- 代价是保守：即使某个次版本实际上没有破坏 Nyanpasu 写的片段，旧应用也不会自动装它。这是有意的取舍，错误方向是“晚一点用上新内核”，而不是“起不来”。
- Clash 系如果将来出现破坏性变更，由维护者在生成脚本里把该内核的世代提到 `2`，并在同一时期发布支持 `2` 的应用。这是为它们预留的开关，平时不动。
- 资产名与归档内路径在生成时确定并写入清单，脚本测试用上游真实的资产列表样例做固定输入。
- 平台变体：sing-box 的 Linux amd64 有默认、`-glibc`、`-musl` 三个资产。清单每个平台只列一个；选哪个在 S5 用实际分发环境验证后定，原则是与现有 Mihomo 资产的兼容面一致。

### 4.6 随包内核与准备脚本

- 安装包自带的 sing-box 版本由 `S/prepare/` 的资源准备脚本决定。它读同一份 v2 清单并应用同一条规则：应用支持的最大世代里的最新版本。这样“随包版本”与“应用内更新会给的版本”不会分叉。
- 支持集合因此有两个读者：Rust 侧的构建与 updater，TypeScript 侧的准备脚本。它只能有一个来源。做法是仓库里放一份数据文件作为来源，Rust 侧用测试断言枚举与文件一致；文件的位置与格式在 S5 定。
- sidecar 文件名用 `sing-box` 加目标三元组，与其他内核一致。
- sing-box 需要版本戳文件（现有 `needsVersionStamp` 机制，`S/prepare/resources.ts:295`），让缓存校验能发现世代变化。

## 5. 时间线上的行为

用一个例子说明各方在上游发布新世代时看到什么。假设应用 A 支持 `{1.14}`，应用 B 支持 `{1.14, 1.15}`。

| 事件                      | 清单 v2 的 sing-box 稳定通道       | 应用 A                                     | 应用 B          |
| ------------------------- | ---------------------------------- | ------------------------------------------ | --------------- |
| 现在                      | `1.14.4`（世代 1.14）              | 可更新到 1.14.4                            | —               |
| 上游发布 1.14.5           | `1.14.5`                           | 可更新到 1.14.5                            | —               |
| 上游发布 1.15.0           | `1.15.0`（1.15）、`1.14.5`（1.14） | 仍是 1.14.5；提示“1.15 需要升级 Nyanpasu”  | —               |
| 发布应用 B                | 不变                               | 不变                                       | 可更新到 1.15.0 |
| 上游发布 1.14.6 与 1.15.1 | `1.15.1`、`1.14.6`                 | 可更新到 1.14.6                            | 可更新到 1.15.1 |
| 上游停止维护 1.14         | `1.15.x`、`1.14.6` 留在清单里      | 停在 1.14.6                                | 跟随 1.15       |
| 1.14 滑出清单保留的组数   | 只剩更新的世代                     | 没有可安装的更新；已安装的 1.14.6 继续可用 | 不受影响        |

应用 A 在任何时刻都不会被引导到它写不对配置的内核。

## 6. 升级预检

世代门控挡住的是“Nyanpasu 写的片段不对”。还有一类失败它挡不住：用户自己的 Profile 用了新版本里被移除的字段。这类失败在换完二进制、重启内核时才暴露，那时旧二进制已经没了。

在替换二进制之前加一步预检，放在现有的内核替换工作流里（`C/client/core_lifecycle/workflow.rs` 的 `replace_binary`）：

1. 下载并解包新二进制到暂存位置（现有步骤）。
2. 读新二进制的版本，解析世代。不在支持集合内：中止，报 `UnsupportedCoreGeneration`。清单筛选正常时不会走到这里；这是给清单与二进制不一致准备的防线。
3. 用新世代重新构建当前选中 Profile 的运行配置候选。
4. 用新二进制对候选跑校验（`check`）。
5. 通过：继续现有的替换与重启流程。
6. 不通过：中止替换，保留旧二进制，返回结构化错误，带内核的校验输出。界面显示“新版本拒绝了当前配置”与输出摘要，让用户决定是修改 Profile 还是暂不升级。

边界：

- 只对正在使用的内核做预检。更新一个没在用的内核不构建配置，只做第 2 步。
- 没有选中 Profile 时用空白配置做第 3、4 步，验证的是 Nyanpasu 自己的片段。
- 预检对 Clash 家族同样执行第 3、4 步（世代不变，构建结果与当前相同）。它们的校验命令已经在启动与切换路径上用过，这里多跑一次的成本是一次子进程。这样两个家族走同一条路径，不为 sing-box 写特例。
- 预检失败不是降级：没有任何状态被提交，按普通错误返回。

## 7. 各处的职责

| 组件                    | 职责                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| `nyanpasu-config`       | `SingBoxGeneration`、支持集合、版本到世代的纯解析、按世代的受管设定写入器        |
| `nyanpasu-contracts`    | `CoreVersionReader` 端口（已有）；版本横幅解析增加 sing-box                      |
| `nyanpasu-os`           | 读版本的实现增加 sing-box 的探测参数                                             |
| `nyanpasu-updater`      | 读 v2 清单、按世代选版本、暴露“有需要升级应用的新版本”这一信息                   |
| `nyanpasu-core`         | 构建前解析世代、世代缓存、升级预检、弃用警告的读取                               |
| `scripts/src/manifest/` | 生成 v2 清单；v1 生成不变                                                        |
| `scripts/src/prepare/`  | 随包内核按同一规则取版本                                                         |
| 前端                    | 内核管理页显示当前世代、可更新版本、需要升级应用的提示、预检失败的输出、弃用警告 |

依赖方向不变：updater 不依赖 core，世代集合由组合根或调用方传入 updater，而不是 updater 反过来引用 core 的常量。集合定义在 `nyanpasu-config`，updater 已经依赖它（`U/updater/mod.rs` 使用 `ClashCore`）。

## 8. 测试

| 对象           | 方法                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| 版本到世代     | 表格化：稳定版、预发布版、带构建后缀、无法解析、低于下限                                                           |
